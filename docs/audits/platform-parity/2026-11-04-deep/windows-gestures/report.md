## Confirmed actionable findings

### WG-001 — Onboarding reports successful gesture activation when device restart never succeeds

Severity **medium**, confidence **high**. Executed worker probe:

| Stubbed device outcome             | Actual onboarding worker exit / result token | Actual tray restart worker exit / result token |
| ---------------------------------- | -------------------------------------------- | ---------------------------------------------- |
| Device present, operations succeed | 0 / 0                                        | 0 / 0                                          |
| No matching devices                | **0 / 0**                                    | 1 / 1                                          |
| Disable operation refuses          | **0 / 0**                                    | 1 / 1                                          |
| Enable operation refuses           | **0 / 0**                                    | 1 / 1                                          |

`ui/onboarding/gesture_registration.ahk:_Onboarding_BuildGesturePsScript :244–254` does not reject an empty device set; it invokes both PnP mutations with `-ErrorAction SilentlyContinue`, then unconditionally sets success code 0. `$ErrorActionPreference='Stop'` does not override an explicit `-ErrorAction SilentlyContinue`. Both no-device and nonterminating-error branches therefore reach success. The worker also has no finally that retries enabling a successfully disabled device if the enable phase fails.

The AHK result reader at `:171–189` correctly reads token 0 and passes it to the actual wizard completion `ui/onboarding/webview.ahk:651–665`, which sets success in the UI. This is a **false device-activation result**, not merely a successful registry write: the worker/module comments explicitly promise both writes and restart; the kernel driver caches mappings until restart/sign-in (`modules/gestures/config.ahk:882–886`, `touchpad_registry.ahk:337–340`). Registry intent may be correct while current gesture output remains unchanged; an enable failure can leave a disabled device unrecovered by this worker.

Negative control/sibling: `_GestureRestartBuildPsScript` at `config.ahk:1076–1082` rejects zero devices, uses `-ErrorAction Stop`, tracks disabled devices and retries enable in finally. The exact same injected failures produce failure token 1 there. Existing single-source registry test passes because values/backup ordering agree; it does not compare restart outcome semantics.

Suggested regression: execute both emitted PS scripts with device command doubles for none/disable error/enable error/partial multi-device failure, asserting token failure and re-enable attempts. Retain a single restart worker body or an explicit equivalence gate; do not infer success from process disappearance or only successful registry writes.

### WG-002 — An existing unreadable/malformed backup permits overwriting values that cannot be restored

Severity **medium**, confidence **high** by source proof; AHK scenario unexecuted. `TouchpadRegistryEnsureBackup` at `modules/gestures/touchpad_registry.ahk:142–144` returns true based solely on file existence, without reading/parsing the backup. The create-race fallback at `:150–153` also trusts existence alone. `TouchpadRegistryApply :182–203` then writes all 34 generated values. Onboarding similarly trusts EnsureBackup before elevation (`gesture_registration.ahk:90–116`).

But actual restore `touchpad_registry.ahk:306–316` requires `_TouchpadRegistryParseBackup` to accept the exact header/key/full current name inventory; malformed/unreadable/missing-field backups refuse restoration. A malformed existing file can therefore authorize destructive configuration while proving no restoration path. A readable original current registry is not snapshotted at all on the existence shortcut, so newly overwritten original values cannot be recovered from that invalid file. A retained backup from a future/older changed value inventory has the same compatibility risk, although no current migration incident was observed.

Unexecuted in-memory repro is provided in `native-repros.ahk`: use the existing `_TPR_*` test seams, set the backup file to `"garbage"`, call `_TPR_Apply()`. Current source returns true/writes every value; `_TPR_UnprovableBackupIsRefused` in the existing suite already proves that Restore rejects that exact garbage. Existing suite covers malformed **restore**, not malformed backup **before apply**.

Negative controls: refusal to create a new backup or a non-DWORD original value already prevents every write (`test_touchpad_registry.ahk:188–202`). A valid existing original backup must remain immutable; the proposed fix is to validate its readability/schema/inventory, **not replace it with Ergopti's current values**. A concurrent create result also needs that proof.

Suggested regression: malformed, unreadable, wrong-version/key and missing-name existing backup all refuse Apply and onboarding launch with zero registry writes; valid existing backup remains unchanged and permits retry. Explain a recovery path instead of silently falling back to factory defaults and claiming original settings were preserved.

### WG-003 — Cross-account UAC elevation changes the hive onboarding writes

Severity **medium**, confidence **medium**: exact source premise plus established Windows account-context behavior; **native two-account reproduction not executed**.

The onboarding launcher backs up the resident user's `HKEY_CURRENT_USER` using `TouchpadRegistryEnsureBackup` before launch (`gesture_registration.ahk:90`). It then starts the entire registry-and-PnP worker using `*RunAs` (`:116`). The generated worker uses `HKCU:\Software\Microsoft\Windows\CurrentVersion\PrecisionTouchPad` (`_generated/touchpad_registry.ahk:23`, builder `:226`). No original-user SID or explicit HKU target is carried across elevation.

With a standard user A entering a distinct administrator B's credentials at UAC, the elevated process runs as B and HKCU is B's hive. Original settings backed up are A's; values written are B's. Result can report success while A's gestures are unchanged, and clearing later restores A only, leaving B's changed settings outside that backup. No production A_IsAdmin/same-account restriction was found in the entry/onboarding path. This is conditional on cross-account credential elevation, not ordinary consent-only elevation by an administrator.

Negative control: tray `GestureAutoConfigureRegistry :871–890` invokes TouchpadRegistryApply **in the resident process first**, and elevates only the subsequent PnP restart, so it does not have this HKCU identity mismatch. Same-account administrator consent likewise targets the same hive.

Suggested fix/test: use the already supported in-process HKCU write owner before elevating only PnP work, or retain/validate the original user's explicit SID-based hive target and backup identity. Native test must compare both users' hives before/after with different UAC credentials; no current source-only passing test is presented as that test.

## Dispatch, parameters, lifecycle and rollback: verified chains and refutations

- **Capture is keyboard shortcut delivery**, not raw touchpad events: `modules/gestures/init.ahk:282–291` binds Ctrl+Win+Shift+F1..F10 to ten slot IDs. GestureDispatch (`:209–260`) checks loaded state, feature enabled, slot assignment and action existence/AI availability; it releases only logically held carrier modifiers whose physical key is up (`GestureReleaseOwnedCarrierModifiers :177–194`). It leaves a genuine user-held modifier alone. No claim of device-source authentication follows from these chord hotkeys: the same keyboard chord can invoke them.
- **Assignment and parameter publication are joined**, not independent disk mutations: `_GestureCommitAssignment` (`config.ahk:516–550`) prepares cloned assignment/parameter maps, commits one Updates batch, and publishes both under Critical only after success. Program actions are stopped before replacing their parameters. Missing/invalid action parameters are checked by shared rule parsers and at execution; this audit did not establish a new assignment-with-missing-parameter bug.
- **Confirmation owns the original target**: `GestureInvokeAction :606–650` detaches HWND/PID/class, resolves force-quit PID and acquires a process lease before deferring. `_GestureConfirmThenInvoke :723–784` checks suspension/target before and after the question and focus restoration; deferred native system dispatch has its own pause and target validation (`system_actions.ahk:106–152`). “Kills whichever app is focused after the dialog” is refuted by these exact target checks. No native HWND/PID reuse test was executed.
- **Pause is not only native Suspend** for the actual output owners: click holds are explicitly released by lifecycle; click/clipboard/screenshot/system actions have owner-specific guards and cleanup. The source contains tests for pre-Critical pause admission (`test_gesture_pause_admission.ahk`) and clipboard admission; these native tests were inspected, not run here. A rapid pause→resume pulse across arbitrary deferred action may require a separate policy/epoch decision; no new confirmed defect is claimed from absence of one generic top-level A_IsSuspended check.
- **Async worker receipts**: both launchers reserve a generation before launching, use their own result files as authority, and defer UI completion while suspended. `_GestureRestartReadResult :1046–1065` distinguishes a string `"0"` from false; `_Onboarding_ReadGestureAutoResult :171–189` also type-checks it. Numeric-zero string mishandling and PID-disappearance false success are already fixed; WG-001 is failure to produce a truthful token, not failure to read it.
- **Malformed restore refuses before mutation** and failed value restores retain the backup. That protection does not close WG-002's earlier Apply admission hole. Partial **Apply** explicitly reports error and refreshes availability from current registry (`config.ahk:873–881`); backup remains for a manual restore, rather than an automatic all-or-nothing registry rollback. No claim that Apply is transactionally atomic is justified.
- **Clear is not one atomic registry+config transaction**: `_GES_ApplyScope` (`menu_gestures.ahk:96–106`) restores touchpad first and then starts scoped config commit; global clear does the same (`infra/config_global_scope.ahk:58–63`). Ordering is explicitly chosen so UAC does not block reload handoff. Registry status is retained as `receipt.touchpad`; config gateway rollback does not restore the prior registry generation. A failed native restore also does not prevent independent config clearing. This is an observed partial-completion policy/limitation, **not established as a new undocumented atomicity violation**; callers must not describe a config receipt as proof both native and config portions committed. Parent may choose a stronger product contract separately.
- **Registry restored ≠ already active mapping**: Restore returns restored/factory status after writes, requests restart, and logs that refused restart applies next sign-in (`touchpad_registry.ahk:337–343`). Menu registry snapshot proves stored values, not the currently cached device gesture map. Document both phases. WG-001 specifically violates the worker's restart result.
- Stale `precision_touchpad_registry.toml` comment says newer Action values are off, but generated data, generator, status predicate and actual writer consistently use 65535. There is no new writer/status mismatch proven from that comment.
