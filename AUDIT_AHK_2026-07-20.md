# Adversarial audit — ErgoptiPlus AHK driver (`static/ergopti_plus/windows`)

**Date:** 2026-07-20 · **Scope:** whole Windows driver · **Method:** loop-until-dry adversarial reading, 7 parallel domain passes + auditor re-verification of every headline claim.

> **This is the SECOND audit dated 2026-07-20.** The first (`AUDIT_AHK_2026-07-20.md`, 47 findings, commit `1171adc90`, removed by `08382fb56`) was completed earlier the same day and all 47 of its regression tests are green. This pass audits *past* that one: it re-verifies the 47 fixes, then targets the three clusters the previous pass explicitly marked `1*` ("one pass clean, not proven dry"): **keylogger/metrics, LLM, UI windows**.

## 1. Executive summary

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 13 |
| Medium | 17 |
| Low | 5 |
| **Total confirmed** | **35** |

Baseline health is genuinely good: **3212/3212 tests pass**, **912/912 `.ahk` files are UTF-8-BOM + LF**, the full `Ahk2Exe` compile succeeds (the only parse gate for the ~30 UI files absent from `run_all.ahk`), and no raw `Menu.Add(label, callback)` bypasses the dispatcher anywhere.

### The dominant pattern, again

Not one finding is a new bug *class*. Every single one is a known, already-fixed invariant with **one un-migrated sibling site**, or a guarantee **defeated one call level up by indirection** — exactly what `project_ahk_invariant_incomplete_application` predicts. Three findings are direct regressions introduced by **yesterday's own hardening commits**, each shipped with a regression test that is structurally blind to the collateral it caused:

- **F-01** — the previous audit's F33 removed `Critical` from `RebuildHotstringsLive`; its test asserts `Critical(` is absent *from that function's body*. One caller re-wraps the call from outside, restoring the exact 1-2 s keyboard freeze F33 removed.
- **F-05** — commit `76fda09de` made `TooltipShow` deferred; the LLM spinner's "cancel the safety timer" line now runs 75 ms *before* the timer is armed, so the spinner is force-hidden mid-inference.
- **F-20** — `_TooltipPresentStack` already takes an `ArmSafety` parameter, but the deferred path hardcodes `true`, so the opt-out is unreachable.

### Most fragile zones

1. **The WebView2 window layer — 11 findings, one shared mechanism.** `lib/webview_utils.ahk` contains a `WebViewHost` factory that handles all four documented gotchas *plus* suspend guards, epoch fencing and ready-once latching, **correctly — and it has zero consumers**. All 14 windows are hand-rolled copies, so every cross-cutting guard was applied only to the sites its regression test happens to name. That single structural fact (F-33) produces F-24 through F-32.
2. **Cross-boundary ordering assumptions** — several findings are "statement A must precede statement B" contracts with no assertion, broken by a refactor that moved B behind a timer.
3. **Keylogger under pause** — the hot path is correctly gated at one chokepoint, but *shutdown* and *accounting* paths are not: a quit/reload while paused silently discards every closing lifecycle event, and a pause is billed verbatim as foreground app time.
4. **Suspend guards on repeating timers and COM handlers** — applied per-site, never per-class: `MF_RefreshFocus` (20 Hz, blocking `WM_GETTEXT`) has no guard, no cancel site, and is armed even when its consuming feature is off; 7 of 9 webview handlers are unguarded.

### The single highest-leverage change

Convert the guard tests from **site lists** to **enumerated class loops**. Five findings (F-01, F-18, F-25, F-30, F-33) exist purely because a regression test pins the one site that was fixed rather than the invariant. `test_webview_bridge_suspend_guard.ahk` is the clearest case: rewriting it to iterate all nine handlers closes F-25 *and* prevents the next window from re-introducing it.

### Honest verdict

The driver is **well-defended and improving**, but it is **not currently provable against G4**. See §3: the previous audit's entire performance section cites log evidence that does not exist in any available artifact, and the driver's own log directory is empty. **No latency measurement of this driver exists.** Every G4 claim in this report — mine included — is derived from reading code, not from measurement. The single highest-value next action is not a code fix: it is to **run the driver and capture one real `[HotPath] Slow` log.**

I make no claim that the driver is free of defects. §5 is the coverage register: absence of a finding there means "audited, with the reason it is safe", not "not looked at".

### F-01 — `ToggleCategoryAllFeatures` re-wraps `RebuildHotstringsLive` in `Critical`, restoring the multi-second keyboard freeze F33 just removed

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading (auditor-verified) |
| **Guarantee** | **G4** (lag), **G3** (hook starvation → dropped keystrokes) |
| **Files** | `lib/config_io.ahk:217-230` |

**Repro.** Driver ready. Tray → `⚡ Hotstrings` → `Rolls` → click the category ON/OFF toggle. (`_IsLiveHotstringCategory`, `config_io.ahk:196-199`, returns true only for `Rolls`/`SFBsReduction`, so this takes the live branch.) Type continuously during the toggle → keystrokes freeze/drop for 1-2 s, worse on a cloud-synced config dir.

**Root cause.** `_TcafCrit := Critical("On")` at `:217` spans through `:227`, covering `TOML_Write` (file write), `ApplyMasterGatesToFeatures` (uncached 12.5 KB `FileRead` + `JsonParse`, see F-11) and `RebuildHotstringsLive()` — which re-runs `RegisterAllHotstrings` (~1.3 s) plus, via `RebuildTrayMenu` → `_HS_InvalidatePersonalCache`, a full recursive personal-hotstrings walk (`Loop Files` to depth 16 + a TOML parse per file) and the bundled-extensions scan.

This is the **exact** cost the previous audit's F33 removed. `RebuildHotstringsLive` (`ui/menu/menu_rebuild.ahk:111`) is now Critical-free and says so at `:118-122`: *"This is deliberately NOT wrapped in Critical … holding Critical across all of that froze the keyboard for 1-2 s on every tray hotstring toggle."* Three of its four callers respect that (`menu_engine.ahk:403`, `menu_hotstrings.ahk:154`, `:192`). `config_io.ahk:227` is the one that does not.

**Why it is silent.** Two reasons, both verified:

1. The outer `Critical` is justified by a comment at `:215-216` — *"RebuildHotstringsLive() re-enters Critical internally; that is safe"* — which **F33 made false**. `menu_rebuild.ahk` has no `Critical` in that function (the only one, `:73`, is in the unrelated `TrayMenuStage_Publish`).
2. The F33 regression test `tests/meta/test_live_rebuild_no_critical_io.ahk:30` asserts `InStr(Body, "Critical(") = 0` against **`RebuildHotstringsLive`'s body only**. A caller-applied `Critical` sails straight through. This is verbatim the weakness PROJECT_MEMORY documents: *"a guard test scoped to one function's body is necessary but not sufficient for a transitive guarantee."*

At runtime the failure is invisible: Windows silently drops keystrokes past `LowLevelHooksTimeout` with no error — the mechanism `menu_dispatcher.ahk:530-533` and `lifecycle.ahk:262-267` both already document.

**Fix.** Hold `Critical` over the in-memory mutation window only; release before persistence and the rebuild.

```autohotkey
_TcafCrit := Critical("On")
try {
	if Bool
		_HSRestoreCategory(V2Cat)
	else
		_HSSnapshotCategory(V2Cat)
	CategoryEnabled[Category] := Bool
	ApplyMasterGatesToFeatures(Features, TapHold, IsCategoryGated, LoggerDebug)
} finally {
	Critical(_TcafCrit)
}
; Persistence and the ~1.3 s engine/menu rebuild must stay OFF the Critical path: both do
; unbounded file I/O, and Critical starves the LL keyboard hook past LowLevelHooksTimeout,
; which makes Windows silently drop physical keystrokes (F33's regression, reintroduced here).
TOML_Write(Bool, ConfigurationFile, "ahk.category_enabled", _CategoryEnabledKey(Category))
RebuildHotstringsLive()
return
```

This still satisfies every existing assertion in `tests/meta/test_toggle_category_all_features_atomic.ahk` (it pins `CritPos < RestorePos/SnapshotPos/GatesPos` and `GatesPos < RebuildPos`, never that `Critical` covers the rebuild).

**Regression test** — the root cause is *"the guarantee is transitive, so the test must cover the whole call class, not one body"*. Extend `tests/meta/test_live_rebuild_no_critical_io.ahk`:

```autohotkey
; Root cause: F33 removed Critical from RebuildHotstringsLive, but the guarantee is
; TRANSITIVE — any caller holding Critical across the call restores the freeze. A test
; scoped to the callee's body cannot see that, so assert it across every call site.
_LRNC_NoCallerHoldsCriticalAcrossRebuild() {
	for _, Fn in ["ToggleCategoryAllFeatures", "_HS_TryLiveToggleV2", "HotstringsSetSectionDelay"] {
		Body := _DriverFuncBody(Fn)
		if (Body == "")
			continue
		RebuildPos := InStr(Body, "RebuildHotstringsLive()")
		if (RebuildPos == 0)
			continue
		AcqPos := InStr(Body, 'Critical("On")')
		if (AcqPos == 0 or AcqPos > RebuildPos)
			continue
		RelPos := InStr(Body, "Critical(_")            ; the restore-previous-level call
		Assert(RelPos > 0 and RelPos < RebuildPos,
			Fn . " must release Critical BEFORE RebuildHotstringsLive(): that call re-runs "
			. "RegisterAllHotstrings (~1.3 s) plus a recursive personal-hotstrings + extensions "
			. "rescan, and holding Critical across it starves the LL keyboard hook past "
			. "LowLevelHooksTimeout so Windows silently drops physical keystrokes (F33 regression)")
	}
}
Test("menu: no caller holds Critical across the live hotstring rebuild", _LRNC_NoCallerHoldsCriticalAcrossRebuild)
```

### F-02 — Boot strips the apostrophe word-boundary from the engine but not from the preview: previewed autocorrections never fire

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading |
| **Guarantee** | **G2** (missing output), **G3** (two sources of truth diverge) |
| **Files** | `lib/hotstrings/hotstring_inputhook.ahk:103` · `lib/boot.ahk:104` · `lib/hotstrings/hotstring_engine_main.ahk:76` · `lib/hotstrings/hotstring_match.ahk:418-423` |

**Repro.** Fresh install, no `word_delimiters` override, `hotstrings.autocorrection.accents` enabled (default). Type `l` `'` `a` `m` `e` → tooltip **appears** showing `âme`. Type space → **nothing expands**; the screen keeps `l'ame `.

**Root cause.** `_PREFIX_WORD_BOUNDARIES` (`hotstring_inputhook.ahk:103`) is a top-level global initializer that **snapshots** `HSE_WORD_TERMINATORS` at include position (`ErgoptiPlus.ahk:275`). `boot.ahk:104` then *replaces* `HSE_WORD_TERMINATORS` with `HotstringsGetWordDelimiters()` — the catalogue default, which contains **no apostrophe** (`_generated/terminators.ahk:73-74`: `apostrophe_typo`/`apostrophe_straight` are both `default_enabled: false`) — and never recomputes the preview set.

So the tooltip anchors on a boundary set containing `'` (finds `SearchKey = "ame"`, renders `âme`), while `_HSE_WordBoundaryAllows` (`hotstring_match.ahk:418-423`) tests `InStr(HSE_WORD_TERMINATORS, "'")` → 0 → no candidate → no fire. The sets also diverge the other way: the boot set gains `★`, which the preview set lacks, so after a non-firing magic-key press `_PrefixBuffer` accumulates `…ab★` and the preview goes dead for the rest of the word.

**Why it is silent.** No error path. The user sees a correct-looking preview and an expansion that simply does not happen. The `Chr()`-spelled "tamper-proof" comment at `hotstring_engine_main.ahk:69-75` documents the apostrophe intent, making the boot overwrite read as deliberate. And `HotstringsSetWordDelimiters` (`hotstrings_io.ahk:146-161`) repairs *both* globals — so any session where the user touches the word-expander menu behaves correctly, masking it from manual testing.

**Fix.** Make the preview set derived, never snapshotted. In `lib/hotstrings/hotstrings_io.ahk`:

```autohotkey
; Extra boundaries the PREVIEW anchors on but the engine does not treat as hotstring
; terminators: double quotes can legitimately sit inside a trigger body.
global HOTSTRINGS_PREVIEW_EXTRA_BOUNDARIES := Chr(0x22) . Chr(0x201C) . Chr(0x201D)

; Recompute the preview boundary set from the LIVE engine terminator set. SINGLE SOURCE
; OF TRUTH — every writer of HSE_WORD_TERMINATORS must call this, or the tooltip and the
; matcher anchor on different sets and previewed expansions silently never fire.
HotstringsRefreshPrefixBoundaries() {
	global HSE_WORD_TERMINATORS, _PREFIX_WORD_BOUNDARIES, HOTSTRINGS_PREVIEW_EXTRA_BOUNDARIES
	if !IsSet(_PREFIX_WORD_BOUNDARIES) {
		LoggerError("HotstringsConfig",
			"HotstringsRefreshPrefixBoundaries(): prefix watcher not loaded — preview boundaries not refreshed.")
		return
	}
	_PREFIX_WORD_BOUNDARIES := HSE_WORD_TERMINATORS . HOTSTRINGS_PREVIEW_EXTRA_BOUNDARIES
	LoggerDebug("HotstringsConfig", "Preview boundaries refreshed ({1} char(s)).", StrLen(_PREFIX_WORD_BOUNDARIES))
}
```

Call it at `lib/boot.ahk:105` (immediately after the `HSE_WORD_TERMINATORS :=` assignment) and replace the inline recomputation at `hotstrings_io.ahk:156-158` with the same call. Separately, settle the apostrophe question in **one** place — either flip the two `apostrophe_*` terminators to `default_enabled: true` in `_shared/core/domain/Terminators.spec.js` and regenerate, or delete the now-dead `Chr(0x27) . Chr(0x2019)` tail at `hotstring_engine_main.ahk:76`. Keeping both is what let the drift hide.

**Regression test** — encode the root cause (*derived, not snapshotted*), not the apostrophe symptom. `tests/unit/test_hotstrings_config.ahk`:

```autohotkey
; Root cause: _PREFIX_WORD_BOUNDARIES was snapshotted from the COMPILE-TIME
; HSE_WORD_TERMINATORS at include position and never recomputed after boot replaced
; that global from the terminator catalogue.
_HC_PrefixBoundariesTrackEngineSet() {
	global HSE_WORD_TERMINATORS, _PREFIX_WORD_BOUNDARIES, HOTSTRINGS_PREVIEW_EXTRA_BOUNDARIES
	SavedWT := HSE_WORD_TERMINATORS, SavedPB := _PREFIX_WORD_BOUNDARIES
	HSE_WORD_TERMINATORS := " ~"                      ; shares NO char with the default set
	HotstringsRefreshPrefixBoundaries()
	Assert(_PREFIX_WORD_BOUNDARIES == " ~" . HOTSTRINGS_PREVIEW_EXTRA_BOUNDARIES,
		"_PREFIX_WORD_BOUNDARIES must be DERIVED from the live HSE_WORD_TERMINATORS, never snapshotted")
	Assert(InStr(_PREFIX_WORD_BOUNDARIES, ".") == 0,
		"a char dropped from HSE_WORD_TERMINATORS must disappear from the preview set too")
	HSE_WORD_TERMINATORS := SavedWT, _PREFIX_WORD_BOUNDARIES := SavedPB
}
```

Plus a meta guard asserting `lib/boot.ahk` contains a `HotstringsRefreshPrefixBoundaries()` call textually **after** its `HSE_WORD_TERMINATORS := HotstringsGetWordDelimiters()` line.

### F-03 — `is_case_sensitive` is interpreted **inverted** by `LoadHotstringsSection` versus every other registration path

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading |
| **Guarantee** | **G2** (wrong output; preview ≠ engine) |
| **Files** | `lib/toml/toml_loader.ahk:376-380`, `:453-457` vs `lib/hotstrings/hotstrings_cache.ahk:406-409`, `lib/hotstrings/personal_toml_io.ahk:555-559`, `lib/hotstrings/hotstring_registry.ahk:280-296` |

Three implementations agree that `is_case_sensitive = true` ⇒ plain `CreateHotstring`. `LoadHotstringsSection` and `LoadExtTomlFile` do the **opposite** — while `hotstrings_cache.ahk:374-382` explicitly claims it *"Reproduces the runtime TOML fallback (LoadHotstringsSection) 1:1 … and the CreateHotstring vs CreateCaseSensitiveHotstrings choice."*

**Repro.** Personal section `emailshortcuts` enabled, `personal_hotstrings.toml` containing `"btw★" = { output = "by the way", …, is_case_sensitive = false, … }` (exactly what `personal_toml_io.ahk:301-310` writes for an *unchecked* "case sensitive" box).

1. Boot. `_HS_RegisterPersonal` → `LoadHotstringsSection("personal", …)`. The cache fast path is skipped for personal (`toml_loader.ahk:292-294`), so `IsCaseSens = false` → **`CreateHotstring`** ⇒ one case-insensitive spec, no conform.
2. `HotstringPrefixWatcherRebuildIndex` → `_AddTriggerVariants(…, IsCaseSensitive := false, …)` ⇒ indexes `btw`/`Btw`/`BTW`.
3. Type `B` `T` `W` → tooltip shows **`BY THE WAY`**. Press the magic key → screen gets **`by the way`**.
4. Open the personal-hotstrings editor, press Save without editing. `ReloadPersonalSection` re-registers via `CreateCaseSensitiveHotstrings`.
5. Type `BTW★` again → screen now gets **`BY THE WAY`**.

Same data, same session, no Reload — behaviour flips because two paths read the flag oppositely. The mirror case (`= true`) is worse: boot registers three cased variants the preview index never contains, so Title/UPPER typing fires an expansion **with no tooltip at all**.

**Root cause.** Two independent transcriptions of the generator convention `is_case_sensitive = not case_sensitive` (documented at `hotstring_registry.ahk:132-138`) were never reconciled. Bundled categories always short-circuit into the cache registrar, so the TOML branch is exercised **only** by `personal` and by extension `*.toml` — the two paths with no automated corpus coverage.

**Why it is silent.** Both branches register successfully; only emitted casing differs. The cache/TOML equivalence test pins the **preview index**, not the **engine registration**, so it is structurally blind to this.

**Fix.** One helper next to the flag's definition; route all four sites through it.

```autohotkey
; lib/hotstrings/hotstring_builder.ahk
; TOML generator convention: `is_case_sensitive = not case_sensitive`.
;   TRUE  -> register the literal trigger only (plain CreateHotstring).
;   FALSE -> register the cased family (CreateCaseSensitiveHotstrings / conform).
; SINGLE SOURCE OF TRUTH — the two open-coded copies of this branch had drifted into
; opposite meanings, so the personal/extension paths registered the wrong casing family.
HSE_RegisterFromTomlFlags(IsCaseSensitive, Flags, Trigger, Output, Options) {
	if IsCaseSensitive {
		CreateHotstring(Flags, Trigger, Output, Options)
		return
	}
	CreateCaseSensitiveHotstrings(Flags, Trigger, Output, Options)
}
```

**Regression test** — encode *"all loaders must agree"*, not the casing symptom. In `tests/unit/test_hotstrings_full.ahk`, assert `HSE_RegisterFromTomlFlags(false, …)` produces the same registry size as a direct `CreateCaseSensitiveHotstrings(…)`, and that `HSE_RegisterFromTomlFlags(true, …)` yields exactly one spec. Plus a meta guard that none of `toml_loader.ahk`, `hotstrings_cache.ahk`, `personal_toml_io.ahk` still contains an open-coded `CreateCaseSensitiveHotstrings` inside an `is_case_sensitive` branch.

### F-04 — `HSE_TypoNbspStripped` leaks from the end-char probe into a star match: one extra BackSpace eats a user character

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading |
| **Guarantee** | **G1/G2** (wrong, destructive output) |
| **Files** | `lib/hotstrings/hotstring_match.ahk:180-191`, `:214-215` · `lib/hotstrings/hotstring_dispatch.ahk:240` · `lib/hotstrings/hotstring_engine_main.ahk:739` |

**Repro.** `hotstrings.sfbs_reduction.e_circ` enabled (default). Type `a` `b` `Ê` then **Shift+comma** (the Ergopti Shift layer emits NNBSP `U+202F` then `;`).

On the `;` keystroke `HSE_Buffer == "abÊ" + NNBSP + ";"`:
- **Star path** (`hotstring_match.ahk:131-163`) matches the 3-char suffix `Ê`+NNBSP+`;` → `BestMatch = Spec{Length:3}`, `BestEndChar = ""`.
- **End-char path** (`:166-211`) independently sets `HSE_TypoNbspStripped := true` at `:186` during *preprocessing*, before any winner is known.
- The star candidate wins (`_HSE_EndCharBeats` requires `Cand.Length > 3`).

`HSE_DispatchMatch` then computes `BSCount = 3 + 0 + 1 = 4` → `{BackSpace 4}` + `U,`.

Expected `abU,` — **actual `aU,`**. The user's `b` is gone.

**Root cause.** `HSE_TypoNbspStripped` is a side-effect flag written during candidate *discovery* but read as if it described the *winning* candidate. It is only meaningful when the end-char candidate that consumed the stripped NBSP wins.

**Why it is silent.** `HSE_ApplyExpansion` (`hotstring_engine_main.ahk:739`) applies the identical `+1`, so the internal buffer stays consistent with the corrupted screen — there is no downstream desync to trip an alarm. The only trace is a DEBUG-gated log line. And on the far more common end-char path the flag *is* correct, so targeted testing of typographic `:`/`;` passes.

**Fix.** Make the flag describe the winner, at the one point where the winner is known — immediately before `hotstring_match.ahk:214`:

```autohotkey
	; The NBSP strip is a property of the END-CHAR candidate that consumed it. When the
	; star path wins, no NBSP was consumed by the match, so the flag must not survive into
	; the dispatcher's BackSpace count — it would delete one character the user typed
	; before the trigger.
	if (BestEndChar == "")
		HSE_TypoNbspStripped := false
	HSE_LastEndChar := BestEndChar
	return BestMatch
```

**Regression test** — `tests/unit/test_hotstring_engine_main.ahk`: register the `Ê`+NNBSP+`;` star trigger, feed `a` `b` `Ê` NNBSP `;`, then assert `HSE_LastEndChar == ""`, `HSE_TypoNbspStripped == false`, and that the dispatcher's `BSCount` formula equals exactly the trigger length (3) — *"the BackSpace count must erase the trigger only, never the preceding character."*

### F-05 — The LLM loading spinner is force-hidden after 3 s, mid-inference

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading (auditor-verified) |
| **Guarantee** | **G3** (race), **G2** (lost output) |
| **Files** | `ui/tooltip/llm.ahk:197-199` · `ui/tooltip/core.ahk:298-314`, `:407` · `ui/tooltip/helpers.ahk:106-107` |

`LLM_TooltipShowLoading` believes it renders synchronously:

```autohotkey
TooltipShow([{ Text: label, ColorHex: accent, IsDimmed: false, DurationSec: 0 }], 0)
; TooltipShow arms a 3 s safety timer — cancel it so loading survives slow inference.
SetTimer(_TooltipTimerFn, 0)
```

It no longer does. `TooltipShow` (`core.ahk:309-313`) now only stores the payload and arms `SetTimer(_TooltipDeferredShowFn, -TOOLTIP_RENDER_DEBOUNCE_MS)` (75 ms). The safety timer is armed **75 ms later** by `_TooltipPresentStack` (`helpers.ahk:107`). **The cancel runs before the arm and cancels nothing.**

**Repro.** Ollama cold start, or any remote API. Type, pause → spinner appears at t≈75 ms. Response lands at t≈8 s (`ollama_http.ahk:53-55` itself allows an 8 s warmup grace). At t≈3.075 s `_TooltipTimerFn` fires; `_TooltipTimerGeneration == _TooltipGeneration` so the gate passes → `TooltipHide("TimerFn", true)`. The `"TimerFn"` tag bypasses the ownership guard (`core.ahk:555`) and clears `_LLM_Tooltip_Visible/_Loading/_ShownAt`. The spinner vanishes; the prediction pops in ~5 s later with nothing shown in between. `_ResetPrefixBuffer()` also fires as collateral.

**Root cause.** Commit `76fda09de perf(tooltip): debounce render work off hot path` (2026-07-19) made `TooltipShow` deferred. Verified against `git show 76fda09de^`: the pre-commit body called `_TooltipBuildGui`/`_TooltipPresentStack` inline, so the cancel was correctly ordered then. That commit touched `core.ahk` + `helpers.ahk` only and never inspected the one caller that opted out of the safety deadline.

**Why it is silent.** The opt-out is an *ordering assumption*, not a contract — no assertion, no log. `LoggerDebug("LLM.tt", "SHOW loading (no auto-hide).")` still asserts the old behaviour in the log. The commit shipped `test_tooltip_render_epoch.ahk::Test_TooltipShowDebouncesHeavyRenderWork`, which pins the debounce and is structurally blind to this collateral.

**Fix.** `_TooltipPresentStack` **already takes an `ArmSafety` parameter** (`helpers.ahk:90`) — see F-20; the deferred path just hardcodes `true` at `core.ahk:407`. Thread the caller's choice across the debounce instead of racing it:

```autohotkey
; core.ahk — carry the caller's safety-deadline choice across the render debounce.
global _TooltipPendingArmSafety := true

TooltipShow(Items, DurationSec := 0, ArmSafety := true) {
	…
	_TooltipPendingArmSafety := ArmSafety
```

`_TooltipDeferredShowFn` forwards it to `_TooltipShowNow`, which passes it to `_TooltipPresentStack(Pos, Row, ArmSafety)`. Then in `llm.ahk`, drop the dead cancel:

```autohotkey
	; DurationSec 0 + ArmSafety false: the spinner lives until the prediction lands or
	; LLM_TooltipHide runs — inference legitimately outlasts the 3 s safety deadline.
	TooltipShow([{ Text: label, ColorHex: accent, IsDimmed: false, DurationSec: 0 }], 0, false)
```

**Regression test** — `tests/meta/test_llm_loading_tooltip_no_safety_deadline.ahk`, encoding the root cause (*an opt-out must not depend on statement order across a deferred boundary*):

```autohotkey
Test_LoadingSpinnerOptsOutOfSafetyDeadlineExplicitly() {
	Body := _DriverFuncBody("LLM_TooltipShowLoading")
	Assert(InStr(Body, "SetTimer(_TooltipTimerFn, 0)") = 0,
		"LLM_TooltipShowLoading must not cancel _TooltipTimerFn inline — TooltipShow defers "
		. "rendering, so the safety timer is armed AFTER this call returns and the cancel is a no-op")
	Assert(RegExMatch(Body, "TooltipShow\([^)]*\],\s*0\s*,\s*false\s*\)") > 0,
		"the spinner must opt out of the safety deadline via TooltipShow's ArmSafety argument")
	Assert(InStr(_DriverFuncBody("TooltipShow"), "_TooltipPendingArmSafety") > 0,
		"TooltipShow must carry ArmSafety across the render debounce")
}
```

### F-06 — 20 Hz foreground-window probe: no suspend guard, no cancel site, armed even when its feature is off

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading (auditor-verified; independently found by two passes) |

### F-09 — `KLWV_IsIsoDate` uses `\\d`: every dashboard date-range request is silently dropped

| | |
|---|---|
| **Severity** | **HIGH** |
| **Confidence** | Confirmed by reading (auditor-verified) |
| **Guarantee** | **G1/G2** |

### F-34 — `_DeleteSection` leaves a stale persisted `default_section`, making three unguarded Map reads throw on the next open

| | |
|---|---|
| **Severity** | **MEDIUM** |
| **Confidence** | Confirmed by reading (a parallel pass supplied the repro that upgraded this from SUSPECTED) |

## 6. Adversarially rejected claims — do NOT action

Refuted during verification, recorded so they are not re-raised:

- ***"`_TooltipResolvePosition` runs a blocking UIA COM call on every keystroke."*** **Refuted — this was my own initial reading.** The double trailing debounce (`_PREFIX_RENDER_DEBOUNCE_MS` 150 + `TOOLTIP_RENDER_DEBOUNCE_MS` 75 ≈ 225 ms) is an effective idle gate, comparable to the keymap path's explicit `UIA_SELECTION_IDLE_REQUIRED_MS := 250`. Only the dead cache and the unbounded call survive, as F-17 (MEDIUM, not HIGH).
- ***"Ollama warmup retry death causes silent permanent LLM degradation."*** Refuted: two independent self-heals (the 8 s inference grace, and `_LLM_Ollama_IsReady` set on any successful prediction) bound it to "the first prediction pays the cold load" — F-21, LOW-MEDIUM.
- ***"`ShellRunner.terminate()` leaks a registration, producing a late spurious 'download failed' dialog after a suspend-abort."*** Refuted by reading `:223-225`: `terminate()` deregisters correctly.
- ***"`toml_loader.ahk:322` `.HasOwnProp` on a scalar is a live crash."*** Refuted for the current tree: every hotstring manifest entry feeding that path uses a table default. Latent only — S1.
- ***"`adapters/timer_scheduler.ahk` leaks armed handles in production."*** Refuted: zero production callers; the port is dormant.
- ***"The WPM widget still cold-starts WebView2 on the typing path."*** Refuted: all 8 `ui/wpm/` matches are comments documenting the completed GDI+ rewrite. Only the stale comments at `ErgoptiPlus.ahk:752-758`, `:862` remain, and they are documentation, not code.
- ***"`HotIf` context leaks process-wide when a `Hotkey()` registration throws"*** (`layout_shift_caps.ahk:181-192`, `:207-228`). The shape is real and systematic — the `HotIf()` reset is not in a `finally`, and `RegisterCapsLockLayer()` runs *before* `RegisterAltGrLayer()`, so a leak would gate the whole AltGr layer behind "CapsLock on". **Downgraded to SUSPECTED:** all these run in auto-execute, pre-`ready`, where a throw hits `ErgoptiGlobalErrorHandler` and `ExitApp(1)`s. The driver dies **loudly** rather than running with a corrupted criterion. Worth hardening (`_RegisterRollsAltGrHotkeys` is documented as deferrable to post-onboarding, which *would* move it past the fatal window), but not a live silent failure today.
- ***"Tap-branch synthetic modifier outside `finally` latches a modifier system-wide"*** (`capslock.ahk:143-147`, `rctrl.ahk:154-157`, `tab.ahk:104-107`). The exposure window is real but exactly one statement wide (the `KeyWait` at `:144`). **Downgraded to SUSPECTED:** a modifier latched there is logically down but *not physically held* — precisely the condition `_ShouldReleaseModifier` (`error_net.ahk:41-44`) tests before force-releasing, so the global net recovers it. (`tab.ahk:53-57` is the stronger sub-claim — that tap branch has no in-thread release at all — and is carried as S12.)
- ***"`RAlt` is an undrained custom-combination prefix."*** Refuted while confirming F-30: in `SC01D & ~SC138` the `SC138` is the **suffix**, and `tap_holds/altgr.ahk:40`'s `KeyWait("RAlt", …)` is not a combination prefix at all. Only `SC01D`, `SC02A`, `SC11D` are genuinely missing.

> **A note on why two claims were downgraded rather than dropped.** Both are absorbed by the driver's global error net and boot-phase fatal gate. That is genuinely good engineering — but it means defects of this class accumulate with **no user-visible symptom**, so the fail-fast hardening is still worth landing. The net is a backstop, not a design.
