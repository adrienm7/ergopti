  ## 8. Boucle CI → release

  Le workflow `.github/workflows/ci.yml` tourne à chaque push sur `dev`. La release est créée
  ainsi :
  - `resolve-release-meta` calcule le tag suivant `v0.0.0-dev.<N>`. Ce job exige que
    `macos-ok`, `windows-ok` et `linux-ok` aient réussi.
  - `build-macos`, `build-windows`, `build-linux` et `release-gate-macos` s'exécutent ensuite.
  - `finalize-release` fait le `gh release create`, en prerelease, avec comme cible le SHA
    poussé.

  Pour chaque SHA poussé :

  ```bash
  SHA=$(git -C D:/Documents/GitHub/ergopti rev-parse origin/dev)
  gh run list --workflow ci.yml --branch dev --commit "$SHA" --json databaseId,status,conclusion
  gh run watch <id> --exit-status > C:/ewtb/ci-<id>.log 2>&1   # jamais dans un pipe tail/head
  gh run view <id> --json conclusion,jobs --jq '.conclusion, (.jobs[] | select(.conclusion!="success" and .conclusion!="skipped") | .name + " "
  + .conclusion)'
  gh release list --limit 5 --json tagName,isPrerelease,createdAt
  gh api repos/adrienm7/ergopti/releases/tags/<tag> --jq .target_commitish   # doit valoir $SHA
  ```

  **Condition de fin :** le run du SHA est en `success` ET une release `v0.0.0-dev.<N>` existe,
  dont la cible est ce SHA et qui porte ses assets.

  **Si la CI est KO :**
  1. `gh run view <id> --log-failed > C:/ewtb/ci-<id>-failed.log`.
  2. Trouve la cause racine et reproduis-la localement quand c'est possible.
  3. Corrige avec un test de régression, dans un commit atomique.
  4. Lance `verify-change`, puis pousse sur `dev` (autorisé).
  5. Recommence la boucle.

  **Cas particuliers :**
  - **Échec d'infrastructure** (runner, réseau, timeout de téléchargement) : relance une fois
    avec `gh run rerun <id> --failed`.
  - **Blocage extérieur au dépôt** (panne GitHub, secret manquant, quota de minutes) : arrête et
    explique.
