# AUDIT_AHK_2026-06-26 — Adversarial robustness audit of the ErgoptiPlus AHK driver

**Scope:** `static/ergopti_plus/windows/` (640 `.ahk` files; ~200 source files across
`modules/`, `lib/`, `adapters/`, `ui/`).
**Goal:** prove that no user action, in any driver state, can produce an unhandled error,
a missing output, a race, or perceptible lag — and ship the fix + regression test for each
breach found. Four guarantees: **G1** robustness, **G2** no missing output, **G3** no race,
**G4** no lag.

**Method (one deep pass, two independent angles + adversarial verification).**
21 finder agents ran in parallel: 15 module-scoped finders + 6 cross-cutting class sweeps
(suspend/pause, raw `Menu.Add`, `Map[absent-key]`, blocking-on-hot-path, async-generation,
encoding/escape/logger-pairing). Every raw finding was then handed to an **independent skeptic
agent** whose default posture was "wrong until the code proves it," which re-read the cited
code to confirm or refute. The class sweeps are the second independent angle that a
loop-until-dry second round would otherwise provide; where a module finder **and** a sweep
converged on the same defect (the near-miss O(n) scan; the screenshot `RunWait`), confidence
is correspondingly high.

**Honesty note on performance.** No runtime `ErgoptiPlus_*.log` was present in the checkout
(the driver had not been run in this environment), so the `hotpath_profiler`/`boot_profiler`
"Slow …" lines could not be mined. The Performance section below is therefore **code-derived,
not log-derived** — the two hot-path costs it flags (F-M04 and F-H07) are proven from source
and reachability, not from a measured slow segment. Recommend re-running the profilers live to
quantify them.

## 1. Executive summary

| Severity | Confirmed | Notes |
|----------|-----------|-------|
| Critical | 0 | None found. The codebase is heavily hardened; the global `OnError` net, the `RegisterMenuItem` bypass, the suspend-drain, and the async-HTTP discipline are all genuinely in place. |
| **High** | **7** | Each is a *missed-sibling* of an already-applied invariant, or dead/unenforced configuration. |
| **Medium** | **12** | Suspend-leak and async-cleanup gaps, one real O(n) hot-path scan, two dead-config toggles. |
| **Low** | **9** | Log-hygiene, dormant edge cases, single-char desyncs, obscure hand-edit crashes. |
| *Suspected* | 1 | Needs a live slow-link download to confirm the WinHTTP receive-timeout semantics. |
| *Rejected* | 6 | Plausible-but-refuted by the skeptics (kept in §6 for transparency). |

**Total confirmed: 28 distinct defects** (29 raw confirmations; the near-miss O(n) scan was
found twice and is merged here as **F-M04**).

**Honest global verdict.** This is a mature, defensively-written driver. There is **no
keyboard-lockup, no crash on a default config, and no missing output on the everyday typing
path.** Every High finding follows the exact pattern PROJECT_MEMORY already names
(`project-ahk-invariant-incomplete-application`): an invariant was applied per-site and **one
sibling site was missed**, or a config flag is fully wired through menu+TOML but never read by
the engine. The recurring failure mode here is not "the fix is wrong" — it is "the fix did not
reach the last sibling," and the meta-tests anchor only the documented site, so the regression
is invisible to CI. The single most valuable structural change is to convert the existing
per-site meta-tests into **whole-class** assertions (every long-press `KeyWait` bounded; every
InputHook re-checks suspend after `Wait()`; every privacy-relevant counter bumped after the
filter; every `chunk.type`/node dereference guarded).

**Most fragile zones, ranked:**

1. **Tap-hold + InputHook suspend re-checks** — two missed sibling sites (`lalt` alt-tab hold
   leaves Alt latched; `SpaceTapHold` leaks a phantom modifier under pause). G1/G2.
2. **LLM prediction privacy & triggers** — `disabled_apps`/`disable_url_bars`/
   `instant_on_word_end` are wired through the UI and persisted but **never enforced/consumed**.
   G2 (one is a privacy breach).
3. **Crash/diagnostic path on the input thread** — the crash-report builder does blocking
   WMI + git-subprocess `Sleep` on the keyboard thread (sibling of the already-fixed crash
   `MsgBox`). G4/G1.
4. **Remote-LLM HTTP** — the *generation* hot path still does a synchronous WinHTTP TCP connect
   on the typing thread (the Ollama paths were migrated to `curl`, the remote one was not). G4/G3.
5. **Keylogger cross-process crash-replay** — `KL_JsonDecode` is a no-op on the shipped 64-bit
   binary, so the documented "crash-safe replay" guarantee is silently false. G2.

### F-H01 — `LAlt` `alt_tab_monitor` hold path: unbounded `KeyWait` latches `LAlt` Down system-wide
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G1
- **Files:** `modules/tap_holds/lalt.ahk:162`, `:170`, `:171` (block 4.3); related `modules/tap_holds/tab.ahk:58` (block 8.1)
- **Repro (initial state → actions):** Tray menu → set `LAlt` tap = `alt_tab_monitor`
  (it is a registered `GESTURE_ACTION`, `modules/gestures/init.ahk:542`, so the tap picker
  offers it). State = normal. Press and **hold** `LAlt` (SC038) past `TapHoldDuration(left_alt)`.
  `TextPressKey("LAlt","Down")` already fired at `lalt.ahk:164`; the timed wait at `:165` expires
  (tap=false) and control enters the `else` at `:170`: a **bare, unbounded**
  `KeyWait("SC038","U")`. Now lose the SC038 key-up — entirely plausible, because
  `alt_tab_monitor` itself pops the OS window switcher / changes foreground focus (a UAC prompt
  steals focus, or `Suspend` is toggled mid-press). The key-up lands on the new foreground
  target, the AHK hook never sees it, `KeyWait` blocks forever, `LAlt` stays Down.
- **Root cause:** Every other long-press branch in the tap-hold engine (capslock 2.3, enter 9.1,
  lalt 4.6/4.7, rctrl 7.4, the `_SpaceHold*` fns) was hardened to
  `try { KeyWait(.., "U T" . STUCK_MODIFIER_RELEASE_TIMEOUT_SEC) } finally { release }`. The two
  `alt_tab_monitor` blocks were skipped by that hardening, and
  `tests/meta/test_hold_modifier_release_bounded.ahk` anchors only the generic blocks, never the
  `alt_tab_monitor` block — so the regression is invisible to CI. `lalt.ahk` has **zero** `Up::`
  hotkeys, so `:170/:171` is the *sole* path that clears the latched Down (unlike `tab.ahk`,
  which has a `SC00F Up::` safety net).
- **Why silent:** The thread is *blocked inside `KeyWait`*, not throwing — no dialog, nothing
  reaches the file logger. The user sees `LAlt` stuck Down system-wide (every keystroke becomes
  `Alt+key`) until a reload, with no log line pointing at the cause.
- **Fix:** Mirror the hardened pattern in `lalt.ahk` block 4.3:
  ```ahk
  else {
      ; Bound the wait and release LAlt in a finally so a lost key-up (Alt+Tab focus
      ; steal, UAC prompt, Suspend toggled mid-press) can never latch Alt Down
      try {
          KeyWait("SC038", "U T" . STUCK_MODIFIER_RELEASE_TIMEOUT_SEC)
      } finally {
          TextPressKey("LAlt", "Up")
      }
  }
  ```
  Reuse the existing `STUCK_MODIFIER_RELEASE_TIMEOUT_SEC` (constants.ahk:57). **Verifier
  correction:** `tab.ahk` 8.1 is a *weaker, structurally different* case — its hold branch has
  **no** unbounded `KeyWait` at all; it falls through leaving Alt Down and relies on the
  `SC00F Up::` hotkey (which `Suspend` disarms). Treat `tab.ahk` 8.1 as a separate **medium**
  defensive-hardening item, not the same High latch; its fix needs an explicit hold-path `else`,
  not the verbatim diff above.
- **Regression test:** `tests/meta/test_hold_modifier_release_bounded.ahk` — add
  `_HMRB_LAltAltTabGuarded()` that scans the `alt_tab_monitor` block (`#HotIf` keyed on
  `TapHoldTapAction(TapHold, "left_alt") == "alt_tab_monitor"`) and asserts it contains
  `STUCK_MODIFIER_RELEASE_TIMEOUT_SEC` + `finally` and **no** bare `KeyWait("SC038","U")`. The
  bare form exists today → fails before, passes after.

### F-H02 — UIA selection-wrap latches the suppress counter forever if a Send throws → HSE + preview go permanently dead
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G1, G2
- **Files:** `lib/hotstrings/hotstring_prefix_watcher.ahk:863`, `:871`, `:874`, `:288`
- **Repro:** State = normal, Hotstrings gate ON, `shortcuts.wrap_text_if_selected = true`
  (default). Select text in any app, type a wrap symbol in `_WS_ACTIVE_PAIRS` (`(`, `"`, `*`,
  `_`). `_OnPrefixChar` enters the UIA-wrap branch: `PrefixWatcherSuppress(true)` (`:871`), then
  `SendEvent("{BackSpace}")` (`:872`) + `SendInstant(Left.Sel.Right)` (`:873`). If either Send
  throws (the block is already wrapped in `catch as _UIAErr`, so the author anticipates it), the
  paired `PrefixWatcherSuppress(false)` at `:874` is **skipped**.
- **Root cause:** The suppress-release sits *inside* the protected `try` with the throwing Send
  calls, with no `finally`. `PrefixWatcherSuppress` is a depth counter that mirrors into HSE; an
  unmatched `true` leaves `_PrefixWatcherSuppressed`/`HSE_Suppressed ≥ 1`. After that, every
  `_OnPrefixChar` (guard at `:831`) and `_OnPrefixKeyDown` (`:1038`) early-returns — **no
  hotstring ever fires and no preview ever renders again** until reload.
- **Why silent:** the throw is caught and only `LoggerError`'d (`:879`) — no crash, no
  `OnError`; the script keeps running with its entire hotstring/preview subsystem silently dead.
  The normal fire path uses a deferred `SetTimer` release and is unaffected; this is the lone
  synchronous suppress pair whose release is on the wrong side of the `catch`.
- **Fix (verifier-corrected):** the finding's premise "AHK v2 has no `finally`" is **wrong** —
  v2 has `finally` and this codebase uses it in 32 places. Wrap only the two Sends and release
  in a `finally`:
  ```ahk
  PrefixWatcherSuppress(true)
  try {
      SendEvent("{BackSpace}")
      SendInstant(Left . UIASel . Right)
  } catch as _UIAErr {
      LoggerError("PrefixWatcher", "UIA wrap send failed for char '{1}': {2}.", Char, _UIAErr.Message)
  } finally {
      PrefixWatcherSuppress(false)
      _ResetPrefixBuffer()
  }
  ```
  Keep `GetUIASelection()` *outside* the protected region (it is a pure cache reader, cannot
  throw).
- **Regression test:** new `tests/unit/test_uia_wrap_suppress_latch.ahk` — stub `SendEvent`/
  `SendInstant` to throw, stub `GetUIASelection` to return a non-empty selection, set
  `wrap_text_if_selected=true` and a `(` pair, call `_OnPrefixChar(IH, '(')`, assert
  `_PrefixWatcherSuppressed == 0` **and** `HSE_Suppressed == 0` after the call. Fails before
  (stuck at 1), passes after.

### F-H03 — Remote-LLM generation blocks the typing thread on a synchronous WinHTTP TCP connect
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G4, G3
- **Files:** `modules/llm/api_remote.ahk:137`, `:141`; dispatch from `modules/llm/prediction_engine.ahk:639`
- **Repro:** LLM ON, backend = `api` (any remote provider), valid token+model. Network changes
  or the host is slow to answer the SYN / needs fresh DNS (WiFi handoff, VPN, captive portal,
  cold DNS). Keep typing. After the debounce, `LLM_Engine` → `LLM_RemoteGenerate_Async` →
  `http.Open("POST",Url,true); http.Send(Payload)`. `WinHttpRequest.5.1`'s "async" mode makes
  only the *response* async — the **connect (DNS + TCP SYN) runs synchronously on the
  message-loop thread**, which is the same thread that pumps the PrefixWatcher InputHook. The
  pump freezes for the connect duration (seconds on a stalled WAN host); `OnChar` is starved and
  the OS drops keystrokes via `LowLevelHooksTimeout`.
- **Root cause:** This exact fact is documented in the sibling Ollama module
  (`api_ollama.ahk:262-269`, `:368-372`) — which is precisely why the Ollama
  generation/health/tags paths were all migrated **off** WinHTTP onto `curl` child processes,
  and why the remote *readiness* probe `LLM_RemoteIsReady_Async` was added. The remote
  *generation* hot path was never migrated. Remote WAN/CDN hosts have far higher, more variable
  connect latency than the localhost Ollama daemon, so the stall is worse here than the
  already-fixed cases.
- **Why silent:** the `Send()` is inside a `try`; a connect *failure* is swallowed into
  `on_fail()` with no stall log, and a slow-but-successful connect throws nothing — it just
  blocks, then returns a valid prediction, so logs look healthy. The dropped keystrokes are
  produced by `LowLevelHooksTimeout` in the OS, which the driver never sees. The 500 ms api
  rate-limit floor masks frequency but not the per-fire stall. (The `Critical()` around the
  dispatch at `prediction_engine.ahk:721` makes the freeze *worse*, not better.)
- **Fix:** mirror `_LLM_Ollama_DispatchAsync` — dispatch the POST through a `curl` child
  (`curl -s -S -X POST --data-binary @payloadfile -o stdoutfile`, per-provider `-H` auth) and
  poll `ProcessExist` on a `SetTimer` tick. The connect then happens in `curl`'s process; the
  message loop only polls `ProcessExist` (instant). Write the JSON body (user-typed PII) through
  `_LLM_Ollama_TempDir()` (per-instance `ergopti_llm_<pid>`), not bare `A_Temp`, to satisfy the
  existing `ollama-curl-temp-pii-plaintext` invariant. Keep the deadline-cap + `on_success`/
  `on_fail` contract.
- **Regression test:** `tests/meta/test_remote_generate_async_nonblocking.ahk` — using
  `_DriverFuncBody("LLM_RemoteGenerate_Async")`, assert the body launches a `curl` child
  (`Run(` + `curl`) and contains **no** `http.Send(`/`WinHttpRequest` on the dispatch path,
  mirroring `test_ollama_reachability_async_nonblocking.ahk`. Fails today, passes after migration.

### F-H04 — `disabled_apps` and `disable_url_bars` are configurable + persisted but NEVER enforced (privacy breach)
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G2
- **Files:** `modules/llm/prediction_engine.ahk:409` (`LLM_Engine_FirePrediction`), `:177`, `:116`;
  `ui/menu/menu_llm/persist.ahk:124`, `:146`; `ui/menu/menu_llm/menu_settings.ahk:106`, `:117`
- **Repro:** LLM bridge enabled, Ollama ready. Toggle `disable_url_bars` ON and add an app (e.g.
  `keepass`) to `disabled_apps` via the menu picker — both persist to TOML and reload into
  `_LLM_Engine`. Focus that app (or a Chrome/Edge address bar), type 8-10 chars, pause. **Result:**
  the violet "Génération en cours…" tooltip appears and a real prediction is generated and shown —
  the typed text is sent to Ollama/the remote API exactly as in any other field. **Expected (and
  what macOS does):** no prediction; context never leaves the excluded app/URL bar.
- **Root cause:** `LLM_Engine_FirePrediction` gates only on `A_IsSuspended`, enabled/empty
  buffer, and `disable_password_fields` (`:427`). It never consults
  `_LLM_Engine["disabled_apps"]` or `["disable_url_bars"]`. The values load into engine state and
  round-trip through menu+TOML, but there is no AHK equivalent of macOS `app_filter.is_blocked`
  (`macos/.../prediction_engine.lua:534` enforces all three filters; Windows enforces only the
  password one). The classic `project-ahk-invariant-incomplete-application`: the
  `disable_password_fields` sibling is present, its two siblings are not.
- **Why silent:** no error — the unenforced flags are dead config. The menu renders the toggle as
  ON and the app list as populated, so the UI *affirms* the feature is active. No log line says
  "prediction allowed in disabled app." No Windows test covers enforcement (only
  `metrics_disabled_apps` is tested).
- **Fix:** add an app-block gate in `LLM_Engine_FirePrediction` immediately after the
  password-field guard, mirroring `app_filter.is_blocked`: resolve the focused process via
  `WIGetFocused()["appId"]` (already used at `:1153`; the adapter returns an empty Map rather
  than throwing, so the `app==""` check handles no-focus), strip `.exe`, and skip with a
  `Logger.info` when in `disabled_apps`. Keep behind the flag so the OS read only runs when the
  user opted in (read at *fire* time, not per keystroke — see Performance). **Verifier split:**
  land `disabled_apps` enforcement + test **now** (clean macOS-parity privacy fix); track
  `disable_url_bars` separately — Windows has **no** URL-bar/browser detector today, so that half
  is net-new infrastructure.
- **Regression test:** `tests/meta/test_llm_app_filter_enforced.ahk` — source guard asserting the
  `LLM_Engine_FirePrediction` body references `disabled_apps` (and, when built, `disable_url_bars`)
  the way it already references `disable_password_fields`; plus a behavioural test that a focused
  app in `disabled_apps` short-circuits before dispatch. Fails today (neither key appears),
  passes after.

### F-H05 — Cross-process cold-replay of `today.log` is a permanent no-op on 64-bit → keystrokes lost after a crash, offset advanced past them
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G2
- **Files:** `modules/keylogger/keylogger.ahk:842`, `:907`, `:1120`, `:23` (header guarantee);
  `modules/keylogger/keylogger_json.ahk:80`, `:86-89`; `modules/keylogger/keylogger.ahk:369` (`KL_LoadState`)
- **Repro (verifier-corrected):** Shipped 64-bit `AutoHotkey64.exe`, keylogger ON. (a) Hard-kill
  the process during/just after an ingest tick that has already `Write()`+`Flush()`'d pending
  lines to `today.log` (`keylogger.ahk:895-900`) but before the offset persist at `:983` — those
  lines are on disk past the persisted offset and never reached `data.sql`; **or** (b) simply
  any 64-bit restart: `KL_LoadState` (`:369`) parses `state.json` through the same no-op
  `KL_JsonDecode`, so `today_log_offset` is never restored (stays 0). On relaunch the
  `KL_IngestOnce(-250)` pass reads the un-ingested lines, `KL_JsonDecode` returns an **empty
  `Map()`** on 64-bit (`keylogger_json.ahk:86-89`), every line is skipped (no `type` key),
  `entries` stays empty, and the `entries.Length=0` branch (`:907`) **still advances**
  `today_log_offset`. Those events are unreachable forever.
- **Root cause:** the crash-recovery design (header `:23-25`: "Crash-safe: `today_log_offset`
  persisted on every successful ingest; replay is idempotent") depends on
  `KL_ReadNewTodayLog → KL_JsonDecode` to re-read lines written by a *previous* instance. But
  `KL_JsonDecode` is a hard no-op on 64-bit (`ComObject('ScriptControl')` is x86-only). The
  same-process loss was hardened via the in-RAM `_pending_entries` queue; the cross-process path
  has no RAM fallback, and the offset advances past the undecodable lines so even a future decode
  fix can't recover them. (Verifier: the bug is *worse* than stated — `KL_LoadState` is also a
  no-op, so the resume point itself is lost on every 64-bit boot.)
- **Why silent:** `KL_JsonDecode` swallows failure (returns `Map()`), the line is skipped in a
  `try`/`catch`, and the offset still advances — logs show a normal zero-entry ingest tick, no
  WARNING, no START-without-SUCCESS. The documented guarantee *reads* as satisfied.
- **Fix:** (1) replace `KL_JsonDecode` with a real hand-rolled JSONL decoder (the *encoder* is
  already hand-rolled in `keylogger_json.ahk:18-78`) so cross-process replay and `state.json`
  restore both work on 64-bit; (2) until/unless decode works, do **not** advance
  `today_log_offset` in the `entries.Length=0` branch when raw lines were read but none decoded
  on a 64-bit host; (3) `Logger.warn` when raw lines decode to zero entries so the path becomes
  observable.
- **Regression test:** functional round-trip `KL_JsonEncode → KL_JsonDecode` on a representative
  `typing`/`app_switch` entry, asserting the decoded `Map.Has("type")` and key values survive
  (fails-before: empty Map on 64-bit; passes-after). Plus a test driving `KL_LoadState` against a
  written `state.json` and asserting `today_log_offset` restores non-zero. File:
  `tests/meta/test_keylogger_json_roundtrip_64bit.ahk`.

### F-H06 — Crash-report build runs blocking WMI + RegRead + git-subprocess `Sleep` loop on the keyboard/dispatch thread
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G4, G1
- **Files:** `lib/crash_reporter.ahk:324`, `:358-372`, `:104`; `lib/error_net.ahk:50`; `lib/hook_dispatcher.ahk:224`
- **Repro:** Driver running normally, `HookDispatcher` started, a keyboard subscriber registered
  (keylogger or LLM-bridge char handler). Make that subscriber throw once on a keystroke (e.g. a
  transient `Map[absent-key]`). `HookDispatcher.Dispatch`'s per-subscriber `catch`
  (`hook_dispatcher.ahk:224`) calls `ErgoptiGlobalErrorHandler(e,"Continue")` **synchronously on
  the InputHook (keyboard) thread**, which calls `CrashReport_Build` →
  `_CrashReport_SysInfo` + `HealthCheck_Run`: a `WbemScripting` WMI query (`:324`), 3× `RegRead`,
  and a git `rev-parse` via `Run` + `while (!FileExist) Sleep(50)` up to a 500 ms deadline — all
  before the keystroke dispatch returns. The keyboard freezes ~100-500 ms (a cold WMI
  `ConnectServer` alone can exceed 500 ms).
- **Root cause:** the team already hardened the crash path against blocking the input thread by
  replacing the modal `MsgBox` (HIGH-02, `test_crash_prompt_blocking_msgbox.ahk`), but only the
  `MsgBox` site was audited — the equally-blocking sysinfo collection inside `CrashReport_Build`
  was not. The code's own comment (`crash_reporter.ahk:100-102`) acknowledges the handler "fires
  at an arbitrary point (potentially mid-keystroke)." Exactly the
  `project-ahk-invariant-incomplete-application` foot-gun.
- **Why silent:** only manifests when an error fires (already a degraded state), WMI/git latency
  is variable and machine-dependent, and the dispatch escalation is throttled to once per 60 s
  per signature — casual testing rarely hits the full cost. The START/SUCCESS pair around
  `CrashReport_Save` still completes, so logs look healthy.
- **Fix:** keep the cheap, must-be-synchronous work inline (modifier release at
  `error_net.ahk:37-41` — must stay synchronous or stuck keys persist; the `LoggerError`) and
  defer only `CrashReport_Build` + `CrashReport_PromptUser` via
  `SetTimer(() => _BuildAndPromptCrash(Exc), -1)` so the keystroke dispatch returns immediately.
  Prefer this over gating WMI/git behind an input-thread check — skipping them would degrade the
  diagnostics for the most common (dispatch-thread) crash, the very crashes you most want full
  data for.
- **Regression test:** `tests/meta/test_crash_build_offthread.ahk` — source guard (via
  `_DriverFuncBody`) asserting `ErgoptiGlobalErrorHandler` schedules `CrashReport_Build` via
  `SetTimer` and contains **no** inline `CrashReport_Build(`/`CrashReport_PromptUser(`. Fails
  today (inline at `error_net.ahk:50`), passes after deferral.

### F-H07 — Gesture screenshot capture blocks the keyboard hook thread with synchronous `RunWait('powershell.exe')`
- **Severity:** High · **Confidence:** confirmed · **Guarantee:** G4
- **Files:** `modules/gestures/screenshots.ahk:72` (`GestureCaptureRegion`), `:165`
  (`GestureScreenshotRegion`); dispatch `modules/gestures/init.ahk:1185`, catalog `:382`
- **Repro:** Normal/typing state, gestures enabled, a touchpad gesture assigned to
  `screenshot_window_*` / `screenshot_fullscreen_*` / `screenshot_region_save`. Perform the
  gesture. The gesture hotkey (`^#+F1..F10`, on the **main pseudo-thread that remaps every
  keystroke**) → `GestureDispatch` → action `Fn()` → `GestureCaptureRegion(...)` →
  `RunWait('powershell.exe …')` at `screenshots.ahk:72`. The thread blocks for the whole
  PowerShell spawn + `.NET Add-Type` JIT + `CopyFromScreen` + `Clipboard.SetImage` (300-1500 ms
  cold). Every keystroke during that window is **not** remapped and queues; typing visibly
  freezes. The region-save variant blocks again at `:165` after the `ClipWait`.
- **Root cause:** `GestureDispatch` (`init.ahk:1185`) invokes the action synchronously on the
  keystroke-remapping thread; `RunWait` (blocking) is used instead of async `Run`. For clipboard
  mode the `RunWait` return value is **discarded** (the function always returns `True`), so
  blocking buys nothing. The sibling `GestureScreenshotInstant` (`init.ahk:590`) and the SC029
  `win.ahk` hotkey were already migrated to async `Run()` for this exact reason
  (`win.ahk:536`: "Run async — hook thread returns immediately"). These two were the missed
  siblings.
- **Why silent:** `RunWait` blocks, it does not throw, so the surrounding `try`/`catch` provides
  zero protection and emits no warning. The only symptom is a transient typing freeze users
  attribute to the OS screenshot tooling. `test_screenshot_async_run.ahk` guards only SC029;
  `test_gesture_screenshot_no_tempfile.ahk` guards only `GestureScreenshotInstant`.
- **Fix:** in both functions replace `RunWait` with async `Run` (fire-and-forget + `TrayTip`,
  matching the migrated siblings — they both chose fire-and-forget over a `FileExist` poll). The
  interactive `ClipWait` in `GestureScreenshotRegion` stays (a deliberate user-wait); only the
  post-`ClipWait` PNG-save `RunWait` at `:165` becomes async.
- **Regression test:** `tests/meta/test_gesture_capture_async_run.ahk` — assert the bodies of
  **both** `GestureCaptureRegion` and `GestureScreenshotRegion` contain no `RunWait` and do
  contain `Run(`. Fails today, passes after.

### F-M01 — `DeadKey()` InputHook completing *after* a mid-sequence pause emits output while suspended

  `KL_SchedulePasswordDetect` sees `pending_hwnd==hwnd` and returns without re-arming; the
  conservative `last_val=true` is never relaxed; `MF_ShouldFilter` returns true → the keylogger
  **drops all content for that field** until focus moves to a different HWND.
- **Root cause:** the suspend-guard hardening introduced an abort path that bails before the
  shared dedupe-guard cleanup. `pending_hwnd` is reset in exactly one place (`:134-135`), and
  resume never touches `KLPasswordCache`.
- **Why silent:** clean `return`, no log, no throw; the verdict stays at its privacy-safe default,
  so no password leaks — the failure is the opposite of loud: legitimate non-password typing is
  silently excluded from metrics. The existing test only asserts the guard exists, never exercises
  the latch.
- **Fix:** in the `A_IsSuspended` branch, clear the guard before returning:
  ```ahk
  if A_IsSuspended {
      ; Pause aborts off-thread detection, but the scheduler guard MUST be released
      ; or every future re-schedule for this hwnd dedupes forever (async-password-detect-suspend-latch)
      if (KLPasswordCache.pending_hwnd = hwnd)
          KLPasswordCache.pending_hwnd := 0
      return
  }
  ```
- **Regression test:** `tests/meta/test_async_password_detect_suspend_guard.ahk` (extend) — seed
  `pending_hwnd:=H`, force `A_IsSuspended`, call `KL_AsyncPasswordDetect(H)`, assert
  `pending_hwnd == 0`. The current structural test passes with the latch present, so it must be
  extended to fail-before/pass-after.

## 7. Performance (G4)

**No live profiler logs were available** (driver not run in this environment), so this is
code-derived. Recommend re-running `boot_profiler`/`hotpath_profiler` live to attach measured
"Slow …" numbers.

**Real blocking calls / O(n) work reachable on the typing or menu thread — these are the
findings above, restated as perf:**

| Cost | Path | Finding |
|------|------|---------|
| Synchronous WinHTTP TCP connect (DNS+SYN), up to seconds | typing thread, per remote-LLM fire | **F-H03** |
| Blocking WMI + RegRead + git `Sleep`-poll, ~100-500 ms | keyboard/dispatch thread, on first error per signature | **F-H06** |
| `RunWait('powershell.exe')`, 300-1500 ms | keyboard hook thread, per screenshot gesture | **F-H07** |
| O(n) ~3180-entry linear `_CheckNearMiss` scan **under `Critical`** | InputHook OnChar, per word-boundary keystroke | **F-M04** |
| 30 s of 50 ms timer wakeups after a dead remote connection | message loop | **F-M06** |

**Hot path verified clean (the everyday typing path is genuinely fast):**
- Base remaps are pre-bound **O(1)** Hotkey callbacks; AltGr/Shift/Caps dispatch is a single
  `Map.Has` + index; the AltGr layer is an O(1) Map probe (`_BuildAltGrTables` builds once); last-
  sent history is a fixed ring with no per-key allocation; tap-hold durations/actions are bounded
  Map probes.
- The star-trigger lookup is bounded to `Min(BufLen, HSE_MaxStarTriggerLen)` Map probes per
  magic-key press (replacing the old ~2100-entry linear bucket scan, ~21 ms).
- `LLM_Bridge_OnChar → OnKeystroke` is buffer-append + cancel + re-arm `SetTimer` under `Critical`,
  no blocking OS call; `WIGetFocused()` is called only at fire time (debounced), not per keystroke.
- `nav_layer` payloads were de-`Format()`'d to plain concatenation (no per-keystroke template
  parsing); the dense 7-chained-Map-read `#HotIf` on SC03A is all O(1) probes.

**Boot:** aggressively trimmed — i18n active-locale preload only (fallbacks warmed post-ready),
the ~157 ms tray-menu build fully deferred under `Critical` after "ready," emoji/symbol hotstrings
(~3000 regs / ~410 ms) deferred to a 1500 ms post-ready timer, WebView2 widget cold-start armed
last. The heavy file-I/O prescans are warmed off-`Critical` before `BuildTrayMenuDeferred` takes
`Critical`, so the `Critical` span covers only the pure Win32 `Menu.Add` pass. The only always-on
boot timers are the 500 ms suspend watchdog and the 1000 ms layout poll (both cheap).

**Off-hot-path costs worth watching (not bugs today):**
- Tooltip destroy+recreate of two top-level windows per render is intentional (AHK v2 can't remove
  Gui controls); bounded by the border alpha zone-scan + cached HFONT. `_TooltipMeasureText` is
  O(rows × chunks) GDI round-trips per rich LLM render (DC re-acquired each call) — the dominant
  render cost; watch if slot counts grow.
- `KLR_BuildDatabase` re-runs all aggregate `GROUP BY` queries every ~5 s while a dashboard is open
  (idle-deferred, off the keystroke thread).
- `GestureGetCyclableWindows` does a `WMGetList()` + **O(n²) bubble sort** per `win_next`/`win_prev`
  (n = top-level window count, tens; only on explicit cycle) — swap for insertion/merge sort if
  high-window-count sessions feel it.
- The synchronous `HTTPPost` adapter (30 s WinHttp, blocks the caller) is **dead in production** but
  still exported — document as off-hot-path-only or remove, lest a future caller wires it onto the
  typing/menu thread.
- Per-event `KL_Hook_RefreshContext.Bind()` closure allocation on every mouse-up/scroll-flush —
  reuse a cached bound ref (minor).

## 10. Recommended remediation order

1. **F-H04** (privacy — typed context leaves user-excluded apps) and **F-H03** (typing freeze /
   dropped keystrokes on remote LLM) — user-facing correctness/privacy on the core path.
2. **F-H01, F-M03, F-M01** (modifier/keystroke latch + suspend leaks) — keyboard-state integrity.
3. **F-H06, F-H07** (blocking work on the keyboard thread) — convert the two remaining
   `project-ahk-invariant-incomplete-application` blocking siblings.
4. **F-H05** (keylogger crash-replay) + **F-M05, F-M08, F-M11** (silent wrong-state).
5. **F-M02, F-M04, F-M06, F-M09, F-M12, F-M10, F-M07** (races, perf, privacy-count, dead config).
6. **F-L01..F-L09** + **S-01** (after a live download test).

**Strategic test upgrade (highest leverage):** several regressions slipped past CI because the
meta-tests anchor only the *documented* site. Convert these to **whole-class** assertions:
- every long-press block bounds its `KeyWait` (F-H01);
- every InputHook re-checks `A_IsSuspended` **after** `Wait()` (F-M01, F-M03);
- every privacy-relevant counter is bumped **after** `MF_ShouldFilter` (F-M09);
- `test_logger_pairing.ahk` scans `ui/` and **fails** (not warns) on START-immediately-before-Reload (F-L08, F-L09);
- every `chunk.type` / personal-node `["enabled"]` dereference is shape-guarded (F-L03, F-L06).

Per project rule 5.9, **each fix ships with the regression test specified in its finding** (each
encodes the root cause, fails before, passes after). Do not weaken any existing test to land a change.
