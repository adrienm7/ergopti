## Confirmed findings

### MRT-001 — Approval timeout counts poll intervals instead of elapsed time

**Medium; high confidence. G3; additional property: bounded approval lifetime.**

The automatic observer reaches `runtime_approval_watch.start()` when admission reports `virtual_hid_not_active` (`adapters/runtime_owner_ports.lua`, `automatic_observer`). `runtime_approval_watch.lua:55–68` carries an `elapsed` counter, increments it only by the three-second polling interval, and excludes the duration of every asynchronous listing and delayed timer. Its listing port is a real five-second-bounded `systemextensionsctl` task. It also assesses success before testing the deadline.

Reproduction: start the watch with the pinned driver still waiting; have each listing complete normally in four seconds and each scheduled poll fire after three seconds. The actual module remains active beyond its declared 900-second lifetime and stops after **2,104 simulated seconds**, not 900. Give it an approved listing at simulated 1,005 seconds and it still initiates reload. Control: instantaneous listings stop at exactly 900 seconds.

`probes/approval-wall-clock.lua` also runs the actual module against genuine Linux libuv timers, scaling the exported budget to one second and both listing/poll delays to 250 ms. The retained initial run measured **2.25222051 seconds** to stop and `active=true` at 1.098374784 seconds. This is actual private-probe elapsed time, not a macOS latency measurement. The normal-constant 2,104/1,005-second results are virtual scheduling observations, not elapsed wall-clock measurements.

Visibility: the final warning says “within 900 s” although that counter excludes task latency. The registered watch test uses immediate listings and manually invokes pending callbacks, so it cannot expose the mismatch. Regression direction: capture an absolute monotonic deadline at start; check it before admitting a result/reload and before scheduling the next observation; cover slow listings, late timers, suspended execution and exact deadline boundaries. Preserve the distinction between observing approval and approving it.

### MRT-002 — Refused timeout timer leaves a started install permanently unsettled

**Medium; high confidence. Named property: bounded command settlement (`P_BOUNDED_COMMAND_SETTLEMENT`).**

`adapters/field_check_ports.lua:47–67` starts the command, then assigns only the first return from `Timer.after`. The real scheduler returns **handle, false** when native construction/start fails (`adapters/timer_scheduler.lua:180–250`). A truthy handle is not an armed deadline. The runner neither terminates the command nor reports a terminal refusal in that branch.

Reproduction: accept launcher start; make native `hs.timer.new` throw while constructing the command's timeout; leave the launcher/admin operation pending. `probes/runtime-probes.lua` loads the actual TimerScheduler, actual bounded runner and actual runtime installer, replacing only the native timer/task boundaries. Observed: command started, zero completion callbacks, zero termination attempts. A second `installer.install` joins the retained waiter list and receives no answer either. An administrator prompt or native operation with no natural completion therefore has no remaining budget. Control: a committed timeout produces one terminal callback.

The scheduler emits an error; this is **not** claimed to be an entirely silent G2 failure. The installer itself never receives that error and continues to retain a running transaction. Existing tests model committed timers and do not exercise this join. Regression direction: make native timer admission part of command ownership; on refusal, retain/retire the exact child and produce a truthful bounded failure according to the command's cancellation contract. Exercise construction/start false/nil/throw and pending/refused cleanup without losing exact task debt. Do not assume a signal is physical completion (see MRT-005).

### MRT-003 — Lua cache and Swift helper disagree on the valid receipt bytes

**Low; high confidence. Named property: verified artifact admission consistency (`P_ARTIFACT_ADMISSION_CONSISTENCY`).**

With every required payload product present, set the local receipt to the pinned lowercase digest followed by `\nextra`, `\n\n`, or ` extra\n`. `runtime_artifact_fetch.lua`, local `kept`, accepts any receipt whose **initial hex run** equals the pin, then `ensure` reports success and skips every command. `OwnedRuntimeDownloadedHelper.swift:85` requires the **exact bytes** `digest + "\n"` and refuses those same receipts as `artifact_receipt_mismatch`.

Reproduction: start/reload with that malformed cached receipt, confirm the automatic or menu install, then retry. Admission's fetch keeps saying already verified and never repairs/refetches it; the launcher's exact-byte guard keeps refusing before the administrator prompt. The pure Lua probe establishes cache success plus zero commands for each malformed suffix and the exact receipt control. `logs/source-joins.json` establishes the live Swift guard and its source hash; Swift was not executed here. The real file-system adapter returns the complete bytes without trimming (`file_system.lua:757–831`).

Visibility: the final install refusal is loud; the defect is the persistent disagreement between “artifact ready” and the actual install admission, not a cryptographic bypass. A malformed receipt must already exist; no ordinary successful writer path is claimed to produce it. Regression direction: one exact receipt predicate shared semantically by Lua cache/admission diagnostics and Swift; malformed/trailing-byte receipts must fail cache reuse and enter the existing safe refetch/refusal flow. Keep Swift's no-follow regular-file and exact-byte checks.

### MRT-004 — The advertised retry route cannot repair an already published runtime

**Medium; high confidence. Named property: recoverable provisioning (`P_RECOVERABLE_PROVISIONING`).**

A normal first-install failure can happen **after** publication: `OwnedRuntimeIdleServiceEntry.swift:28–39` publishes Runtime, then acquires/provisions Core and VirtualHID. If a service step refuses, it returns `files-published-service-cleanup-pending`; the files remain by design. Separately, a previously installed runtime may have an unloaded owned job. `runtime_owner.lua`, `check_jobs`, returns `runtime_job_not_loaded` and explicitly says to reinstall. The Tap-Holds menu maps that reason to the not-installed block and publishes the retry command (`menu_tap_holds.lua:1138,1198–1210`). The facade admits it (`platform/remap/init.lua:5224–5246`).

Both routes invoke only `--request-owned-runtime-install` → `--owned-install-first`. `OwnedRuntimeFirstInstallOwner.swift:63` requires `Runtime` to be **absent** before any publication or service repair; it throws `destination` whenever the directory already exists. The sole user install role cannot reach `CoreProvisionOwner` repair independently of first publication. Retrying the exposed action therefore cannot resolve this state, even when the original service failure was transient and has cleared.

The retained probe runs real owner admission with all installed files present, the pinned active extension and an unloaded job: it obtains `runtime_job_not_loaded`. It then evaluates an exact source projection of the facade's declaration/function to prove that public request is still admitted. The projection's final refusal is a recording boundary, **not native helper execution**. Native inevitability comes from the unconditional original `fstatat(...,"Runtime",...) == -1 && ENOENT` guard, the fixed role dispatch, and publish-before-provision sequencing in `logs/source-joins.json`.

Visibility: cleanup-pending and later refusal are loud. This is a recovery/action-affordance defect, not a G2 silent-no-op or a proposal to overwrite unknown files. Existing tests exercise first-install results and fresh publication separately, not failed-service → same public retry → eventual admission. Regression direction: add an authenticated recovery/service continuation under the original namespace/journal policy, or expose a truthful distinct recovery action/reason. Keep the existing first-install refusal for unknown/live Runtime trees. Test failure after publication, transient Core/VirtualHID bootstrap failure, an unloaded job, restart and repeat requests.

### MRT-006 — A false native Settings-open result is treated as success

**Low; high confidence. G2.**

`runtime_owner_ports.lua`, `approval`, supplies `open_settings = function(url) return hs.urlevent.openURL(url) end`; that native operation returns a boolean. `runtime_approval_watch.lua:78–79` captures only `pcall`'s status and checks whether it threw. `false` from the native opener is accepted and never logged as an opening failure.

Reproduction: the owner reaches not-active; the real watch calls an opener returning literal false. The retained probe observes `start=true`, `active=true` and **zero error diagnostics**. The pane did not open, yet the only watch message says it is opening it. The background listing can continue legitimately; that does not deliver the promised pane or report its refusal. Control: the successful opener path in the registered test opens the exact declared URL; thrown errors are explicitly caught and logged by the live code.

The registered watch fake's opener returns no value, and the shared `hs.urlevent.openURL` stub records a call without returning the native boolean, so those tests do not establish success acknowledgement. Regression direction: retain both protected-call status and native result; report false/nil refusal while keeping any intentional independent watch behavior. Include true, false, nil and throw controls; do not fabricate a successful native result merely because a call was recorded.

## Rejected hypotheses, memory and honest gaps

- **MRT-005 (not confirmed): timeout necessarily violates install cancellation or proves root overlap corruption.** The pending-native-task probe proves the Lua waiter slot can clear while an exact child is pending. It does not prove forbidden continued work: original install consent can remain valid, `install_unanswered` is a loud unknown answer, and the helper's EX lifecycle lock fences publication. No physical-done success receipt is emitted. A separate native continuation/retirement contract and an actual bad observer/effect are needed before promoting it. The private probe is retained transparently, not included in findings.json or confirmed counts.
- **The install still stages the application bundle's helper. Refuted.** Current() resolves LuaSourceSelection and the kept download. Root trust then rechecks identity/tree/code; a receipt alone does not grant privilege. The old memory paragraph under `project-hs-owned-remap-runtime` still says “the privileged installer still reads only the payload sealed in its own signed bundle”: that wording is now stale for the outer helper source. Its inner runtime products remain sealed inside the downloaded signed helper. `_shared/data/owned_runtimes.json` also retains “dormant” wording despite the current default. Recorded as memory follow-up, not production findings.
- **The helper result certifies approved keyboard readiness. Refuted.** Result vocabulary explicitly certifies files/services/stage only. Lua manager activation is followed by reload and admission. Wrong team/version/inactive drivers and missing jobs block before capture READY.
- **Ordinary duplicate install immediately launches a second role. Refuted.** The actual installer queues callbacks behind its waiter list; the registered duplicate test passes. MRT-005's distinct timeout case is not this ordinary duplicate case.
- **Callbacks vanish merely because source contains pcall. Refuted.** Runtime installer/updater waiter errors are logged; actual ShellRunner callback boundaries report throws. No blanket silent-callback claim is made.
- **Root partial publication should be blindly deleted/replaced. Rejected fix direction.** Native destination, journal, signature and lifecycle guards deliberately preserve unknown/live state. MRT-004 concerns selection/exposure of recovery, not weakening those guards.
- **G4**: no production driver logs were accessed. The live Mac paths.toml/LogsDirPath and native runtime were unavailable, so there is no production latency measurement, no “no lag” assertion, and no file-name-derived dating. The libuv elapsed measurement qualifies only the private scaled approval-loop experiment. Test timing is not typing-path latency.
- **Not qualified here**: signed installed-app source/current-account resolution in a real user session; macOS 15/26 on Intel/ARM; actual AppleScript administrator cancellation; SecCode/ACL behavior; downloaded archive content beyond existing checks/tests; native package/signature acceptance; launchd queued registration/start vs process observation; actual DriverKit replacement, user approval/reboot; permission-denied native Settings opening; physical keys; root helper continuation after launcher timeout/reload/quit; live same-OS installed-runtime conflicts. Prior hosted acceptance recorded in TODO is provenance, not re-run or newly certified evidence.

AGENTS, adversarial-audit/report contract/Hammerspoon reference, hammerspoon-driver and false-green-tests were read; routed README, relevant macOS/workflow/shared-architecture and maintainer-decision topics were consulted. The prior parity audit reports and TODO were searched: their recent delivery delta explicitly left this watch's wall-clock bound unqualified. Existing old migration/updater findings are not reissued here.
