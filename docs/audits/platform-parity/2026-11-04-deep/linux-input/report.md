## Confirmed new availability correction

### LI-001 — physical shortcut editor and active physical-action delivery are unavailable on production Linux

Severity: medium (missing advertised/declarative capability). Confidence: high. Guarantees: G2, G5. **Intentional fail-closed qualification boundary; do not bypass it. The feature is guarded and unimplemented/unqualified; this is not a settled product decision to omit it.** This is an actionable availability/documentation/inventory correction, not evidence that the refusal itself is a bug.

The prior input report (`docs/audits/platform-parity/2026-11-04/input.md`) called Linux/macOS physical editors real native capabilities, conditionally available with runtime/session support. Production code at the audited SHA proves a stricter condition: they are unavailable regardless of desktop readiness because physical action delivery is deliberately unqualified.

Exact Linux path:

- `static/ergopti_plus/linux/modules/shortcuts/keyboard_shortcuts.lua:728–734`: explicit comment “The current Linux Hook has no qualified physical delivery capability”; `physical_delivery_available()` returns **false unconditionally**. Existing logical shortcuts remain active; physical None may still reserve native input.
- `linux/ui/physical_shortcuts/bridge.lua:24–26` forwards this exact production capability; `:37` requires it for bridge availability; `:45–47` refuses open before creating an editor/capture session.
- `linux/infra/shortcuts_scope.lua:463–464` forwards the same capability. `:471` and `:493` refuse physical-action mappings/parameters requiring delivery. Removal and disabled/None mappings retain their separate established publisher; do not incorrectly classify every physical config operation as unavailable.
- `linux/ui/menu/menu_shortcuts.lua:669–673` joins the actual bridge to the production menu getter/command.
- `_shared/lua/shortcuts/physical_editor_menu.lua:15–17` requires `host.physical_delivery_available()==true` before even GUI readiness; `ready()` is false and `open()` refuses.
- `linux/adapters/keyboard_hook.lua:1973` correctly calls `position_capture_available` **observation readiness, never physical delivery**. Capturing a physical position is not proof a configured action can safely execute.
- `linux/modules/shortcuts/physical_collisions.lua:3–4` explicitly says its preflight is partial and grants no all-owner/output readiness. Its seven captured owners cannot be promoted to a delivery capability by counting code paths.

Real-Lua reproduction: `probe-physical-availability.lua` imports the production keyboard owner, bridge and shared menu controller; it provides a scope that forwards the real production capability and a GUI-ready function returning true. Assertions prove: capability=false, bridge.available=false, bridge.open=false, menu.ready=false, menu.open=false; GUI/capture/save never called. Only GUI readiness and scope plumbing are controlled; the decisive capability and forwarding/menu code are genuine. No native desktop needed to establish an unconditional false branch.

Other OS equivalents: `macos/modules/shortcuts/keyboard_shortcuts.lua:521–527` explicitly states broker/output integration is not yet qualified and also returns false unconditionally. Windows `ui/physical_shortcuts/README.md` states no native editor host/runtime. Therefore report **unavailable on all three today**, with dormant/shared host components and observer capabilities distinguished from complete delivery. This is not a newly missing Linux-only parity feature. Recommended TODO: complete and qualify native physical broker + all-owner conflict resolution + source/output custody on macOS/Linux, and editor/runtime on Windows; then enable only through an acknowledgement tied to that complete native path.
