# Audit AHK ErgoptiPlus - 2026-06-19

## 1. Méthodologie

Audit adversarial au format "Loop Until Dry" sur static/ergopti_plus/windows/.
Catégories de recherche ciblées :
- [A] Action -> error / crash / locking (Exceptions non gérées)
- [B] Action -> no output (Pertes d'output, callbacks silencieux)
- [C] Race conditions (Appels bloquants, états partagés)
- [D] Lags (Scans O(n), appels synchrones)

## 2. Vulnérabilités Critiques (G1 / G3)

### 2.1 Blocage clavier par exception SendInput non gérée (space.ahk)
- **Fichier** : modules\tap_holds\space.ahk
- **Gravité** : Critique (G1 / G3) - Gèle les modificateurs système.
- **Root Cause** : SendInput("^" . captured) est utilisé pour envoyer le caractère capturé. Si l'utilisateur saisit un caractère spécial (ex: {, ^, +), AHK v2 lève une exception TargetError ("Invalid key name"). Cette exception coupe le thread courant *avant* l'exécution du bloc inally qui libère le modificateur physique (SendInput("{LCtrl Up}")). Le clavier reste bloqué dans l'état "Ctrl enfoncé" jusqu'à ce que l'utilisateur appuie physiquement sur Ctrl.
- **Fix appliqué** : 
  1. Échappement des métacaractères AHK via RegExReplace(captured, "([!#^+{}])", "{}").
  2. Remontée du bloc 	ry pour englober l'appel SendInput dynamique, empêchant l'exception de contourner le inally.

### 2.2 Appels API natifs non protégés (Startup Crash)
- **Fichiers** : modules\shortcuts\win.ahk, modules\shortcuts\altgr.ahk
- **Gravité** : Moyenne (G1 localisé)
- **Root Cause** : Appels Hotkey() et InputHook() sur des scancodes ou définitions sans bloc 	ry/catch. En cas d'erreur système ou de layout inattendu, l'exception arrête le script AHK, rendant le driver muet.
- **Fix** : Encapsuler l'enregistrement Hotkey() et la création InputHook() dans des blocs 	ry.

## 3. Lags et Blocages Thread Principal (G4)

### 3.1 WinHttp Synchrone sur la construction du Menu Tray (menu_models.ahk)
- **Fichiers** : ui\tray_llm\menu_models.ahk, modules\llm\api_ollama.ahk
- **Gravité** : Élevée (G4) - Bloque le remapping complet.
- **Root Cause** : La ligne installed := deps_ready ? LLM_OllamaListModels() : [] s'exécute de façon synchrone lors de la construction du menu, utilisant WinHttp.WinHttpRequest.5.1 avec un timeout de 5000ms. Si l'API Ollama locale freeze, le thread principal d'AHK est suspendu pendant 5 secondes (le hook clavier AHK ne répond plus, les frappes sont perdues ou accumulées). 
- **Fix proposé** : Remplacer l'appel direct par le cache _LLM_GetInstalledTagsCached() qui implémente déjà un TTL. L'appel bloquant initial doit lui-même être basculé vers un pattern asynchrone dans une refonte globale, ou déclenché au boot en background, afin que l'UI (le menu) ne lise que des valeurs en mémoire (Map/Array local). Mise à jour des tests stricts associés (	est_llm_menu_regressions.ahk).

## 4. Bilan

L'architecture est globalement robuste suite aux audits précédents :
- Le pattern Updater asynchrone (Poll) est strictement respecté et verrouillé par 	est_updater_sync_winhttp_blocks.ahk.
- Les paires Lifecycle (Logger.start/success) sont équilibrées.
- Le fix "AltGr SC138" est en place avec le KeyWait dans ToggleSuspend.

L'effort doit se poursuivre sur l'élimination des appels ComObject("WinHttp...").Open("...", "...", false) (mode synchrone) restants dans pi_ollama.ahk.
