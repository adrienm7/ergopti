# AHK Driver Audit — 2026-07-01

## 1. Executive summary

This adversarial G1–G4 robustness audit examined the ErgoptiPlus AHK driver (`static/ergopti_plus/windows`) across 17 zones plus 3 cross-cutting sweeps (suspend/pause, shared-state races, blocking hot-path). All zones reached a "dry" state (repeated passes stopped surfacing new findings) between pass 2 and pass 4. **64 findings survived independent adversarial verification** — every finding in this report was re-checked against live source by a skeptical second pass and confirmed accurate (with minor citation corrections noted inline where the verifier caught them).

**Findings by severity:**

| Severity | Count |
|---|---|
| Critical | 2 |
| High | 8 |
| Medium | 40 |
| Low | 14 |

(64 total; some findings' severity was independently re-affirmed by the verifier as already well-calibrated.)

**Follow-up pass (2026-07-02):** F40's test fragility was fixed and the `project_config_v2_refactor` watch-list item (which failed verification in the original run due to an agent infrastructure error) was completed, surfacing one new finding (**F48**, same bug class as F5). See F40's and F48's entries and the Section 4 watch-list table for details — both are reflected in the counts above.

**The two critical findings are the headline result of this audit:**
- **F1** — `LLM_Menu_Init` silently reverts the just-applied `AboveNormal` boot priority boost back to `Normal` 16ms after every single launch, on every boot, regardless of whether the LLM feature is even enabled. This defeats a same-day perf fix (commit `3d27945be`) before it can ever help a real user.
- **F2** — The tray Metrics category toggle is completely dead: clicking it rebuilds the menu and writes an inert TOML key, but never touches the actual keylogger enable flag or the confirmation/security-warning dialog gate. Users believe they can enable/disable the keystroke logger from this control; they cannot.

**Most fragile zones** (by finding density and lowest dry-pass number — i.e., zones that kept yielding findings the longest):
- **updater** (6 findings, dry at pass 4) — WebView2 lifecycle ordering, re-entrancy, and Suspend-guard gaps recur throughout this zone.
- **adapters** (8 findings, dry at pass 4) — the "foundation" layer has the most volume of findings, though nearly all are low/medium diagnosability gaps (bare `try` with no `catch`), not correctness bugs.
- **keylogger** (5 findings, dry at pass 4) — includes a genuine privacy-relevant bug (app-switch/window-switch events filtered against the wrong side of a focus transition) and several silent-data-loss gaps (event types with no schema table).
- **llm** (5 findings, dry at pass 4) — backend switching doesn't propagate to the live engine; async cancellation has a narrow gap.
- **cross_infra** (5 findings, dry at pass 4).

**Honest verdict:** This is a mature, heavily-defended codebase — the majority of zones are "audited-clean" for G1 (crash/correctness) and G3 (race/lifecycle) under normal operation, and the project's own hardening campaigns (Pattern 1–4, the `_SafeHotkey`/`RegisterMenuItem`/Suspend-guard conventions) are real and largely successfully applied. However, this audit found that **hardening campaigns are consistently incomplete by one sibling site** — nearly every finding here is "the same bug class that was already fixed elsewhere, but missed at this one call site." The watch-list regression check independently confirms this pattern: of 19 previously-documented fixes re-verified, 5 show the identical class of bug re-appearing at an unprotected sibling (SC038 prefix latch, `feature_io.ahk`'s global-Features anti-pattern, macOS menu-manifest desync, webview bridge gap, and — found in the 2026-07-02 follow-up pass — a second `ToggleAllFeatures` site reproducing F5's stale-duplicate-TOML-section bug) and 1 memory entry itself went stale (a documentation-only drift, not a code regression). No zone could be fully certified defect-free; this report should be treated as a snapshot of currently-known gaps, not a certification of correctness.

**Zones that could not be audited due to agent infrastructure failures: none.** All 17 zones plus the 3 cross-cutting sweeps completed their full loop-until-dry passes. The one watch-list item that failed verification in the original run (`project_config_v2_refactor`) was completed in a 2026-07-02 follow-up pass — see Section 4.

## 2. Findings

Sorted by severity (critical → high → medium → low). Guarantee key: **G1** = correctness/crash, **G2** = functional gap/silent failure, **G3** = race/lifecycle, **G4** = performance/hot-path.

### Critical

**F1 — `LLM_Menu_Init` unconditionally resets the fresh AboveNormal boot priority back to Normal on every launch, 16ms after boot**
- **Severity:** critical · **Confidence:** confirmed_by_reading · **Guarantee:** G4
- **Files:** `ui/menu/menu_llm/init.ahk:47`, `ErgoptiPlus.ahk:14`, `modules/llm/ollama_deps_checker.ahk`, `ui/menu/menu_init.ahk:163`
- **Repro:** Boot the driver normally, any config. (1) `ErgoptiPlus.ahk:14` runs `try ProcessSetPriority("AboveNormal")` at the top of boot. (2) ~16ms after "ready" (`MENU_BUILD_DEFER_MS`), `BuildTrayMenuDeferred` fires and calls `initMenu()`, which unconditionally calls `LLM_Menu_Init(_LlmSavedOpts)` — not gated on whether LLM is enabled. (3) `LLM_Menu_Init` unconditionally executes `try ProcessSetPriority("Normal")` as its first statement, with no guard, no check of current priority class, no awareness of the boot boost. Priority silently reverts to Normal for the rest of the session. Any later CPU contention reproduces the exact multi-second "Slow OnChar"/"Slow HSE.FeedChar" HotPath warnings the boost was meant to prevent.
- **Root cause / why silent:** Commit `3d27945be` introduced the new AboveNormal baseline but never audited the four pre-existing `ProcessSetPriority("Normal")` restore sites left over from the older Ollama-install High-priority boost (AHK-30). `LLM_Menu_Init`'s own docstring literally says "every boot starts from Normal" — it predates and is unaware of the new baseline. `ProcessSetPriority` succeeds silently in both directions; nothing logs when priority changes, so nothing in the log distinguishes "still AboveNormal" from "silently downgraded 16ms after boot." The only guarding test (`test_hotpath_priority_starvation.ahk`) does pure string-presence checks on `ErgoptiPlus.ahk` in isolation and never looks at any other file.
- **Fix:** Introduce a single named constant (e.g. `DRIVER_BASELINE_PRIORITY_CLASS := "AboveNormal"`, single source of truth) and replace all four `ProcessSetPriority("Normal")` restore sites (`ollama_deps_checker.ahk:402,442,458` and `menu_llm/init.ahk:47`) with a reference to it.
- **Regression test:** A meta test reading the concatenated driver source and asserting every `ProcessSetPriority(` call site outside the boot-time boost line references the same baseline constant — specifically asserting `LLM_Deps_Fail`, `LLM_Deps_Cancel`, `_LLM_Deps_OnPollProbeResult`, and `LLM_Menu_Init`'s restore calls do NOT contain the literal string `"Normal"` immediately after `ProcessSetPriority(`.

**F2 — Metrics master enable/disable toggle in the tray menu is dead**
- **Severity:** critical · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `ui/menu/menu_metrics.ahk`, `lib/manifest_menu.ahk`, `ui/menu/menu_metrics_actions.ahk`, `_shared/modules/features/manifest.toml`
- **Repro:** Tray → 📊 Métriques submenu → click "✅ Métriques activées (cliquer pour désactiver)". The whole tray menu rebuilds, but `MetricsShortcuts.enabled` (the actual keylogger master flag) is untouched, no confirmation/security-warning dialog appears, and the row still reads "activées" on next open regardless of real keylogger state.
- **Root cause / why silent:** Commit `597e2cc6a`-class refactor deleted `BuildMetricsMenu`'s explicit `AddCategoryToggleItem(..., ToggleMetricsEnabled())` call as a perceived duplicate of the manifest-driven generic toggle renderer. For Gestures the same refactor correctly kept the bespoke toggle AND tagged the manifest entry `platforms: ["hs"]` so the generic renderer skips it on AHK. For Metrics no such platform restriction was added, so `_MR_RenderToggle` auto-renders it via `IsCategoryGated("Metrics")` (which defaults to `true` since "Metrics" was never added to the `CategoryEnabled` Map) and `ToggleCategoryAllFeatures("Metrics", !Gated)` — which persists a key `ApplyMasterGatesToFeatures` never reads. `ToggleMetricsEnabled()` (with its real confirm/security-warning dialogs) has **zero call sites** anywhere in the driver.
- **Fix:** Restore the explicit `AddCategoryToggleItem(..., ToggleMetricsEnabled())` call in `BuildMetricsMenu` and add an AHK-side skip to the manifest's `metrics_menu` toggle entry, mirroring the Gestures fix from the same commit.
- **Regression test:** AHK meta test asserting `ToggleMetricsEnabled` has ≥1 call site in `ui/menu/menu_metrics.ahk`, and that the `metrics_menu` manifest toggle entry either carries a `platforms` filter excluding `ahk` or that the real wiring is present in source.

### High

**F3 — `HookDispatcher.Start()`'s InputHook construction is unguarded**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `lib/hook_dispatcher.ahk:326-334`, `ErgoptiPlus.ahk:642`
- **Repro:** On a session where low-level keyboard hook creation is contested (RDP, a second AHK/accessibility tool, transient OS resource exhaustion — the code's own comments acknowledge this happens), `InputHook("V L0")` construction, `ih.KeyOpt`, or `ih.Start()` throws inside `HookDispatcher.Start()`. Called as a bare call (no try wrapper) at `ErgoptiPlus.ahk:642`. `OnError(ErgoptiGlobalErrorHandler)` catches it globally, logs once, and boot proceeds normally — tray menu builds, hotstrings register, "Driver fully initialised — ready" logs — but there is no InputHook and no mouse hotkeys for the rest of the session. Every hook-dependent feature (remap, hotstrings, keylogger, CapsWord cancel, gestures, LLM dismiss-on-click) goes completely dark.
- **Root cause / why silent:** The mouse Hotkey registrations a few lines below are correctly wrapped in `_SafeHotkey` (try/catch + WARNING). The InputHook construction just above was never given the same treatment. `OnError` absorbs the exception exactly like any recoverable one — logged, toasted, execution continues — with no post-call check of `HookDispatcher._started`/`IsStarted()` anywhere in the boot sequence.
- **Fix:** Wrap the InputHook construction/configuration/`.Start()` span in its own try/catch, symmetric with the existing `_SafeHotkey()` pattern. Log at ERROR and either retry once or surface a persistent failure indicator.
- **Regression test:** Meta test alongside `tests/meta/test_dispatcher_start_guarded.ahk` asserting the InputHook-construction block is wrapped in its own try/catch with a `LoggerError` call on failure.

**F4 — Personal-hotstring section created live (editor "new section") is never seeded into Features, so its tray-menu toggle silently no-ops forever**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `ui/personal_toml_editor.ahk`, `ui/menu/menu_hotstrings.ahk:621`, `ui/menu/menu_engine.ahk`, `lib/feature_io.ahk`, `lib/personal_features.ahk`, `modules/hotstrings/hotstrings_personal.ahk`
- **Repro:** Editor → "Nouvelle section" → name it "voyage" → close editor (no Reload) → reopen menu → toggle "voyage" on. `_HS_TryLiveToggleV2` classifies any 3-segment `hotstrings.<x>.<y>` path as live-eligible by string shape alone and calls `WriteFeatureV2` unconditionally; `WriteFeatureV2` returns `false` with **zero logging** because the Features node was never created (`EnsurePersonalHotstringFeature` is only wired at boot / bulk-toggle paths, never in the editor's `_NewSection`). The caller ignores the return value, calls `RebuildHotstringsLive()`, and returns `true` as if it succeeded. The section's hotstrings never register. Only a full Reload fixes the seeding gap, silently discarding the user's enable click.
- **Root cause / why silent:** `MenuAddItemWithLabel` (unlike its sibling `MenuAddItemFromManifest`) has no `FeatureLocateV2` guard, and `WriteFeatureV2` has no logging on its false-return path (unlike `WriteFeatureBatchV2`, which does).
- **Fix:** Call `EnsurePersonalHotstringFeature(SecName)` in the editor's `_NewSection`. Defensively, `WriteFeatureV2` should log a warning on unresolved paths, and `MenuAddItemWithLabel` should skip/warn like its sibling.
- **Regression test:** Test that seeds a Features fixture without the new section, calls `WriteFeatureV2` on it, and asserts either success (if seeding is fixed) or a logged WARNING; source-scan test asserting `_NewSection`'s body calls `EnsurePersonalHotstringFeature`.

**F5 — `SaveFullConfig`'s `_CollectFeatureUpdates` writes every `ahk.`-namespaced Features section under its bare, un-prefixed section name**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `lib/config_io.ahk`, `lib/feature_io.ahk`, `lib/toml/toml_config_loader.ahk`, `lib/manifest_reader.ahk`
- **Repro:** Fresh boot (unconditional `SetTimer(SaveFullConfig, -500)`) writes both `[ahk.gestures] enabled=true` (correct) AND a spurious bare `[gestures] enabled=true` (from walking the already-prefix-stripped in-memory Features tree). `TOML_BatchWrite` sorts sections alphabetically, so `ahk.gestures` writes before `gestures`. User hand-edits only `[ahk.gestures] enabled=false` and reloads — `ApplyConfigToml` applies sections in file order, applies the correct edit first, then reaches the later stale `[gestures] enabled=true` and silently overwrites it back to `true`. Same pattern affects 100% of Layout toggles and all `ahk.shortcuts.*` sub-Maps (including AltGr+modifier dispatch, which has no separate assignment table).
- **Root cause / why silent:** `ManifestBuildFeaturesMap()` strips the `ahk.` prefix uniformly when building the in-memory Features tree. `WriteFeatureV2`/`FeatureLocateV2` correctly re-derive the section from the original (prefixed) manifest path, but `_CollectFeatureUpdates` walks the already-stripped Features Map directly with no re-prefixing mechanism. The two sections never collide (different TOML keys), so no error is raised, and `TOML_RunStrictCanonicalization`'s merge/preserve semantics guarantee the stale duplicate is never pruned.
- **Fix:** Give `_CollectFeatureUpdates` a per-top-level-key TOML-section prefix map, or drive it off the manifest's own `section` field per leaf instead of re-deriving from the stripped Features nesting.
- **Regression test:** Unit test building a Features fixture with a top-level `layout`/`shortcuts.script_control` shape, calling `_CollectFeatureUpdates`, asserting every emitted Section starts with `ahk.` (fails today — emits bare names).

**F6 — CapsLock dead-key dispatch now runs `InputHook.Wait()` under Critical, stalling the whole AHK message pump for up to 2s**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G4
- **Files:** `modules/keymap/layout/layout_shift_caps.ahk`, `modules/keymap/layout.ahk`, `modules/keymap/layout/layout_altgr.ahk`
- **Repro:** CapsLock ON, `ergopti_base` enabled (default). Press the physical key bound to SC01B (¨) or SC02B (^). `LayerDispatch`'s `SerializeSymbols=true` path (added by commit `acae304b1`, justified by "none of CAPSLOCK_SYMBOLS' own callbacks ever Sleep") wraps `Cb()` in `Critical("On")`. But `CAPSLOCK_SYMBOLS["SC01B"/"SC02B"]` call `DeadKey(...)`, which creates an `InputHook("L1 T2", ...)` and calls `ih.Wait()` — a blocking, message-pumping wait with a 2-second timeout. The project's own test comment states explicitly: "ih.Wait() pumps the message loop, so a pause can land DURING the wait." A sibling pre-existing bug exists in `AltGrShiftDispatch`'s unconditional `Critical("On")` wrap, which covers 8 (not 7) `DeadKey.Bind(...)` entries.
- **Root cause / why silent:** The commit's justifying comment is factually false and nobody cross-checked it against the CAPSLOCK_SYMBOLS table 10 lines above. `test_input_serialization.ahk` only asserts the structural position of `Critical("On")` relative to `Cb()`, never what `Cb()` actually does.
- **Fix:** Exclude the DeadKey-bound entries from the Critical path, or have `DeadKey()` release Critical before `ih.Wait()` and re-acquire it for the final emit.
- **Regression test:** Meta test extracting CAPSLOCK_SYMBOLS/ALTGR_* tables and asserting no `DeadKey.Bind(...)` entry is reachable through a Critical(On)-preceded path without an intervening release before `ih.Wait()`.

**F7 — Personal hotstring editor's live-reload never removes/clears old HSE registrations**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `lib/hotstrings/personal_toml_io.ahk`, `ui/personal_toml_editor.ahk`, `ui/personal_toml_editor_webview.ahk`, `lib/hotstrings/hotstring_engine_main.ahk`
- **Repro:** Add trigger `test★→AAA`, save (works). Edit the same entry's output to `BBB`, save again without reloading. Typing `test`+magic key still expands to `AAA` — the stale, first-registered spec wins the tie-break. Same for delete: the trigger keeps expanding to its old output.
- **Root cause / why silent:** `ReloadPersonalSection()` re-registers every entry via `CreateHotstring`/`CreateCaseSensitiveHotstrings`, appending fresh Specs, but never calls `HSE_DisableGroup`/`RegistryClear` first. Its `Options` Map omits `Section` entirely, so every re-registered personal hotstring lands in the generic `"default"` group (never cleared). `_HSE_Beats`'s tie-break favors lower `Seq` (oldest) on ties, so the newest edit is registered as a dead duplicate that can never win.
- **Fix:** Pass `"Section", SectionName` in Options so the derived Group matches the boot-time loader, and clear/disable the old group before re-registering (or route through the `RebuildHotstringsLive()`-style clear+re-register pattern).
- **Regression test:** Call `ReloadPersonalSection` twice with different outputs for the same trigger, assert the match resolves to the second output (fails today); call it with an entry removed and assert the trigger no longer matches at all.

**F8 — Notepad clipboard dispatch branch never records the real emitted character in the last-sent ring**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `lib/hotstrings/hotstring_dispatch.ahk`
- **Repro:** Any HSE hotstring expansion in Notepad. `HSE_DispatchMatch`'s Notepad branch calls `SendNewResult(BackSpaceSeq, false)` — but `SendNewResult` unconditionally calls `UpdateLastSentCharacter(SubStr(Text, -1))` where `Text` is the literal BackSpace escape string, extracting `'}'` and polluting the process-global `_LSC_RING`/`LastSentCharacterKeyTime`. The subsequent `SendInstant(Replacement . EndCharEmitted)` — the real paste — never calls `UpdateLastSentCharacter` at all. Any deadkey combo or time-gated hotstring typed next (in any app, since the ring is process-global) silently misfires.
- **Root cause / why silent:** A prior fix (`b92f06941`) added the correct `UpdateLastSentCharacter` call to the atomic (non-Notepad) branch and its own regression test, but never touched the Notepad branch. `IsTimeActivationExpired` fails closed with no error distinguishing this from ordinary gate expiry.
- **Fix:** Issue the backspace via a helper that doesn't corrupt the ring, and add `UpdateLastSentCharacter(SubStr(EndCharEmitted != "" ? EndCharEmitted : Replacement, -1))` after `SendInstant`, mirroring the atomic branch.
- **Regression test:** Extend `test_hse_consumed_endchar_ring.ahk`-style meta test to assert the Notepad branch does not feed `BackSpaceSeq` into `UpdateLastSentCharacter` and does call it with the real emitted text.

**F9 — `app_switch`/`window_switch` events check the privacy filter against the NEW window, leaking the app/title being protected**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G2
- **Files:** `modules/keylogger/keylogger_hook.ahk`, `modules/keylogger/keylogger.ahk`, `lib/metrics/metrics_filters.ahk`
- **Repro:** Add `1password.exe` (or leave private-browsing filtering ON, default) → focus that app → Alt-Tab away to a normal app. `KL_Hook_RefreshContext` detects the switch and calls `KL_LogAppSwitch(prev_app, new_app, duration)`/`KL_LogWindowSwitch(...)` with the OLD app/title as payload — but `KL_AppendLog` calls the zero-argument `MF_ShouldFilter()`, which evaluates the LIVE (new, non-excluded) focused window. The exclusion check always evaluates the wrong side of the transition, so the excluded process name and/or the verbatim private-browsing window title text are written to `today.log` and the SQL event tables.
- **Root cause / why silent:** `MF_ShouldFilter()` is architecturally stateless — there is no `MF_ShouldFilterFor(app, title)` helper anywhere. It never throws or logs; it answers a technically-true-but-wrong-context question. Deterministic on every transition away from a protected context, not a narrow timing race.
- **Fix:** Check the OUTGOING (`prev_app`/`prev_title`) side against exclusion/private-browsing rules before emitting the switch event; redact or skip emission when the previous context was filtered.
- **Regression test:** Stub `prev_app`/`prev_title` to an excluded/private value, switch the live focus cache to a different app, invoke the refresh logic, assert no `app_switch`/`window_switch` entry with the excluded data reaches the pending-entries buffer.

**F10 — `Updater_DownloadAndInstall` has no re-entrancy guard — two "Update now" dialogs can trigger concurrent downloads racing on the same staging file**
- **Severity:** high · **Confidence:** confirmed_by_reading · **Guarantee:** G3
- **Files:** `lib/updater/self_update.ahk`
- **Repro:** TrayTip balloon click opens update-prompt dialog A (fresh `Gui()`, non-modal, no singleton). Open the AHK-native changelog fallback and click "Install this version" for the same release → opens dialog B. Click "Update now" on A → download starts, `_UpdaterDownloadInProgress:=true`, async WinHTTP request + poll chain begins. Before it completes, click "Update now" on B → `Updater_DownloadAndInstall` runs again unconditionally, deletes/recreates `NewExe`, opens a SECOND async request targeting the same path. Both eventual `ADODB.Stream.SaveToFile` writes race with no lock, risking a corrupted/truncated `ErgoptiPlus_new.exe` that the swap script moves into production.
- **Root cause / why silent:** Only `Updater_OneClickUpdate` checks `Updater_GetUpdateState()` before proceeding; `Updater_ShowUpdatePrompt`'s button and the changelog's "Install this version" button call `Updater_DownloadAndInstall` directly with zero re-entrancy check, and the dialog itself has no singleton guard.
- **Fix:** Add the same `_UpdaterDownloadInProgress` guard directly inside `Updater_DownloadAndInstall` (single source of truth protecting all three call sites), and make `Updater_ShowUpdatePrompt` a singleton.
- **Regression test:** Source-scan asserting `Updater_DownloadAndInstall`'s body contains an early `_UpdaterDownloadInProgress` check with a `return` before `DirCreate`/`Req.Open`.

**F16 — `ActivateLayer`/`DisableLayer` invert nav_layer's boot-time `A_MaxHotkeysPerInterval=1000` raise**

**F18 — `LAltCapsLockShortcut` lacks the defense-in-depth Features sub-map guard its AltGr siblings just received**
