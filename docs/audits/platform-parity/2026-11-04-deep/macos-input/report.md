## MI-001 — Catalogue layer actions update keyboard remapping but leave wheel-layer state unchanged

Severity **medium**, confidence **high** for the composed production Lua behavior. Native macOS execution was unavailable.

The navigation layer's declared wheel bindings do not follow `layer_on`/`layer_off` when those catalogue actions are assigned to a gesture or an action-based keyboard slot. Starting from ordinary scrolling, `layer_on` requests `layer_active=1`, but the wheel remains ordinary scrolling. Conversely, after a tap-hold/generated action entered the layer, `layer_off` requests `layer_active=0`, but the wheel can continue consuming scroll and posting the layer's volume action until an F19 exit sentinel arrives. Normal generated tap-hold entry/exit does work.

Evidence and root cause:

- `static/ergopti_plus/macos/modules/gestures/actions.lua:966` and `:970`, registered `layer_on`/`layer_off`: call `ke.set(KE_LAYER_VARIABLE, KE_LAYER_ON/OFF)` and supply no completion callback or wheel-state notification. These actions are dispatched by the actual action registry, including keyboard action slots.
- `macos/platform/remap/ke_variables.lua:964`, `M.set`: generic exact-generation variable write/enqueue; it does not publish a layer signal. The file contains no F19/F20/control-sentinel producer. Setting a Karabiner variable through its CLI is a variable write, not a key event.
- `macos/modules/shortcuts/actions/system.lua:1048`, `M.bind_layer_wheel`: private `layer_held` changes only inside the registered `ControlSentinels` listener; the scroll callback passes through while false and consumes a bound slot while true.
- `macos/modules/keymap/control_sentinels.lua:43` maps only F20/F19 to the nav enter/exit signals. `claim_key` at `:111` publishes on actual sentinel key-down.
- `macos/platform/remap/generator.lua:619` and `:652` inject enter/exit sentinels into generated actions that write the layer variable; this cannot patch a Lua catalogue action that writes that variable directly.

Executed reproduction:

```
/workspace/scratch/parity-toolchain/lua-5.4.8-dlopen/src/lua docs/audits/platform-parity/2026-11-04-deep/macos-input/probe-gesture-wheel.lua
```

`probe-gesture-wheel.lua` loads the existing fixture constructors from their original source prefixes without rewriting production modules. It composes the real gesture/action registry, actual wheel binding owner, actual control-sentinel owner and synthetic-input broker, with Hammerspoon event/window/timer doubles and an accepted Karabiner variable-write boundary. Assertions check both exact requested variable values and the observable scroll decision/output:

```
REPRO ON: registered layer_on writes layer_active=1, but bound wheel passes ordinary scroll (zero slot lookups)
REPRO OFF: registered layer_off writes layer_active=0, but wheel still consumes scroll and posts SOUND_UP down/up
CONTROL: generated F20/F19 sentinels do synchronize wheel entry/exit; same wheel owner stays healthy
```

The native CLI success itself is modelled, not executed. There is nevertheless no later completion observer in the actual actions that could update the wheel after success. This distinguishes the integration omission from an unverified native failure. No evidence of an intentional product restriction was found: the same navigation layer is advertised, and the wheel owner specifically follows that layer.

Silent failure: no error accompanies the successful action/variable write; only wheel behavior disagrees with the keyboard layer. A regression test should exercise both `layer_on` from an unarmed wheel owner and `layer_off` after a sentinel-armed owner, including refused/superseded native writes. A fix should publish the matching state only after the same exact-generation write succeeds, retain generation/revision admission and avoid emitting an application-visible F-key. This is a proposed fix direction, not code changed by this auditor.

## Pass 2 — adversarial/error follow-up and refutations

1. **Tap-holds OFF allegedly disables combinations:** refuted. Actual generator/model suite gives 9/9; holds/chords still emit while tap-holds are off and combinations on. Toggle combinations off removes its rules. The Tap-Holds-on graph is also pinned against the earlier generated graph, rather than merely comparing a new implementation to itself.
2. **Held modifiers leak into an exact trigger or suppress a chord:** no reproduction in the executed typed-output model suite, 53/53, including catalogue-wide sticky actions, tap-only keys, all combo taps, symmetric chords, first-key holds and exact trigger hand modifiers. These remain model claims tied to the pinned Karabiner semantics, not a physical keyboard run.
3. **Layer editor/physical editor can retire a successor through a stale native callback:** refuted by the executed real host ownership tests. Window/controller deletion failures remain retained; one native close notification is sufficient; original observational capture and original cancel capabilities survive replacement.
4. **Recommended layer rollback can delete an external edit or accept a forged receipt:** refuted by the 20/20 scoped transaction tests, including partial removal, changed file bytes, source races, private receipt identity, compensation failure and global-parent restore debt.
5. **Owned `reconcile(false)` might hang every asynchronous pause:** broader claim refuted. `probe-stop-retry.lua` confirms that repeated reconcile creates a different observer, rejected by real `runtime_owner.stop` as `observer_conflict`, but also demonstrates that ordinary delayed settlement invokes the original observer and restores the user's Karabiner correctly. Production `adapters/installed_physical_source.lua:283` retains a repeating retirement pump; `physical_history_session.lua:359` and `:504` retain retirement hints/continuations. A native state that needs an otherwise absent explicit retry was not established. Therefore this stays a hypothesis about exceptional retry liveness, **not a confirmed finding or TODO**. The actual direct-owner retry control succeeds, and its limitation is preserved in `stop-retry.log`.
6. **Three nav preset assertions failed in the first batch:** refuted as cross-module test-fixture contamination in the custom unisolated harness. The nav-rule module run alone with real LuaFileSystem passes 31/31. No product defect was inferred from those failures.
7. **One layer-authority meta-test failed:** unavailable dependency, not a product reproduction. That tree-scanning test requires native `luv` through runner discovery. LuaFileSystem was built later and works, but luv was absent. Its `0 passed / 1 failed` diagnostic remains visible in `isolated-results.json` and its own log; no green claim is made for it.
