# Independent countercheck: Windows clipboard WCP-001 / WCP-002

Source pinned to `213d65af24d2aa4845ba47743c9bab6787b61964`. Reviewed the original report/JSON, all three proof files, actual capture/output/clipboard/lifecycle callers and existing selection/SendInstant test fixtures. No original artifact, production or registered test was changed. **No AHK, native clipboard, HWND transition or input emission was executed.** The source-evidence generator was read rather than rerun because it rewrites an original probe.

## Verdict

Both findings survive on the narrower **external native foreground-window change** path. Their pause/physical-generation evidence needs qualification. `Critical` serializes AHK pseudo-threads; it is not an OS foreground/clipboard lock. An external foreground transition can occur while the script cannot run another callback. Conversely, a fake clipboard function calling `Suspend(true)` directly does not prove a real pause hotkey can preempt native ClipboardAll, especially under an inherited Critical span.

## WCP-001: defensible path and qualifications

Actual chain:

1. `windows/infra/hotstrings/hotstring_send.ahk:726` (`GetSelectionAsync`) captures physical generation and later `Job["foreground"]` before `SaveFn.Call()`.
2. Its short Critical section at `:778` protects installation of the job only; it restores the caller's previous Critical state before clipboard preparation. An inherited Critical caller is possible; absence of one is also possible (`GestureDispatch`, `Search`).
3. `_SelectionCaptureStartCurrent :871` checks `!A_IsSuspended`, exact active job and ID. It checks **neither native HWND nor physical generation**.
4. `_SelectionCapturePoll :906` checks physical generation and `WinExist("A")`, but only after startup has called clear and copy.

Strong reachable native-semantic sequence: editor window A owns the selected text; a successful ClipboardAll snapshot takes time (for example, a separate owner renders a non-bitmap rich format after the preflight). While it runs, an application already entitled to control foreground opens/focuses window B. No AHK pseudo-thread preemption is required. After snapshot return, startup's guards can still pass, and its global Ctrl+C targets current B. Poll later rejects the old A job, which cannot undo that control chord. A native reproduction must respect normal SetForegroundWindow entitlement; arbitrary focus-stealing from a background helper should not be assumed.

The clipboard-loss variant requires a separate precise order: saved snapshot A must already be detached and its native clipboard lock released; an external process publishes B **after that snapshot but before `CB_ClearWithReceipt` clears it**. An external writer cannot mutate the clipboard while another process genuinely holds OpenClipboard. `CB_ClearWithReceipt :957` authenticates its own clear; it does not compare the clipboard generation to the earlier SaveAll snapshot. If the later copy produces nothing and no newer copy occurs after the clear, the owned-clear cleanup can restore older A. Do not say every focus change causes that loss, or that a new external copy can pass through an existing native clipboard lock.

**Recommended WCP-001 qualifier:** “Source confirms that startup does not recheck foreground HWND or physical generation before clear/copy. External native focus changes are not excluded by Critical. The supplied generation-only fake proves the missing predicate; timing of real InputHook updates during/after ClipboardAll remains unexecuted and is not universally guaranteed.” Keep the external-HWND scenario as the primary reproduction.

## WCP-002: original target checks stop before the sender's own preparation

The apparent outer defenses are real, but they end too early:

- `_SelectionCaptureFinish :1032` rechecks context after restore and at `:1048` checks suspension/ID immediately before invoking the callback. It has already retired `_SelectionCaptureJob`.
- `modules/gestures/actions.ahk:736` (`GestureTransformSelection`) dispatches `_GestureSendTransformedSelection`, which calls `SendInstant` with plain transformed text and **no retained HWND/control/generation admission**.
- `modules/keymap/layout.ahk:630` (`WrapTextIfSelected`) explicitly turns Critical off, consumes a current UIA selection, and then calls SendInstant. The consumed selection capability is not supplied to that sender.
- `infra/hotstrings/hotstring_send.ahk:486` (`SendInstant`) obtains a process-local clipboard token, checks busy/image fallback, calls `CB_SaveAll :542`, writes with receipt, arms restoration and calls global `SendInput(Prefix . "^v") :563`. There is no HWND/control/suspension/input-epoch test after its preparation. Its clipboard-free fallbacks also use global SendInput, without a target receipt.
- `GesturePastePlain :833` has native clipboard-content ownership/CAS; `SendFinalResult` → `_SendFinalResultUnchecked :438` does not add destination admission. This supports the sibling target-check concern, but the focused reproduction should remain one actual selection-transform/wrap route.
- `GestureInvokeAction`'s immutable window receipts apply to separately confirmed active-window actions such as force quit/unblock. They do not wrap the ordinary case-transform/selection sender with a later selected-target guard.

Strong sequence: complete a valid case/wrap capture for editor A, enter the sender's own successful non-bitmap clipboard snapshot, and let an authorized native foreground transition focus B before that snapshot returns. The sender then pastes A's prepared replacement into B because neither its global SendInput nor its clipboard receipt names A. Critical on a particular caller would not eliminate this external-window sequence. This is a source/Win32-semantics conclusion; actual application consumption and native timing remain unexecuted.

**Recommended corrected WCP-002 title:** “Selection transformations and wrapping can paste into a new foreground window during clipboard preparation.”

**Recommended corrected reproduction:** “Invoke an actual case-transform or typed/explicit wrap in editor A. During SendInstant's subsequent successful clipboard snapshot/preparation, an independently authorized native window transition focuses B. After preparation returns, the sender has no retained destination check and issues global Ctrl+V to current B. The supplied AHK pause probe is unexecuted and demonstrates only a missing helper-level suspension predicate; it is not evidence that a normal pause pseudo-thread preempts native ClipboardAll under Critical.”

Pause may be separately reachable on an interruptible caller after a message-processing/native-return boundary; the source has relevant open-Critical routes. However, that needs a genuine caller/lifecycle/scheduler test. Keep it as **conditional/unvalidated**, rather than the primary title or an unconditional high-confidence native reproduction. `ToggleSuspend` includes prefix deferral and lifecycle/NavEventOwner work, which the fake `Suspend(true)` omits. The clipboard shutdown preflight is not evidence of a universal pause gate either: `CB_PrepareShutdown` is used for shutdown; the reviewed pause path changes Suspend and separately cancels selection jobs.

## Probe and test evidence limits

- `selection-startup-native-probe.ahk` calls the real API only in a proposed, **unexecuted** harness, with save/foreground/generation/clear/send ports replaced. Its expected result is useful for a root-cause regression, not native scheduling proof.
- `sendinstant-pause-native-probe.ahk` embeds a source-derived sender and replaces native primitives. Its fake SaveAll directly mutates Suspend. That mutation is possible even when ordinary AHK thread preemption would be blocked, so it cannot settle the Critical question.
- Existing `_SCSC_Startup` / capture-finish tests cover explicit job cancellation, pause and nested admissions using injected boundaries. They do not refute the external-HWND window or validate the timing of a real physical-generation callback during a native snapshot.
- `tests/fixtures/sendinstant_clipboard_owner_body.ahk:329` deliberately executes genuine SendInstant under its Notepad caller's Critical contract and coordinates a separate native clipboard writer. It supports the important distinction between internal scheduling exclusion and external OS custody changes. I read the fixture; I did not execute its native assertions or infer focus safety from clipboard-ownership checks.

Disposition: retain two findings, narrow both to the externally reachable native-window boundary as primary evidence, qualify physical-generation/pause variants and keep every native AHK/receiver result explicitly unexecuted. No additional defect is inferred from a direct paused helper call.
