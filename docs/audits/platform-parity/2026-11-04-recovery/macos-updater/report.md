# macOS updater and reload lifecycle audit

Audited commit: `3a680d9f530a9af686fccc16d3f7611ec7fb034c`. Scope: macOS updater Lua owners, Versions/check/menu bridges, chosen-release stage and emitted swap shell, reload guard and directly connected termination/launcher owners. Audit only: no production or registered test edits. One new, bounded finding; existing MC-002 restore/reload reporting remains an acknowledged duplicate, not recounted.

## Result: MUR-001 — a refused restart reports an armed installation as failed and idle

Severity **medium**; confidence **high for executed Lua and emitted shell**, macOS native manifestation unexecuted. Receipt/state ownership mismatch at an asynchronous handoff. The initial install consent remains valid: this is **not** an unconsented installation, a claim that cancellation was promised, or a requirement to roll back an armed install.

The Versions binding accepts an exact native ARMED receipt through `modules/updater/release_installer.lua:270–312`; its `ui/changelog/init.lua:564–573` restart calls the real `TerminationCoordinator.request_user_exit`. That coordinator may refuse **before** its emergency deadline exists: `infra/termination_coordinator.lua:920–921` calls publication admission first; root `init.lua:1256–1258` binds `hotstrings_config.capture_terminal_admission`, whose `:1501–1502`, `:1525–1538` refuse pending native hotstring publication or an already-held terminal token. This is narrower than a failed lease fence: after emergency-exit admission, the independent deadline normally exits the process even when fencing fails.

After this refusal the real shared `updater/release_install.lua:319–324` calls `fail`; `:128–168` clears `running` and publishes `phase=failed`, `reason_key=changelog_window.install_error_install`. The French string (`_shared/data/locales/fr.json:182`) is “L’installation de {tag} a échoué.” The shared page `script.js:992–994` treats failed as not running and renders its ordinary retry controls. None of these owners cancels, retires, or waits out the already-armed native worker. The actual shared failed path has **no file cleanup port or deletion**; the actual macOS binding has no inverse/disarm capability. Closing Versions only retires the page owner (`ui/changelog/init.lua:1021`), deliberately retaining accepted native work.

The exact emitted `SWAP_SCRIPT` remains on the original native installation lease and checks only launcher PID liveness, up to 1,200 sleeps of 0.1s (`release_installer.lua:94–100`). If that launcher exits within this window, the first installation still publishes its retained staged app. A second installation is not actually idle: the native lease refuses it. Thus the UI says failed/retryable while the previously accepted installation remains pending and monopolizes the native install slot. A pending-on-quit/restart-refused state or another explicit reconciliation would represent the existing semantics accurately; this audit does not prescribe cancellation.

### Executed reproduction and negative controls

Replay from any cwd:

```sh
python3 /workspace/scratch/parity-recovery/macos-updater/probes/refused-exit.py
```

`probes/refused-exit.lua` loads **actual** `updater.release_install`, macOS `release_installer.arm_swap`, `termination_coordinator`, and `emergency_exit`. Logger, stage-download, backup and native task ports record safe synthetic activity. The coordinator publication-admission port returns nil for the failure case, matching the explicit actual hotstring API refusal; it does not fabricate a generic restart failure. The accepted control retains the lease-fence callback pending; it is not a claim of completed Hammerspoon exit.

Python creates and deletes private disposable app/previous/stage marker directories and a private `sleep` PID. The emitted production shell actually runs under `/bin/sh`, with only `/usr/bin/stat` adapted to Linux device observation and `/usr/bin/open` recorded. Its executable boundary uses the repository's explicit test-only `tests/support/release_rename_physical_port.py`: real Linux `flock` and kernel exclusive `renameat2`, **not** macOS Darwin `renameatx_np`. The receipt comes from this physical worker before the Lua installer callback receives it. Only this delivery of the exact receipt crosses the recorded native task port; neither a real native Hammerspoon process nor codesign is involved.

`logs/refused-exit.txt` records:

| Case                              | Real session phases                                 |  busy | exit/lease/deadline calls | Private PID later exits                                 |
| --------------------------------- | --------------------------------------------------- | ----: | ------------------------- | ------------------------------------------------------- |
| Accepted admission, fence pending | backing_up,downloading,installing,restarting        |  true | 0 / 1 / 1                 | CHOSEN published, ORIGINAL retained as previous         |
| Publication admission refuses     | backing_up,downloading,installing,restarting,failed | false | 0 / 0 / 0                 | **Same CHOSEN publication despite failed/idle receipt** |

Both cases challenge a second physical worker while the first waits: exit 4, lease refused. This **refutes** a double-swap/data-corruption hypothesis. The first staged marker remains physically retained through the actual shared failed path. Private PID termination simulates a later legitimate launcher exit; no user process is signalled. The probe does not prove when a particular live user's publication will become pending, or how often this refusal occurs.

Regression direction: drive the actual Versions install through ARMED then refused publication admission; require UI/session state to remain reconciled with the retained worker until it succeeds/expires or is explicitly retired. Include admitted asynchronous exit, lease refusal with force-exit watchdog, late/duplicate native receipts, duplicate install refusal, page retirement, and the retained-stage control.

## Challenges that did not produce additional findings

1. Dispatch accepted before exact arming receipt: real receipt owner buffers early completion, admits only literal true dispatch and exact ARMED, fences duplicate/late results. Focused native-shell receipt tests pass; worker success is not inferred from process creation.
2. Two native workers/destination race: emitted shell and test native port refuse occupied destination and lease collision; no copying/nesting fallback. Our duplicate-worker control exit4 corroborates this. Darwin descriptor/rename semantics remain native-unexecuted.
3. Refused restart always leaves process alive: **refuted as a general claim**. EmergencyExit normally force-exits on request/fence failure/deadline. Finding requires the earlier capture refusal, before emergency admission; it does not infer failure-frequency.
4. Shared failure removes the stage so later publication is impossible: **refuted**, actual shared fail has no cleanup and executed retained-stage replay publishes it later.
5. Refused reload scheduler yields a permanently inert app: the coordinator has separate bounded native-reload/fatal paths, exact owned-abort handling and shutdown EOF backstop. No new source certainty of a harmful reachable path established in this scope.
6. Stale reload sentinel keeps Karabiner alive on real quit: old reload_guard doc/test prose suggests this, but **current root always revokes exact lease on every shutdown**, using sentinel only to label reason. Wall-clock TTL/backward clock alone does not prove missing remap revocation.
7. Manual check while paused is a bug: explicitly permitted for a direct user request; automatic due dispatch remains gated. Late results after owner stop/restart/channel change are fenced by generations; manual result intentionally survives channel changes and uses a separate transport.
8. Page close must abort native install: **refuted by explicit retained accepted-work semantics**. No cancellation claim is used for MUR-001.
9. Successful open means successful application boot: **refuted**; table names the missing post-boot proof rather than inventing it. A new rollback requirement would be a product decision, not a confirmed implementation violation here.
