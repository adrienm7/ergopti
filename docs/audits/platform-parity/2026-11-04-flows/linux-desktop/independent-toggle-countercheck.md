# Independent countercheck: Linux dark-mode toggle concurrency

Audited immutable commit: `213d65af24d2aa4845ba47743c9bab6787b61964`. Scope: candidate LDS-002 only. Production evidence was read with `git show`/`git grep` at that commit; no working driver, generated manifests or driver suites were loaded. The scratch proof was replayed successfully on 2026-11-04 with `python3 /workspace/scratch/parity-flows/linux-desktop/toggle-race.py`.

**Verdict: retain**, with medium severity and high confidence in the race, bounded by the native limits below. Suggested title: “Two overlapping Linux dark-mode activations can collapse into one toggle.” This is a successful-command lost-update issue, distinct from LDS-001's hidden command failures.

## Reachability and attempted refutations

All paths below are `static/ergopti_plus/` paths at the pinned commit.

- Shared `_shared/modules/actions/actions.toml:943–947` exposes `toggle_dark_mode` on all platforms and requires only `tool:gsettings` on Linux. Its generated catalogue metadata (`_shared/lua/actions/catalogue_data.lua:498`) has no confirmation or coalescing policy.
- A real user-assigned keyboard shortcut reaches `linux/modules/shortcuts/keyboard_shortcuts.lua:816–826` (`dispatch` → `fire`) and `:794–799` (`fire` → `Gestures.execute_action`). Under the grab, `consume` at `:841–910` admits and defers each matching event. Its `dispatched` guard at `:878–882` protects one queued callback from double execution; it is local to that invocation and does not serialize two activations or wait for their children. Generation/admission guards protect ownership and pause state, not outstanding desktop jobs.
- Independently, enabled bound gestures reach `linux/modules/gestures/manager.lua:1952–1985` (`dispatch_gesture` → `_execute_action`). Its checks cover slot assignment, pause and AI eligibility; there is no action-completion/cooldown check. A second complete gesture after the first returns is sufficient if the first child remains outstanding. The proof does not rely on key-repeat being admitted or duplicate firing of one physical event.
- `manager.lua:1934–1939` (`execute_action`) invokes `_execute_action`; `:809–814` calls `SystemActions.command_for` and then `run_background`. `run_background` at `:374–376` uses `os.execute(cmd .. " 2>/dev/null &")`. Serial Lua callbacks therefore do **not** serialize the detached shell jobs. No job ownership/lock is acquired here.
- `linux/modules/gestures/system_actions.lua:107–109` reads `gsettings get ... color-scheme`, then issues a separate derived `gsettings set`. `command_for` at `:156–164` groups the shell command; grouping is not mutual exclusion. No lock or compare-and-set surrounds the pair.

Concrete user sequence: with Linux dark mode initially `default`, bind a supported shortcut or gesture to this action and activate it twice while the first child's read/set operation remains outstanding. Both commands may read `default`; both then set `prefer-dark`. Two accepted activations leave dark mode on instead of returning to the original state. No driver concurrency, script pause, failure status or native injection is required. Native scheduling frequency is **not measured**: the deterministic barrier proves a valid interleaving, not that ordinary typing always reproduces it.

## Proof validity and limitations

The replay extracts the exact command table from the immutable Lua blob using unused dependency recorders. It then executes the extracted command in real `/bin/sh` processes against a scratch-only fake `gsettings`. Sequential control logs `get default; set prefer-dark; get prefer-dark; set default` and returns to `default`. Concurrent control logs two reads of `default`, then two writes of `prefer-dark`, with both shell exits zero. See `toggle-race.json` and `toggle-race.py`.

I checked the fake contract: its quoted GVariant string output is compatible with actual `gsettings get`; `*prefer-dark*` matches the quoted value. Set argument 4 is the intended setting value. Each fake get/set is individually consistent, and writes replace the scratch state atomically. The barrier delays independent read results until both reads have occurred, a permissible ordering of separate subprocess calls; it introduces no impossible shared Lua callback concurrency. Stronger backend serialization of each individual get/set would still permit get-A/get-B/set-A/set-B. The proof never calls real `gsettings` or touches user preferences. It does not execute the full native driver, a real GNOME/dconf session, evdev input, or desktop events.

The exact command already loses a toggle even when every command succeeds; reporting child failures alone does not repair this race. A regression should execute two admitted activations through the production dispatcher with a controlled command boundary, require both to be preserved/serialized, and retain the sequential control. A future fix must preserve nonblocking input while owning/ordering the toggle jobs.
