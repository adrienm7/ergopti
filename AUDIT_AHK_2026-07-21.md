# Adversarial audit — ErgoptiPlus Windows AHK driver (2026-07-21)

Scope: `static/ergopti_plus/windows/`. Branch `dev`, HEAD `d0a8648d1`. Suite green
**3386/3386**, encoding gate clean (956 `.ahk` files UTF-8 BOM+LF). This pass mined
11 days of real driver logs (`<ConfigDir>/autohotkey/logs/`, resolved through
`%APPDATA%\Ergopti\paths.toml`), ran loop-until-dry to a third pass, and
adversarially verified every finding with two independent lenses (code-truth and
reachability/absorption); disputed verdicts went to a tie-breaker, and the
highest-severity findings plus every internal contradiction were re-derived by hand
against source and, where measurable, against a live bench.

---

## 1. Executive summary

**52 findings confirmed** (1 high, 17 medium, 34 low), **10 claims refuted**, **3
labelled hypotheses** (no reproducible path). Verdict: the driver is **markedly
healthier than a month ago and has no open crash on the typing hot path**, but it
carries one genuine data-loss defect and a broad, consistent seam of *silent
fail-open* behaviour — config readers that treat "unreadable" as "empty", persist
failures that are swallowed, and buffer/ring desyncs that corrupt text far from
where it was typed. None of these throw; all of them read to the user as "the
driver is being flaky."

What this pass did that the prior two did not:

- **Measured G4 from the bytes.** The `07-20` UIA-probe bound + idle-gate is real
  and worked: `Tooltip.ResolvePos` day-max fell `2560 ms → 728 (07-19) → 27.9
  (07-20) → 0 slow events (07-21)`, dragging `OnChar` down with it. Re-derived
  independently, 11 of 13 figures reproduce to the byte.
- **Killed a confident false-positive by measurement.** The workflow's two Opus
  verifiers both *confirmed* that Ollama warmup's `WinHTTP Send()` blocks the
  thread on connect (would have been the only "high G4"). A standalone bench shows
  async `Open(url,true)+Send()` returns in **15 ms** against a black-hole IP — it
  does **not** block on connect. Refuted, with its sibling. (§3)
- **Settled the `/validate` confusion by probe.** On this v2.0.26 binary
  `/validate` *does* validate without executing **when the flag precedes the
  script path**, and executes the script live only when it trails it. (§3)

Most fragile zones, by confirmed density and severity:

1. **Config plumbing** — the "unreadable file = empty, then persisted" class, led
   by the one high finding (whole feature config lost on a transient boot lock).
2. **Hotstring engine ↔ preview (G5)** — the two buffers still diverge on nav-layer
   sends, Home/End, tooltip expiry, declined raw callbacks and lock/unlock.
3. **Keymap ring/emit** — the `3f9ab1a1e` dead-key ring fix left three sibling
   emit paths ungated.
4. **LLM/menu persistence** — swallowed `TOML_BatchWrite` failures desync
   memory/engine/disk with no log.

**Thinnest evidence:** G3 (races). Only one confirmed race; every other race
conclusion rests on "AHK is single-threaded + Reload is a full restart" with no
measured corroboration, because the LLM subsystem — the richest async surface — was
dormant across all 11 log days.

Each finding carries: guarantee (G1 robustness / G2 no missing output / G3 no race
/ G4 no lag / G5 tooltip truth), confidence, `file:line`, repro, root cause + why

### HIGH

#### [x] H-01 · Transiently unreadable `config.toml` at boot resets the ENTIRE feature config to defaults and persists it
`G1` · confidence: confirmed-by-reading (hand-verified) · `lib/toml/toml_config_loader.ahk:140`

- **Repro.** User has a fully-configured `config.toml`. Start the driver while the
  file is briefly held by a reader lock (OneDrive/Dropbox sync, AV real-time scan,
  backup) during the first ~200 ms of boot. `ApplyConfigToml` (`ErgoptiPlus.ahk:544`)
  calls `ReadTomlFile(config.toml)`; the catch at `toml_loader.ahk:80-89` logs one
  ERROR and **returns `""`**. `loop parse, ""` applies 0 overrides, so `Features`
  stays at `ManifestBuildFeaturesMap()` **defaults**, and the apply logs
  `SUCCESS "0 value(s)"`. The lock clears before the `-500 ms` boot timer
  (`ErgoptiPlus.ahk:752`) fires `SaveFullConfig`, which re-collects the *default*
  tree (`config_io.ahk:395 _CollectFeatureUpdates(Updates,"",Features)`, no gate)
  and `TOML_BatchWrite` now writes successfully — **overwriting the user's real
  config with defaults.**
- **Root cause.** `ReadTomlFile` collapses "unreadable" into "empty" and exposes no
  signal to later writers, unlike `ParseTomlFile`'s `_TomlReadFailures` mechanism
  that `TOML_BatchWrite` honours. `SaveFullConfig` has no guard that the boot apply
  read failed. The existing `TOML_ReadFailed` guard only protects when the file is
  *still* unreadable at write time; a lock that clears in between defeats it.
- **Why silent.** The apply logs `SUCCESS "0 value(s)"` (indistinguishable from a
  genuinely fresh config); the only trace is one easily-lost `TomlLoader` ERROR;
  the destructive `SaveFullConfig` logs nothing about a reset. The critic confirmed
  the persist path independently: the `_DriverReady`/`_LLM_Menu_Loaded` guards that
  "cleared" `SaveFullConfig` protect only the LLM/deferred-menu keys, not the core
  feature tree.
- **Fix.** Give `ApplyConfigToml` the unreadable-vs-empty distinction: read through
  a path that records a read failure (reuse `_TomlReadFailures` or set a dedicated
  `_ConfigBootReadFailed` flag), abort the apply loudly (ERROR + skip persistence)
  when an *existing* `config.toml` cannot be read, and make `SaveFullConfig` refuse
  to serialize the feature tree while that flag is set. This is the class fix — it
  also closes M-12, L-14, L-15 and L-18 below.
- **Regression test.** Force `ReadTomlFile` to fail for an existing `config.toml`
  (inject a failing read), call `ApplyConfigToml`, assert it returns a failure
  signal / sets the boot-read-failed flag, then assert a subsequent
  `SaveFullConfig()` declines to write the feature sections. No test covers the
  unreadable-yet-existing case today (`test_features_manifest.ahk` covers missing
  and empty only).

#### [x] M-01 · Nav-layer synthetic navigation/backspace is invisible to BOTH buffers — expansions backspace into wrong text
`G1` · confirmed-by-reading (hand-verified) · `lib/nav_layer_helpers.ahk:92`

Enable the Space nav layer, type `att` (tooltip offers `attention`), hold Space and
tap the Up-arrow layer key (`nav_layer.ahk` → `ActionLayer("{Up}")`), release, press
the magic key: `HSE_Buffer` still holds `att` (the synthetic `{Up}` is `SendInput`
at SendLevel 0, filtered by the watcher InputHook's `I1`, and `ActionLayer` does no
`HSE_FeedReset`), so the engine fires `attention` with `{BackSpace 4}` **at the new
cursor position**, deleting four characters of the line above. Same class:
nav-layer `{BackSpace N}` (`SC03A`) and physical Home/End/PgUp/PgDn (see M-17).
Physical arrows/Esc/Tab/Enter/mouse all reset both buffers precisely because cursor
movement invalidates the left-context invariant; the nav layer bypasses every reset
site. **Fix:** make `ActionLayer` (and the `win.ahk` `{Home}{End}` shortcuts)
declare their effect — cursor-movers call `HSE_FeedReset(true,true)+_ResetPrefixBuffer()`,
`{BackSpace N}` calls `HSE_FeedBackspace` per rep. **Test:** every `ActionLayer`
action containing a nav/`{BackSpace}` key must route through a wrapper that also
feeds HSE; behavioural: `HSE_Buffer:='att'` → layer backspace → assert `'at'`.

#### [x] M-05 · Single-owner mutex yield (`ee006d453`) kills every KLPF prefetch worker
`G2` · confirmed-by-reading (hand-verified) · `ErgoptiPlus.ahk:62`

The metrics dashboard spawns a background projection worker by re-running the entry
(`keylogger_prefetch.ahk:95` → `AutoHotkey64 /force ErgoptiPlus.ahk
--keylogger-prefetch-worker …`). The worker re-enters `ErgoptiPlus.ahk`; the
single-owner mutex block (`:20-64`, the *first* auto-execute statement) runs
**before** the `KLPF_IsWorkerInvocation()` gate at `:348`. The live driver owns

`3000 ms`, returns `WAIT_TIMEOUT`, and `ExitApp(0)`s before ever reaching its worker
main. The projection can never publish while the driver is alive; field logs show
zero projection lines in 11 days. **Root cause:** `45ed3856b`/`ee006d453` reasoned
about double-launches only; the driver *deliberately* self-spawns with `/force`

below. **Fix:** guard the mutex block with `if !KLPF_IsWorkerInvocation() { … }`
(`KLPF_IsWorkerInvocation` reads only `A_Args`, callable at line 20). **Test:**
extend `test_single_instance_mutex_first.ahk` to assert `KLPF_IsWorkerInvocation()`
precedes `CreateMutexW` in the entry source.

#### [x] M-13 · LLM menu live toggles silently desync memory/engine/disk when a config write fails
`G5` · confirmed-by-reading · `lib/config_io.ahk:467`

`SaveFullConfig()` calls `TOML_BatchWrite` and **discards its boolean return**.
`TOML_BatchWrite` returns false (no throw, no log) when `FileOpen(tmp)` yields no
handle or `FileMove` fails. The LLM live-toggle callbacks mutate `_LLM_Menu` in
memory, re-init the engine and rebuild the menu with **no Reload** — unlike the bulk
togglers (`8a84bdb49`) and gesture/metrics toggles, which reach an unconditional
Reload that self-heals from disk. So a failed persist leaves memory, engine and menu
showing a state never saved, with zero WARNING/ERROR. **Fix:** `SaveFullConfig`
returns the write result; `LLM_Menu_SaveConfig` surfaces + Reloads on failure
(mirroring `8a84bdb49`); give `TOML_BatchWrite`'s two failure branches a
`LoggerError`. Siblings: L-16 (`menu_rebuild.ahk:185`), L-17 (`menu_engine.ahk:402`).

#### [x] M-14 · `shell_runner` logs every error via `Func("LoggerError")`, which throws at runtime — all diagnostics vanish to `OutputDebug`
`G1` · confirmed-by-reading · `adapters/shell_runner.ahk:58`

`_SR_LogError` runs `LoggerFn := Func("LoggerError")`, which throws
`ValueError: Invalid base` in AHK v2 (`Func` is the native class, not a name-lookup
built-in). The throw is caught by the helper's own try and falls to `OutputDebug`
(invisible without a debugger), so **every** shell_runner error is lost. The
codebase already knows this idiom is broken — `test_feature_state_boot.ahk:53`
forbids `Func("IniCacheGet").Call` as "boot-fragile" — yet
`test_shell_runner_isolated_logger.ahk:19` *requires* `Func("LoggerError")` in the
source, string-matching it without ever invoking the helper, so the test **enshrines
the bug.** **Fix:** use `%"LoggerError"%` (verified to resolve) or call
`LoggerError(...)` directly (logger is always earlier in the include graph); rewrite
the test to actually call `_SR_LogError` with a capturing sink and assert the line
arrives. This is a corrected wrong assertion, not a weakened test.

### LOW (34) — grouped by class

Each is confirmed-by-reading (verifier verdict noted where a single verifier or
tie-breaker decided). Full repro/fix/test per finding is in the run journal; the

**G5 preview ↔ engine divergence** (buffer/marker/rule written or reset on one side
only). Class fix: derive the preview from the engine, never wipe it independently.
- `L-01` `ui/tooltip/core.ahk:122` — tooltip expiry timer wipes `_PrefixBuffer` while
  `HSE_Buffer` keeps the word; any mid-word pause >~0.55 s kills the preview for text
  the engine still expands. Remove the `_ResetPrefixBuffer()` from the timer.
- `L-02` `lib/hotstrings/hotstring_dispatch.ahk:108` — a *declined* raw callback still
  wipes the preview (its `finally` resets unconditionally). Gate on `Fired`.
- `L-03` `lib/hotstrings/hotstring_inputhook.ahk:865` — backspacing over a word
  terminator re-exposes the previous word in `HSE_Buffer` but leaves `_PrefixBuffer`
  empty (sibling of the `356ba64c0` backspace fix, at the site it missed).
- `L-04` `lib/hotstrings/hotstring_inputhook.ahk:1093` — collision tie-break written
  twice: `_PrefixCandidateBeats` duplicates `_HSE_Beats` with divergent fallbacks
  (Priority 0 vs 50, no GroupOrder/Seq). Delete the duplicate; call the engine's.
- `L-05` `lib/hotstrings/hotstrings_cache.ahk:405` — magic-key marker substituted in
  preview OUTPUT but not in engine REPLACEMENT; tooltip text can differ from emitted.
- `L-06` `modules/keymap/layout.ahk:463` (tie-break) — `_LockWorkstationEmit` resets
  the engine buffer with `IsPhysical` defaulting false, so a Win+L inside the suppress
  window no-ops the HSE reset while still wiping the preview — stale context survives
  lock/unlock and can BackSpace into unrelated text.
- `L-07` `lib/hotstrings/hotstring_inputhook.ahk:909` — dead code in the G5 zone:
  `_SuffixAfterLastBoundary` and `TooltipRearmTimer` have zero callers (also L-31).
- [x] `L-13` `lib/hotstrings/hotstring_match.ahk:39` — config-window **priority** changes

## 3. Refuted claims — do not re-raise

Each was investigated and rejected with evidence. The first two are the ones **this
pass overturned that the workflow's own verifiers had confirmed** — logged in detail
so they are not re-raised.

- **"Ollama warmup `WinHTTP Send()` blocks the thread on connect" (was proposed
  high G4, `ollama_warmup.ahk:47`) — REFUTED by measurement.** A standalone bench
  (`scratchpad/winhttp_guarded.ahk`, self-terminating, no hooks) opened
  `WinHttp.WinHttpRequest.5.1` with `Open(url, true)` + `SetTimeouts(3000,…)` and
  called `Send()` against a black-hole IP (`10.255.255.1:81`, SYN dropped). Result:
  **`Send() returned after 15 ms`** — async `Send` does **not** perform the connect
  synchronously. What blocked the *first* (unguarded) bench for >120 s was
  `WaitForResponse(0)` (0 = infinite), not `Send`. The two Opus verifiers both
  confirmed the finding on code-reading alone; the measurement refutes it. This is
  the "an adversarial verifier can be wrong in the confident direction" lesson
  (`project-perf-2026-07-21-implementation`) recurring — hold the refutation to the
  same standard, which is why it was benched, not argued.
- **"`api_remote.ahk:581` — `LLM_RemoteIsReady_Async` connect blocks the pump"
  (was proposed medium G4) — REFUTED, same mechanism, same bench.** The workflow had
  already independently refuted the third sibling (`updater/core.ahk:536`) on the
  same grounds — that verdict was correct.
- **"`/validate` doesn't exist in v2.0 / executes the script."** Both the gates
  agent's "flag only exists in v2.1-alpha, exit 2 on both" and a doc note in
  circulation are wrong. Probed on this v2.0.26 binary via `Start-Process` with a

### 4b. Proposed optimizations (offensive)

Ranked by gain × confidence. All measured against real logs or standalone benches
(`scratchpad/bench_hotpath.ahk`, `bench_menu.ahk`); micro-ones honestly labelled.

1. **Truncate the per-keystroke debug serialization** (`high` × measured) —
   `hotstring_inputhook.ahk:603/901/1133`. With debug on (the maintainer runs it:
   14k DEBUG lines/day), every keystroke pays 2-4 `Format` calls interpolating the
   *full* `_PrefixBuffer` + `HSE_Buffer` (up to 256 chars each) inside `Critical`.
   Debug-off days have **zero** slow `OnChar`; today has 84. Fix: `SubStr(buf, -24)`
   at the debug sites (the tail is all the `SearchKey` lookup uses), or gate the two
   per-keystroke sites behind a separate hotpath-trace flag. Target: constant
   ~50-char interpolations, log volume `1.8 MB → ~0.2 MB/day`. Risk: low
   (debug-only; no test pins the full serialization).
2. **Content+anchor short-circuit on redundant tooltip renders** (`medium` ×
   measured) — `ui/tooltip/core.ahk`/`helpers.ahk`. Every debounced render
   destroys+rebuilds both windows even when the row set is identical to what's on
   screen (`Present` logged slow 2780× over 11 days). Compute a cheap signature
   (`Text/TriggerLabel/ColorHex/IsDimmed/DurationSec` per row + resolved anchor);
   if identical and visible, skip teardown+Build+Present. **Not** the rejected
   window-reuse — full skip or full rebuild, no control mutation. Risk: generation
   discipline (a skipped render must not orphan the auto-hide timer; dequeue
   rebuilds must bypass the skip; position must be in the key). Target: ~0 ms for
   identical re-renders.
3. **Instrument the 2.1 s flat-submenu boot phase before touching it** (`high` ×
   measured) — `ui/menu/menu_submenus.ahk`. My benches attribute <10 % of the phase
   (registration 0.16 ms/item × ~75; TOML count-parses ~60 ms); ~1.9 s is
   unattributed. Add per-child-builder `BootProfile` sub-marks; one boot later the
   dominant term is known and the fix is a one-liner instead of a guess. Do **not**
   chunk with `SetTimer` yields — reverted at `+7969 ms`
   (`project-typing-latency-tooltip-coldstart`).
4. **Per-category prefix sub-index** (`medium` × measured) —
   `hotstring_inputhook.ahk`. Every live section toggle rebuilds the whole 6-category
   index (2999 triggers, ~7500 case variants), measured 219-297 ms per toggle. Keep
   one prebuilt sub-index per category, invalidated (generation-fenced, not
   flag-based) only when that category changes; a toggle rebuilds only its own.
   Target: typical toggle ~20-60 ms. Risk: byte-identity pinned by
   `test_prefix_index_cache_equiv.ahk` + `test_preview_matches_engine.ahk` — both
   must stay green.
5. **Hoist the per-keystroke suffix slice** (`high` confidence, `low` value) —
   `hotstring_match.ahk`. The star path allocates 2 strings per suffix probe (×≤31);
   benched 85.3 µs → 44.5 µs/keystroke by slicing/lowercasing the tail once. A
   *within-invocation* hoist (not a cross-call cache — the twice-shipped cache-drift
   mode is structurally excluded). Explicitly a micro-opt: ~0.07 ms/keystroke, far
   below the 5 ms tripwire — worth it only because the diff is tiny and this is the
   hottest code. It is **not** a fix for any `Slow` line (the bench refutes that
   attribution).

Not re-proposed (decided/forbidden): tooltip window-reuse, emoji-registration
chunking, OPT-9b end-char tail cap, process-priority changes, raising
`TOOLTIP_POSITION_CACHE_MS`.
