## New confirmed finding

### LC-001 — configuration restore reports that the app restarts when restart was refused or unavailable

Severity: medium. Confidence: high. Guarantee: G5 (truthful visible outcome). Shared with the macOS restore/reload reporting observation; root should deduplicate the user-facing TODO while retaining per-driver evidence.

The **configuration can genuinely be restored** and its pre-restore backup exists. The defect is a false restart/effective-runtime promise, not a failed byte restore and not a reason to roll back successfully restored files.

- `linux/ui/changelog/bridge.lua:620` acknowledges backup owner restore.
- `:628–630` notices absent restart hook or `restart('configuration restored')~=true`, but only writes a log error.
- `:632` returns exactly the same `{action='restore_progress',phase='restored',backup_path=...}` as the successful restart path; no restarted flag/reason/notice.
- `_shared/ui/changelog/script.js:1307` maps restored to `changelog_window.restore_done`.
- `_shared/data/locales/en.json:201` says “Configuration restored: ErgoptiPlus restarts on it.” French `fr.json:201` makes the same promise. The old process can still be running old in-memory preferences after a refused restart.

Executed reproduction: `probe-restore-restart.lua` imports the real Linux changelog bridge through the repository's authenticated document fixture and its existing effect-isolated backup/restart harness. The original fixture's successful backup restore is retained; restart is changed to return false, then removed. Both cases publish phase=restored and no restart-status/reason metadata. Output retained in `probe-restore-restart.log`:

```text
refused restart_calls=1 answer={"action":"restore_progress","backup_path":"/cfg/backups/pre-restore-y","phase":"restored"}
missing restart_calls=0 answer={"action":"restore_progress","backup_path":"/cfg/backups/pre-restore-y","phase":"restored"}
```

No real user files or native process restart are involved in this reporting reproduction. Real backup bytes and native install ownership are separately exercised by existing scratch fixtures below; their success is not inferred from this model.

Other OS: macOS dedicated lifecycle audit found the analogous reload-reporting path. Windows `windows/ui/changelog/init.ahk:987–1084` has explicit reload-handoff admission/refusal reporting; same field/phase wording cannot be assumed equivalent. This audit does not claim an end-to-end Windows runtime comparison.

Recommended correction: distinguish “configuration restored, restart still required” from “restart handoff accepted”, render a visible translated outcome/notice and retain the pre-restore path. Add false/missing/throwing restart tests plus successful handoff; never tell the user that restored disk bytes were rolled back if they were not.
