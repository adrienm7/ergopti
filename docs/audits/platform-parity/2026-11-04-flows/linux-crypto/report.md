## Confirmed findings

### LCR-001 — literal typed text beginning with the cipher marker bypasses encryption and can block decryption migration

Severity **medium**; confidence **high**. Guarantee **G2** applies to the subsequent conversion failure. **Additional confidentiality impact, distinct from G1–G5:** encryption-enabled SQL retains the literal protected raw text for this input. No G5 preview claim is invented.

`_shared/lua/keystats/text_crypto.lua:102–104` calls any string starting `ergopti-enc-v1:` encrypted. `_shared/lua/keystats/text_cipher.lua:119–124` returns such input untouched before checking native availability or deriving/encrypting a key. That idempotence rule is applied to **new raw input**, not only to a trusted already-stored envelope: `linux/modules/keystats/sqlite_writer.lua:668–671` hands `ev.text` directly to it, then renders the returned value into the raw SQL text column at `:692`.

Reproduction with real policy, actual EVP AES, actual native SHA256 and the original Linux SQL composer:

1. Build the shared cipher with a synthetic fixed key and the genuine Linux EVP/Base64 ports; enable it. Ordinary control text encrypts and round-trips.
2. Supply raw text `ergopti-enc-v1:SYNTHETIC_CLEAR_CANARY`. Encryption returns exactly those clear bytes without invoking AES; the original Linux typing SQL composer preserves them in its SQL value.
3. Supply raw text `ergopti-enc-v1:` + 32 zero hex characters + `:SYNTHETIC_CLEAR_CANARY`. It also bypasses AES. Reading through the cipher cannot decode the literal payload and returns empty.
4. Feed that second genuine raw-text result to the original shared migration runner in decrypt mode. It aborts at the first row before applying any batch. Thus switching encryption off can leave this pass blocked by text the user literally typed, without any corrupt ciphertext or wrong key.

`probes/marker-collision.lua` passes; `logs/marker-collision.log` and `logs/marker-{1,2}.sql` retain exact synthetic results. The probe extracts the original `_compose_raw` closure from `insert_typing_events`; it does not replace its logic. Key derivation is a synthetic-key port; native AES/digest/Base64, shared policy, SQL rendering and migration runner are genuine. No SQLite COMMIT is claimed from this SQL-bound proof. The verified source path demonstrates where those exact accepted values enter normal writes. Linux's current dashboard reads aggregates; this report does **not** invent a raw-text dashboard display path. The actual migration consequence is separately executed.

Why current tests miss it: they prove idempotence by feeding a previously produced genuine envelope back into encrypt; they do not distinguish that provenance from a new literal typing string that merely begins with the marker. A stricter syntax check alone is insufficient for a genuine-envelope-looking literal. Preserve raw-input provenance or use a reversible escaping/typed storage protocol while maintaining already-stored migration compatibility.

Counterparts: macOS uses the same shared core and its independent scope probe joins the actual Mac writer. Windows `keystats_text_cipher.ahk:170–173,221` has the same prefix-based encryption bypass by source inspection. Windows malformed-envelope decryption returns empty; the Lua core returns unchanged text when unwrap cannot parse the IV. Those decoder details do not excuse the common raw-input collision. Deduplicate the common root while retaining per-OS writer evidence. Native macOS/Windows execution is not claimed here.

Root-cause regression: encryption-enabled raw capture must round-trip literal malformed markers, valid-IV-looking strings and byte-identical copies of genuine envelopes **as literal input**; the raw SQL image must not expose their clear protected content. Genuine stored-envelope replay/migration must remain idempotent through an explicit trusted boundary. Disabling/restarting migration must not stall or replace literals with empty/different text.

### LCR-002 — secret-tool store can publish success after its stdin write explicitly failed

Severity **medium**; confidence **high**. Guarantee **G2**. This is credential integrity/availability failure; the probe does not show disclosure of a real credential.

`linux/modules/llm/api_token_store.lua:91–92` ignores both the return value of `pipe:write(input)` and the pipe close result. It reads the helper's separate status file and returns it at `:93–94`. `SECRET_TOOL.store:122–127` accepts status 0 as complete key storage even when stdin transport explicitly returned failure. API entries then publish the reference normally (`api_entries.lua:361–364,403–424`). A missing transport receipt is not proof that all key bytes reached the secret store.

Executed public-flow reproduction (`probes/secret-tool-short-write.lua`):

- A disposable executable models secret-tool store/lookup/clear against one scratch synthetic file. No Secret Service or desktop prompt is invoked.
- The original `io.popen` creates the real shell pipe. Its recording write boundary forwards only `SYN`, then returns `nil, 'controlled short write'`; the child consumes EOF and exits 0.
- Public `ApiEntries.add` nevertheless succeeds, writes only a secret-service reference to its genuine private metadata file, and keeps the complete synthetic key in RAM.
- Reloading that same metadata through the original entries owner resolves only `SYN`: the backend stored 3 of 27 synthetic bytes. The file/reference publication and the RAM secret disagree. All scratch files/executable are removed.

This is a **fault-injected pipe write refusal**, not a claim that a live secret service actually truncated a key in this session. The private metadata writer, entry/token owners, real shell child and helper status file execute; the controlled native I/O boundary exhibits the ignored acknowledgement. Existing tests only cover full successful stdin delivery and helper exit refusal, so both pass while this failure is accepted. A transient write failure can masquerade as a valid saved credential until a restart/reload or remote authentication attempt.

Counterparts: macOS uses asynchronous signed-launcher Keychain ownership and completion/deadline receipts (`macos/modules/llm/api_token_crypto.lua`), not this shell pipe. Windows DPAPI returns a native protected-blob acknowledgement (`windows/modules/llm/api_token_crypto.ahk:66–85`) and has no secret-tool stdin. Those are source-derived mechanism comparisons; the dedicated OS scopes own their native fault qualification.

Root-cause regression: when key-input write or native pipe completion refuses/throws after partial/full input, no successful secret reference or successful metadata save may be announced from the helper exit code alone. Preserve previous metadata/credential, retire any newly created orphan reference only with its own acknowledged ownership, and test exact complete bytes on a successful store followed by reload. Do not weaken no-plaintext-fallback or pass key bytes in command arguments.

## Two dry passes and rejected hypotheses

`pass-ledger.md` records initial confirmed roots, then pass 1 and pass 2, each zero new confirmed roots. Broader consequences of LCR-001 (migration stall) were retained under its original ID rather than counted again.

- Native AES short/update/final refusal does **not** publish intermediate output: context-owned private buffer, native final success and cleanup precede returned Lua bytes. Existing ABI tests and actual wrong-key/truncation controls pass.
- Canonical Base64 does **not** accept arbitrary printable bytes: re-encoding exact output checks alphabet, padding and unused bits. Executed malformed controls refuse.
- A mere Secret Service refusal does **not** write a plaintext fallback: existing add/migration tests verify original file or failed save. LCR-002 is narrower: child status 0 does not prove stdin accepted.
- Canceled access-token requests do **not** automatically send when token later arrives: existing request ownership/cancellation cases pass. Scheduler `after()` returns an explicit unarmed handle on native allocation/start failure; no nil-handle production path was established from test-double speculation.
- A raw marker literal is **not** a trusted encrypted value: executed original SQL composition distinguishes ordinary encryption from the bypass. Genuine-envelope idempotence tests alone do not refute LCR-001.
- **Unauthenticated CBC integrity limit, not a newly asserted authentication bug:** genuine native ciphertext decrypted under a one-bit-changed IV passes padding and changes the first plaintext byte (`A` → `@`). The v1 format has no MAC/tag and no explicit authenticity promise was found. This establishes lack of corruption authenticity, not another quota-driven finding or an invented G guarantee. Record as a design qualification; no hostile live file/service touched.

## Memory and G4 provenance

Memory watch-list: shared cipher retains one derived Lua hex key plus failure latch per session; EVP buffers/context are cleansed/freed per call and actual native controls pass. API entries retain decrypted keys in RAM for requests; `_access` uses provider + full key as cache identity and retains access slots until reset/process exit (`api_remote.lua:397–400,1558`), so removed/replaced keys can have residual process-memory cache entries. This is a retention watch-list, not a measured unbounded leak finding or a claim of process-memory erasure. No real user memory snapshot was taken.

G4: no hot-path profile/log/latency measurement was collected. Synchronous keyring I/O and cached derivation cost are source-derived constraints; historic comments about ~0.5s derivation/~0.25s RSA are **not measurements from this audit**. No G4 finding is asserted. Synthetic 64KiB byte controls test correctness, not desktop performance.
