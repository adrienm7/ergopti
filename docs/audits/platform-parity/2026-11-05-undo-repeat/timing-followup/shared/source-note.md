# Repeat timing — contradictory shared follow-up

Audited commit: `b17e47ed3bb92c106703d3e3482b3c2973f5bc1e`. No production or registered test changes. This note establishes an observed policy difference and its evidence limits; it does not invent a common repeat-delay requirement or a second copy of a peer-owned finding.

The registered delay and repeat fallback must not be conflated. The shared manifest declares `hotstrings.repeat_key_enabled` as a Boolean with no repeat-specific delay parameter. Registered correction rows have separate section timing; they are not the transient doubling rule.

## Effective macOS values

The shipped `magickey.toml` has `[_meta].delay = 2.0`. This agrees with the raw Keymap fallback but is independently present in canonical source data. `menu_state.lua` synchronizes `STAR_TRIGGER` through its `magickey` category mapping and `hotstrings_config.resolve`, while retaining the documented legacy `state.delays` override priority. Therefore 2 seconds is the ordinary shipped category value, not a claim that user overrides cannot change it.

The current shared timing registry declares multiplier **2** and carry **300 milliseconds**. The multiplier widens the allowed window when the expander itself uses Shift/Alt/AltGr, or when the preceding complex key is within the carry window. For an otherwise unconfigured repeat, a plain magic key has a 2-second window; a complex expander can have 4 seconds; a complex preceding character alone does not stretch a 2.5-second pause because it lies outside the 300-millisecond carry. Idle reset is an independent limit: meaningful long-pause public reproductions must disable it or choose an interval below its effective threshold.

`timing-model.lua` executes the actual shared TOML codec, manifest view, delay resolver, complex multiplier and registered gate under Lua 5.4 and LuaJIT. It authenticates the shipped 0.75-second base, 2-second category delay and registry values, then checks nine factor/deadline controls plus unlimited timing: **21 assertions** each. These are actual shared-helper observations. They do not execute the macOS public repeat gate, and they do not translate or execute AHK. In particular, the macOS repeat caller uses its direct seconds comparison, whereas this shared registered gate quantizes its deadline to milliseconds.

## What is explicitly intentional, and what remains unresolved

- The maintainer explicitly excludes repeat doubling from preview because it would be ubiquitous noise. That says nothing about whether an unadvertised repeat should expire.
- Routed memory explicitly calls Windows repeat doubling “ungated.” This is evidence that the current property was known, not an explicit cross-OS decision requiring all drivers to be ungated.
- macOS source explicitly intends validated star mappings to bypass their regular speed gate, to avoid fallback changing the requested expansion. This is a local stated rationale and can be documented as such.
- No inspected manifest, routed maintainer decision, corpus description or scoped repeat test establishes a common product requirement that transient repeat must be timed or untimed. Label the repeat-window difference **observed, intention unresolved**, rather than manufacturing a G2/G5 violation or declaring one OS wrong.
- The time-gate corpus checks registered delay admission, not the presence or absence of a public caller gate around transient repeat. The repeat corpus checks one pure repeat decision with no timestamp input. Neither certifies timing parity.

A parity follow-up should choose and document a repeat timing contract across all three systems, covering no mapping, an expired registered winner, a disabled mapping, a final no-op, zero/unlimited timing, exact/after deadline, complex expander/reference/carry and independent idle reset. Preserve focus/privacy/rebuild guards. This is a review/decision TODO, not authorization to remove an existing guard as an audit fix.

## Stale-memory counterexample and historical limits

`docs/memory/text-input-and-config.md` says macOS alone widens complex-key windows. Current code contradicts that broad historical comparison: Windows `HSE_ComplexDelayMultiplier`, Linux `ExpansionDelay.allows` and the shared timing registry all implement widening for eligible registered mappings. Cite current code for that behavior. This does not make Windows/Linux transient repeat timed: no positive delay is passed for those fallback specs/results.

A bounded blame check reaches the shallow repository boundary `ae77ad5` for all three relevant constructions. It cannot identify their original introducing decision. No historical intent is inferred from those boundary records.

No latency, memory, native receiving, AHK runtime or live keyboard claim is made. Source hashes and the exact helper outputs are retained alongside this note. Earlier scoped artifacts and the frozen metadata implementation are unchanged.
