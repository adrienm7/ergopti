# macOS secret storage, encryption and credential persistence: flow audit

Audited commit: `213d65af24d2aa4845ba47743c9bab6787b61964`. Scope: remote API Keychain persistence/read/delete, local-server credential replacement, HuggingFace login secret transport/storage, typed-text cipher/migration, and the bundled Encryptor source/launch flow. Read-only audit; no production/test edits, commits, user Keychain access, user clipboard, user files or external service requests. Fixtures and generated evidence remain under this scratch directory; the OpenSSL probe creates and removes its own private temporary fixture directory.

## Confirmed findings

### MCR-001 — Encryptor destroys a pre-existing overwrite destination on decryption failure

Severity **high**, confidence **high** for the reproduced source behavior. Reviewed criterion: failure-safe replacement/data integrity, outside G1–G5. Overwrite was explicitly approved and failure is reported; preservation-on-failure atomicity was not found as an explicit product promise. Native compiled-script equivalence remains unqualified.

Entry: drag-and-drop/open handler or file picker → `Encryptor.app/.../Scripts/main.applescript:process_file` → existing destination overwrite question → hidden password → direct OpenSSL `-out <dest>` → error cleanup `rm -f <dest>`. Both encryption/decryption commands at `:305–314` target the final path directly; the catch at `:321–326` unconditionally deletes that path, with no staged-output receipt or distinction between a newly created output and the user's pre-existing file.

Executed safe repro (`probes/encryptor-openssl.py`, `logs/encryptor-openssl.txt`): create an encrypted synthetic file using the exact source command and correct password; pre-populate the decrypt destination with a different valuable sentinel; execute exact decrypt command with a wrong password. OpenSSL exits 1 and the former destination bytes are already replaced; executing the source's exact failure cleanup removes the destination altogether. Correct-password control exits 0 and round-trips exactly. Only private temporary fixture files were touched; that directory is removed afterward.

Reachable user example: Encryptor keeps the original clear file on encryption; dropping its .enc later proposes overwriting that original. Accept overwrite but mistype the password: the error alert appears after the original destination has been removed. The encrypted source survives, but an existing destination is not necessarily the same content as the encrypted source and need not be recoverable from it. This is independent of whether AES-CBC can detect every corruption.

Why hidden: failure is loud, but the alert says decryption failed; it does not disclose that a former destination was destroyed. Existing `test-encryptor-launch.cjs` covers icon/process replacement, not file conversion or wrong-password overwrite.

Regression: use the actual conversion owner with a pre-existing destination, wrong password/corrupted input, subprocess refusal and correct-password control. Preserve original destination byte-for-byte on every refused conversion; publish a successfully completed staged output only after acknowledgement. A cleanup may delete only the exact newly owned stage. Windows/Linux have no bundled counterpart here (known feature gap), so no claim of an equivalent file workflow on them.

### MCR-002 — Encryptor puts the hidden password into the shell command arguments

Severity **medium**, confidence **high** for the transport mechanism. **Confidentiality finding; no invented G-code.**

The hidden-answer dialog protects the UI presentation, but the actual commands use `-pass pass:` concatenated with the quoted password (`main.applescript:308,314`), then pass the whole string to `do shell script` (`:318`). Shell quoting prevents metacharacter interpretation; it does not make an argument private.

Executed safe primitive evidence: the OpenSSL probe uses a synthetic password and observes that sentinel in its own `/bin/sh -c` process arguments on Linux while the operation runs. It **did not observe** the sentinel in the OpenSSL child's arguments in this run, so this report does not claim a measured child-argv exposure or measured macOS `ps` visibility. The shell-command disclosure is sufficient and source-derived on Mac; platform process-inspection permissions determine which local observers can read it.

This differs from explicit protections elsewhere: shared `keystats/text_crypto.lua:derive_key_command` refuses `pass:<secret>` for this very reason, and macOS typed-text key material/plaintext crosses `ShellRunner.exec_private_stdin`. No Encryptor rationale authorizing password-in-argv was found. Its exact local attacker/argument-confidentiality threat model is undocumented; do not conflate this with the deliberately weaker hardware-derived metrics threat model.

Regression: capture the actual native shell/task arguments with a sentinel password and assert zero occurrence, while a private pipe/file-descriptor input delivers exact password bytes; preserve quoting, cancellation and partial-output controls. Protecting process arguments is distinct from changing the encryption algorithm. No Windows/Linux bundled Encryptor equivalent is claimed.

### MCR-003 — Raw typed text beginning with the envelope marker bypasses SQL encryption

Severity **medium**, confidence **high**. **Confidentiality root shared across OSes**, distinct from previously tracked plaintext JSONL journal exposure.

Actual raw ingress: `macos/modules/keystats/sqlite_writer.lua:_builders.typing :520` sends `e.text` directly to the actual macOS TextCipher. Shared `keystats/text_cipher.lua:124` assumes any `TextCrypto.is_encrypted(plaintext)` is already sealed and returns it unchanged. Shared `text_crypto.lua:is_encrypted` checks only prefix `ergopti-enc-v1:`; it does not establish provenance. No user-facing reservation/escaping contract for literal typed text beginning with that marker was located. The deliberate “do not double-wrap stored envelopes” policy does not prove a raw user-content value is a stored envelope.

Executed probe `probes/cipher-prefix.lua`: actual macOS TextCipher + actual SQL writer/Query renderer, recording native Shell/hash ports, no database. Ordinary raw text is absent from SQL and uses two encryption primitive calls (text + event JSON). `ergopti-enc-v1:SENTINEL-PRIVATE-CONTENT` is retained literally in the SQL text column and uses only one primitive call (event JSON). An authentic-envelope-lookalike raw string is likewise retained, then the reader treats it as ciphertext and yields different content through the recording primitive. The malformed prefix reads back unchanged because unwrap fails and shared decrypt returns the original value. Log: `logs/cipher-prefix.txt`.

Migration cannot repair the ambiguity automatically: its marker-based `needs_conversion` treats the same raw prefix as already converted. Existing double-wrap regression verifies a genuinely generated envelope, not raw content colliding with its syntax. Event JSON remains separately encrypted; this is specifically the text column's protection, not an assertion every SQL field becomes clear.

Windows counterpart independently source-traced: `keystats_text_cipher.ahk:KL_Enc_Encrypt` has the same early return; raw `KL_BuildInsertTyping` supplies event text. Linux uses the same shared policy and raw SQL ingress; its agent additionally ran native EVP. Windows malformed-prefix decrypt differs (empty result/migration refusal), while shared Lua decrypt returns the malformed value. **One shared admission root, multiple OS manifestations**; root deduplication is required.

Regression: actual raw typing ingress for ordinary text, malformed reserved prefix, and a valid-envelope-shaped raw literal; all nonempty raw inputs must be sealed and read back exactly. Preserve idempotent migration of actual stored envelopes using explicit provenance/column state rather than text content alone. Guarantees are empty here rather than inventing an availability guarantee for a confidentiality defect.

### MCR-004 — HuggingFace login embeds the API credential in bash argv

Severity **medium**, confidence **high**. **Confidentiality finding; no invented G-code.**

Normal MLX model authentication entry → HF token prompt/read seed → `_process_hf_token` → actual flow provenance/adoption → `login_script` → native task. At `ui/menu/menu_llm/models_manager_mlx_hf.lua:1072–1085` the token is escaped into a Python string **inside** a shell script; `:1206–1213` passes that script as `/bin/bash` argument `-c`. The token thus exists in the native argv before any API validation, independent of eventual Python/HTTP outcome.

Executed `probes/hf-secret-argv.lua`: load the actual mixin and real direct-flow business path; provide a recording TaskLifecycle native acquisition boundary and refuse start. Actual acquired executable is `/bin/bash`, argv[1] is `-c`, and argv[2] contains the synthetic `hf_...` sentinel. No process, network request, file write, clipboard or Keychain effect occurs. Log: `logs/hf-secret-argv.txt`. This proves arguments handed to the native constructor; it is not a live Mac process-inspection measurement.

The later native HF SDK token file and optional git credential helper do not excuse argv disclosure. Those stores are deliberate compatibility behavior (see differences table); the standard remote API path instead uses a signed launcher with private stdin. HF ownership tests exercise pause/construction/teardown but do not assert that credential bytes are absent from argv.

Regression: invoke the actual mixin through prompt and direct login with recording native task arguments/stdin. Credential sentinel must be absent from command arguments and logging and delivered only through a private, bounded byte channel. Preserve the validated token file/optional git helper behavior separately. Windows/Linux equivalents of this particular macOS MLX HF login mixin were not found; this is not a claim those OSes lack all HuggingFace authentication mechanisms.

### MCR-005 — Failed API token replacement rolls metadata back to a Keychain account already overwritten with the new secret

Severity **high**, confidence **high**. G3: mutable secret publication is outside the compensating metadata transaction.

Reachable entry: `local_server_panel.lua:294` edits an existing local server's token → `api_panel.apply_local_server` retains `existing.id` at `:1097`, stages the new token, then persists at `:1140`. The coordinator builds encrypt jobs under that same id (`modules/llm/init.lua:1008–1017`) and invokes TokenCrypto at `:1077`. The signed worker `KeychainTokenWorker.swift:SystemKeychainTokenStore.write` uses `SecItemUpdate` on service/account; success replaces the old secret **before** final settings publication.

Only metadata is compensated: `write_combined_state` restores its prior combined settings when readback fails (`init.lua:566–582`), and the panel restores prior runtime entries at `api_panel.lua:1156–1164`. Both old entries still contain `keychain:<same id>`, which now resolves to the **new** secret. Pending-delete cleanup avoids deleting referenced accounts; it cannot restore the overwritten old bytes.

Executed `probes/api-replacement-rollback.lua`: load an existing valid `local-omlx` combined entry and synthetic OLD secret; edit the same entry token to NEW; run actual coordinator + actual TokenCrypto with in-memory native helper/SecItem and settings effects; corrupt the final combined-settings readback using the original fixture's fault seam. Result is `settings_readback_failed`, `durable=false`; old metadata/reference is restored, native write count is one, and the referenced account contains NEW rather than OLD. No actual Keychain access. Log: `logs/api-replacement-rollback.txt`.

Why hidden: exact metadata readback and rollback tests pass because they do not retain a separate native old-secret store when replacing an already persisted account. A reported refused edit can therefore change authentication anyway and discard the previous credential. Natural completion/cancellation fencing alone cannot compensate an in-place mutable secret update.

Comparator: Linux `api_entries.lua:350–364` stores a **fresh revision** for a changed key, publishes its file, then retires old refs only after ACK (`:403–424`); `api_token_store.lua` explicitly documents this reason. Windows DPAPI keeps ciphertext in the settings image itself, so this separate mutable account overwrite is not its mechanism. Linux's independent backend-preference ACK policy explicitly leaves a newly saved entry visible on backend refusal; macOS instead advertises rollback of the entry, which is what this finding contradicts.

Regression: create an existing persisted credential; replace its token; refuse final publication/readback, supersede, time out and cancel after native mutation; assert **both metadata and the secret reachable through the retained reference** remain the prior pair, or report a truthful explicit committed-new state. Use fresh immutable secret revisions until metadata commits, then retire the old one. Do not delete the old account pre-publication.

### MCR-006 — A refused migration slice timer is reported as a running migration with no scheduled work

Severity **medium**, confidence **high**. G2: owner acknowledges a pass that cannot progress or complete.

Entry: metrics encryption toggle (`menu_metrics.lua:499`) or keystats posture resume (`modules/keystats/init.lua:1182`) → actual macOS migration wrapper → shared migration driver. `text_migration_driver.lua:88–89` retains only the first return from `scheduler.after`, discarding the explicit committed boolean. `start :111–115` returns true regardless. Actual macOS `TimerScheduler.after :241–254` returns `(handle,false)` on native start/refused running-state/early-delivery failure; such a handle is inert. Same ignored result applies to later slice rearming.

Executed actual macOS wrapper/shared driver+runner+cipher/SQL modules and actual TimerScheduler with recording native hs.timer and in-memory data ports (`probes/migration-scheduler.lua`). Refused acquisition returns a handle with `committed=false`: `start_for_posture(true)` reports true, `is_running()` stays true, committed timers = zero, rewritten rows = zero. Healthy committed-timer control rewrites the one fixture row and ends normally. No native timer/database. Log: `logs/migration-scheduler.txt`.

The scheduler may log the native failure, so this report does **not** claim total absence of diagnostics. The missing receipt is at the migration owner: it neither rejects start nor settles its running/progress state, and existing history stays in the old posture indefinitely. Source comments promise a pass is in flight on true; migration tests use a healthy scheduler and remain green.

Comparator: Linux instantiates the same shared surface **without a scheduler**, pumping from its daemon tick; this ignored acquisition ACK is not exercised there. Windows has a separate migration owner. Share the root fix where appropriate but do not assert the same native timer defect occurs on every OS.

Regression: actual wrapper over TimerScheduler start false/nil/throw and rollback debt; assert no successful pass/running state without an admitted slice, and truthful failure/retry at a later slice refusal. Preserve cursor-after-apply discipline and exact native cleanup ownership.

## Refuted hypotheses and deliberate limitations

- **Metrics menu encryption failure must leave runtime toggled:** callback-local reading suggested it, but actual `menu/init.lua:744–765` binds PreferencesTransaction rollback and `sync_state_to_modules(snapshot)`; `preferences_transaction.lua:100–111` restores state/runtime on refusal. No new callback-local toggle bug is filed without defeating that actual caller chain.
- **A refused timer stop must execute a stale migration slice:** actual TimerScheduler.cancel (`:349–365`) sets `handle.committed=false` **before** native stop; its wrapper (`:195–211`) uses uncommitted delivery only for cleanup. It also retains cleanup debt. Client handle loss is not proof of a stale business callback. MCR-006 instead concerns acquisition ACK, proved separately.
- **Keychain mutation cancellation is equivalent to a synchronous kill:** `api_token_crypto.lua:180–186,259–264` expressly waits for natural completion after a write/delete is dispatched to securityd; late mutation cannot be ruled out by killing the helper. Timeout/cancel suppresses logical delivery while retaining native ownership. Existing cancellation/deadline fixtures support that mechanism; native securityd latency is unmeasured.
- **Opaque references may name any account:** coordinator validation (`llm/init.lua:475–480`) requires exact `keychain:<entry.id>` and rejects another account, while Swift bounds account size/NUL and validates token byte input. That protects references; it does not protect MCR-005's mutable same-account old value.
- **Wrong-key migration must erase rows:** shared runner `convert_value` refuses empty failed decrypt, prepares the whole batch before apply, and advances cursor only after apply ACK (`text_migration_runner.lua:145–164,235–264`). Twenty migration tests pass. No new wrong-key destructive rewrite was established.
- **All credentials use the same storage:** remote API Keychain, native HF SDK token file, optional git helper, and clear proxy preferences have distinct contracts. Existing explicit proxy-cleartext decision is preserved, not relabelled a new secret-store parity defect.
- **AES-CBC implies integrity/authentication:** real scratch OpenSSL control flips an early ciphertext bit and decrypts to changed bytes with exit 0. This is an evidenced **unauthenticated format limitation**, not a new finding based on an invented authentication promise. The hardware-derived text codec similarly carries a modifiable IV without MAC/tag. Integrity/authenticity intent is undocumented; root may make a separate design/TODO decision. MCR-001 remains independent: detectable decryption failures still must not destroy an old destination.
- **Encryptor compiled runtime verified:** no. `.applescript` is the audited source; native `osacompile`/packaged droplet execution is unavailable. Existing TODO336 and `tools/dev/collect-macos-field-report.sh:263–277` already require native recompilation. This report does not count that known delivery boundary as a new defect or assert a stale .scpt matches source.
