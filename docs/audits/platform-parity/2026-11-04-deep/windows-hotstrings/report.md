# Windows × hotstrings, dynamic and programmable sources: deep audit

Audited SHA: `89b0b774c8c960c7ad458ac3cb98d5c97598e518`.
Audit date: 2026-11-04. Scope: Windows production hotstring registration, dynamic dates/personal prefixes and programmable-source ownership, plus the directly relevant Lua equivalents. Audit only: no repository edits, commit, branch change or push.

## Result and evidence boundary

One new actionable defect is confirmed by production state transitions: repairing a refused programmable source through the actual Reload menu command leaves callback admission disabled while removing its problem indicator (WH-001). Native execution was unavailable; this is a high-confidence source finding with an unexecuted standalone AHK policy reproduction, not a claimed live Windows reproduction.

This is bounded coverage of this OS/module, not proof of exhaustive product parity or of all possible text-editor behavior. The prior audit's date vocabulary, phone trigger and international phone-output differences are carried forward below, not counted again as new findings.

## WH-001 — repaired source remains disabled after Reload removes its problem

- Severity: medium; confidence: high. Guarantee: G2 (no silent missing output).
- Root cause: `RefuseSource` sets `this.enabled := false` (`_shared/modules/hotstrings/user_code.ahk:180-183`). A later successful owner `Reload` sets entries/source/ready only (:172-175), preserving false. The production reload completion (`windows/modules/dynamic_hotstrings/user_code.ahk:284-289`) calls only that method and clears `_UserHotstringsProblem`. `Find` immediately returns false for `!this.enabled` (:203-205).
- Reachability: the menu's actual `RELOAD_USER_HOTSTRING_SOURCE` command is bound directly to `UserHotstringsReload` (`windows/ui/menu/menu_hotstrings.ahk:1588`), with no intervening enable reconciliation.
- User reproduction: enable programmable hotstrings while source is missing, unreadable, invalid or its factory throws; leave the configured switch on. Create/repair the source to publish the clock example, then click Reload source. Wait for loader completion. Problem suffix disappears and the admitted metadata count becomes nonzero, but `@clock` + magic key never invokes its callback. Switch off/on (or explicit `UserHotstringsSetEnabled(true)`) restores operation.
- Silent failure: after repair, metadata is reported published and the source problem is cleared; disabled `Find` produces no callback ticket and no new refusal diagnostic. This is distinguishable from the initial correctly reported source failure.
- Other OS equivalent: shared Lua driver `user_code_driver.lua:194` explicitly combines `_owner.reload(rules, receipt)` with `_owner.set_enabled(_desired_enabled)`, then sets `_active_enabled`. Its successful reload restores desired admission. This is actual implementation drift, not an OS constraint.
- Reproduction artifact: `recovery-repro.ahk` invokes the actual shared Windows policy class and proves the state sequence without replicating its implementation. It has **not been executed** here because neither AutoHotkey nor Wine is installed. The public UI/worker sequence above remains a native Windows integration check to add.
- Regression test needed: use the real source loader and actual Reload command: desired enabled -> real source failure -> repair -> reload -> await completion -> assert enabled/ready/problem/count, static preview and a callback request. Repeat for missing file and throwing factory; also assert reloading while desired off does not enable callbacks. Reconcile admission with the current effective desired config, not unconditional true.
