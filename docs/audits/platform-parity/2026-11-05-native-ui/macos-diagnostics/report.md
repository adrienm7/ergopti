## Canary proof and raw-local-policy adjudication

Exact command:

```sh
/workspace/scratch/parity-toolchain/ci-bin/lua /workspace/scratch/parity-native-ui/macos-diagnostics/probes/crash-canary.lua /workspace/worktrees/parity-2026-11-05/macos-webview /workspace/scratch/parity-native-ui/macos-diagnostics
```

The root and artifact destination are explicit CLI arguments. `logs/crash-canary.log`, `logs/finalA-crash-canary.log` and `logs/finalB-crash-canary.log` independently show these assertions:

- Actual macOS `CrashReporter.report` → actual `save` → actual shared `CrashReport.build/encode` sends a recognized synthetic `sk-` credential canary and private account/path to the filesystem port. Linux libuv exclusively creates, writes and closes the supplied bytes; a subsequent independent file read finds both canaries. The generated file is removed. This establishes the business payload and real Linux persistence, not Darwin hard-link/lock/symlink qualification.
- The real canonical `Logger.redact_message` removes the same token/account. The normal logged control line is redacted. A failed write port returning false and one throwing both cause actual `Reporter.save` to return nil. The probe does not make “pcall succeeded” stand in for persistence.
- Actual shared `Share.document` excludes synthetic raw issue/path/unknown-field canaries. Actual `DayLog.prepare/file` removes canaries from both preview and retained attachment. `DayLog.file` refuses another snapshot and a discarded slot. All input is synthetic; real user files/logs were not read.

**Why this is not a confirmed leak finding:** Windows explicitly documents the policy in `windows/modules/diagnostics/crash_reporter.ahk`: “Full detail locally: the error, its stack, the log tail and the window context are kept whole” and “whatever is copied, saved for GitHub or sent is redacted at that boundary”; `CrashReport_Build` says “nothing is redacted here, the report stays on this machine.” macOS uses the shared local record as reference and has the same separate approved-sharing boundary. Linux `modules/diagnostics/crash_reporter.lua:238-270` instead captures an admitted sink redactor and redacts before opening/writing. That is a real asymmetry, but not evidence that all local reports must follow Linux policy.

macOS's own comments at `crash_reporter.lua:8-15,205-209` claim the report never contains personal data; the synthetic proof falsifies that categorical claim even when the ordinary log sink masks the same value. The report has raw err/stack/config fields directly, independently of prior logger/ring or metrics plaintext retention. Record this as a contract/documentation inconsistency and **unknown macOS policy intent**, with no high data-exposure severity assigned and no MDG ID. It is not an automatic-upload claim. Future policy work should reconcile the comment or add an admitted redaction owner and regression asserting the agreed raw-versus-sanitized local boundary.
