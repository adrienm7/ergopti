Audited SHA: `213d65af24d2aa4845ba47743c9bab6787b61964`. Date: 2026-11-04. Scope: Linux configuration persistence, canonical schema migration, legacy settings import, explicit unused-key cleanup, paths/settings ownership and restore/clear transactions. Production and repository tests were read-only; evidence is under this directory. Source paths below are relative to `static/ergopti_plus/` unless stated otherwise.

Two confirmed persistence defects were reproduced through actual production owners. LCF-002 is the Linux manifestation of the macOS agent's MCF-001 split-commit root and must be deduplicated in the integrated TODO. ## Confirmed findings

### LCF-001 — Failed legacy-alias cleanup resurrects a later accepted neutral preference

Severity medium; confidence high; G2 (an accepted preference silently loses its requested durable effect at the next boot).

Actual flow: `linux/ergopti_hotstrings.lua:881` invokes `infra.legacy_hotstring_storage.import` before hotstring initialization and does not stop startup on its false return. That importer writes and adopts canonical leaves first (`linux/infra/legacy_hotstring_storage.lua:284,293`), then separately deletes old storage aliases (`:295–300`). A failed delete leaves an old alias eligible for the next import. The planner treats absence in config.toml as unclaimed (`:270`). The current menu owner writes a neutral choice by deleting its canonical leaf (`linux/infra/hotstring_preferences.lua:293`), and returns success after real publication (`:304–307`). Consequently, the legacy alias overwrites this later accepted neutral choice on the next startup.

Reproduction: seed synthetic legacy `hotstrings.preview_ai_enabled=false` (manifest default true); let config import publish successfully but refuse the native rename of storage.json once. Import returns false, daemon continues, current preview is false. Invoke `modules.hotstrings.preview_settings.set('ai', true)`, the production method used by the generated menu (`linux/ui/menu/menu_hotstrings.lua:1437`); it returns true and canonical preview leaf is absent as intended. Next startup import now succeeds, writes false again and finally deletes the old alias. The user's later successful choice has been lost. Genuine Storage, ConfigPaths, Preferences, PreviewSettings, TOML Writer and Import were used; only `os.rename` to the private storage.json was made to return a synthetic native permission error. No production owner or decision logic was replaced.

Receipts: `probes/legacy-neutral-real-storage.lua` and logs for LuaJIT and Lua5.4. Both record `native_rename_refusals=1`, `later_neutral_save=true`, `old_choice_resurrected=true`. `probes/legacy-neutral.lua` additionally demonstrates the successful-cleanup control: neutral survives when the initial alias deletion succeeds. The native file failure is injected, rather than a claim of reproducing an actual desktop permission problem.

This is not ADR009 preservation of retired entries: this alias is active migration input, not an unknown preserved row. The import's own explicit policy (`:21–24`) promises that a committed import never resurrects a later neutral choice. The initial cleanup error is logged truthfully; the later menu save and subsequent replay both report success and give no indication that an accepted newer choice is being superseded.

Regression target: retain the exact committed-import retirement state across a failed alias deletion, or prevent stale migration authority from overriding subsequent admitted edits. Test partial deletion, crash/restart, neutral sparse writes and explicit nonneutral config precedence, without erasing unknown fields or changing the intended default sparsity.

### LCF-002 — A rejected locale change remains canonical startup authority

Severity medium; confidence high. Additional property: truthful persistence failure and consistency between rejected choice, canonical saved state and next startup. No G1 crash, G3 async race, G4 performance or G5 engine-preview violation is claimed for this synchronous Linux manifestation. macOS has an additional deferred-timer variant documented by its owning agent.

`linux/ui/menu/menu_language.lua:50–54` returns the actual i18n setter result and refreshes the old checked locale after refusal. `linux/infra/i18n.lua:233–236` first rewrites an existing canonical `[script].locale`, then calls `_save_locale`. If native storage refuses, the public setter returns false and explicitly logs “was not persisted — nothing changed”; active locale and native alias remain old. The canonical row has already committed. At startup, `linux/infra/script_scope.lua:48–51` adopts that row into native storage; a fresh i18n initialization then loads the rejected choice.

Reproduction: private config `[script]\nlocale = "fr"`, real native storage alias fr, real i18n initialized fr. Refuse just the native storage.json rename while calling `set_locale('en')`. Return is false, RAM/native alias fr, but file is en. Restore native rename; run the production startup adoption and a fresh i18n module initialization: locale becomes en. The absent-config-row control is identical except no canonical script row exists: refusal leaves the file untouched and next startup remains fr. Receipts: `probes/locale-split-commit.lua` and LuaJIT/Lua5.4 logs. Real Storage, ConfigPaths, shared script authority, Writer, locale discovery/reader and i18n execute; only the native rename boundary refuses once. Module reinitialization models the actual fresh daemon lifecycle, not an in-process call to idempotent `init()`.

The explicit 2026-10-31 decision in `_shared/lua/script_config_authority.lua:13–19` makes existing config rows authoritative and requires rewriting them first; it does not declare that a rejected selection should be adopted later. The Linux receipt says nothing changed, whereas Windows `windows/infra/i18n.ahk:201–224` accepts durable canonical intent and `:239–250` explicitly says saved-but-reload-refused. Thus this is not a complaint about persistence preceding live application. Either a truthful accepted saved-intent receipt or exact conditional compensation with retained failure ownership would satisfy that distinction. Source-order siblings log-level/error-dialog were inspected but are not counted as separately reproduced findings.

## Rejected hypotheses and bounded observations

- Paths editor saving an unusable logs folder: rejected by real caller `LoggerSink.prepare_dir` before bootstrap publication; 21 native directory target scenarios and path bridge contracts pass.
- Locator change followed by reload using the old cached configuration path: rejected. The production reload callback starts a successor daemon; it reruns path/schema initialization. Failed restart is logged and not claimed current live application.
- Cleanup preview deleting bytes added by an external editor: rejected by exact preview source check, current record-root receipts, verified independent backup and conditional publication. Tests exercise stale/native-page ownership.
- Global clear/restore reporting success while inverse remains pending: rejected by retained composition debt and typed failure-point menu diagnostics; transaction/composition/global-owner tests pass.
- Unsupported schema silently normalized on ordinary save: rejected by sticky session write refusal and per-publication schema admission. Unknown retired values being kept is ADR009 policy.
- Startup configured-script adoption before schema boot: source ordering exists on Linux and macOS. Current registry has no script locale/log/error transformation that makes this a concrete stale-value defect; adoption does not rewrite the protected config file. Kept as a bounded ordering observation, not a fabricated product finding.
- Any two-store partial commit must be rolled back: rejected as a universal rule. Accepted saved intent is legitimate. LCF-002 uses exact rejected receipt, active/native old locale, canonical new locale and next-start result as its narrower violation.

## Performance, memory and native gaps

G4 is unmeasured for the actual Linux desktop. No event-to-output latency, jitter, desktop menu responsiveness or native permission behavior was benchmarked; passing headless contracts does not certify no lag. Ordinary Preferences reads use a cached document, and writes/cleanup are explicit actions rather than per-keystroke disk work; that is source provenance, not a performance claim.

Memory watch-list: schema destination/read-only registries, Storage ownership generations/cache and retained cleanup/debt, active cleanup scan source/model, global transaction runtime/file inverses and page opening epochs. Failed inverses intentionally retain exact ownership for retry; tests verify settlement/overlap, not long-running RSS bounds. Config-path restarts reclaim process-local registries; arbitrary prolonged failure/retry load was not measured. No leak confirmed.

Native gaps: actual GTK tray/WebKit lifecycle, process restart under a running session, permissions/ACLs on a real user filesystem, power loss/fsync durability, concurrent external processes in the final source-check-to-rename interval, and Windows/macOS native execution. Existing exact-source checks are not presented as an OS-wide interprocess transaction lock. Feature-specific import/export content semantics and every module's live scope participant are separate bounded scopes; this report covers their common configuration ownership and selected true callers, not every feature implementation.

Manifest tooling: pinned Node22 ran `tools/audit/workflow.cjs validate-report` against this scratch manifest; the existing CLI refused before schema validation because “report must be inside the repository” (`probes/logs/audit-validator.txt`). This is the expected location restriction for the parent-assigned read-only scratch artifact, not a passing canonical validation. No tooling was weakened and no report was copied into the repository. JSON parsing, required fields, exact SHA, known guarantee IDs and source identity were independently checked; integrated dated report validation belongs to the parent delivery step.
