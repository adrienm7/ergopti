## What the delta changes, and which old scope descriptions are superseded

1. **Embedded engine name: explicit user-facing identity decision.** `tools/build/build_macos_app.sh:543–544` now sets embedded CFBundleName and CFBundleDisplayName to `$ERGOPTI_APP_NAME`, so Accessibility/Input Monitoring/Notifications identify the app the user installed. CFBundleIdentifier still comes from `$HAMMERSPOON_BUNDLE_ID` at539. This supersedes any description saying macOS necessarily displays “Hammerspoon” in these permission surfaces. It does not rename the legacy migration roots, alter the environment authority, suppress the initial migration call, or change updater bundle/PID resolution.
2. **Owned-runtime first-install and approval: newly reachable automation.** `runtime_owner_ports.lua:214–229` now offers the existing owned-runtime install UI once for declared install reasons through deferred work; when the driver is installed but inactive, it starts `runtime_approval_watch`. The latter opens the Extensions pane, reads `systemextensionsctl list`, polls3seconds for up to its configured900-second elapsed sequence, and requests reload on the pinned active-driver assessment (`runtime_approval_watch.lua:55–80`). This supersedes “blocked availability only emits a notice” for these owned-runtime reasons. It does **not** supersede the distinctions between shared runtime vs owned runtime, macOS approval vs installation, or updater install vs runtime provision. This review does not validate wall-clock boundedness/native callback delivery of that new watcher.
3. **Approval reload uses the existing terminal owner.** Port `runtime_owner_ports.lua:201` calls `hs.reload()`; root292 wraps it through `TerminationCoordinator.request_reload` after initialization, preserving native early-boot fallback beforehand. This is a new reload trigger, not an updater disarm or a guard on `request_user_exit`. Even a successful later driver reload is not an app-launcher exit; it does not prove an already-armed chosen app swap was retired. No new protection refutes MUR-001's precise receipt/state mismatch.
4. **CoreLaunchctl / VirtualHID helper ownership moved, not migration ownership.** Native `OwnedRuntimeCoreLaunchctl.systemTool` limits executable tools to pkgutil/installer and retains bounded child execution; package payload validation/signature/install helpers moved private into `OwnedRuntimeVirtualHIDProvisionOwner`. The provision owner still verifies the sealed package/signature before installing. This supersedes file-location claims that packageSignature/installPackage remain CoreLaunchctl methods; it does not change chosen-release arm/swap or filesystem migration methods. This delta review is not proof of all native provision security properties.
5. **Path-catalog delta is Windows-only.** Parsed TOML changed only `runtime.windows.managed_ollama_folder_name`, removal of singular `migration.windows.legacy_ollama_folder` and addition of plural `legacy_ollama_folders`. All Mac path and migration data remain identical. Windows sibling→nested Ollama migration must not be described as a new Mac root migration.

No fixed/withdrawn finding is inferred merely from a shared build hash, a changed helper name, newly offered installation, or a scheduled reload. Native permission/provision behavior is a genuinely changed capability that should be described as such, without projecting it backward into unrelated updater/legacy-file safeguards.
